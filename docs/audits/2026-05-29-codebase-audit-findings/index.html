Endless Journey — Codebase Audit Findings

Date: 2026-05-29 Scope: First-party gameplay systems (vendored libs out of scope — see charter). Method: System-by-system end-to-end trace, correctness/hallucination-first. See charter. Phase: 1 (report only — no code changed). Phase 2 will plan fixes for the shortlist.

1. Summary​

The codebase is in genuinely good shape. The client-predict/server-authoritative pattern is applied consistently, the most security-sensitive systems (Placement, Shredder, Train Fuel, Stamina) have careful server-side validation, and lifecycle/cleanup is handled well across the board. No Critical issues were found.

The findings cluster into three themes:

  1. A few real exploits where a system trusts the client more than its peers do — most notably placeable theft and sound injection (neither validates the way Placement/Shredder do).
  2. Correctness/hallucination items — code or docs that reference behavior/structure that doesn't exist (an unimplemented eject cap, an orphaned material-pickup path, a latent math.random float bug, dead signals), plus a couple of resource-leak / item-loss edges.
  3. Consistency drift — mixed animation libraries (one explicit CLAUDE.md violation), dead config/API, and documentation that has fallen behind the code.

Headline issues (start here):

  • [P1] Any client can stash/steal every placed item in the server from anywhere (High, exploit).
  • [SND1] ReplicateSoundAtLocation relays arbitrary, unrate-limited client sounds to everyone (Medium, exploit).
  • [SH1] The documented shredder eject cap (MAX_ANIMATED_EJECT_ITEMS/DIRECT_GRANT_BATCH_SIZE) is not implemented — unbounded ejection (Medium, perf + doc hallucination).
  • [PP1] Merge + keepModel loses items when two identical dropped tools combine (Medium, correctness).
  • [PP2] MaterialPickupService is an orphaned, internally-broken pickup path (Medium, correctness).
  • [J1] Junk collection has no server-side proximity/aim check (Medium, exploit).

2. Findings by system​

Cross-cutting / contract layer​

[C1] Stale Packets header comment​

  • Severity: Low · Category: Consistency · Confidence: Confirmed
  • Location: Packets/init.luau:7
  • What: Header says "Defines every network packet used by the placement system." The module defines all packets (junk, shredder, train, sound, health, etc.).
  • Why: Misleads maintainers into thinking this is placement-only.
  • Fix: Reword to "Defines every network packet in the project."

[C2] RequestDrop packet undocumented​

  • Severity: Low · Category: Consistency / Doc · Confidence: Confirmed
  • Location: Packets/init.luau:161; absent from the networking map in Project-Maintenance-Guide.md
  • What: RequestDrop (C→S, drop active craft material) exists in code but is not in the documented networking map.
  • Fix: Add it to the networking-map table.

[C3] Dead signals (no producer or no consumer)​

  • Severity: Low–Medium · Category: Correctness / Dead code · Confidence: Confirmed
  • Location: Signals/init.luau
  • What: Several signals are half-wired:
    • ApplyTierMultiplier / ApplyTypeMultiplier — connected in JunkService:110/:117 but never fired anywhere (the dynamic spawn-modifier feature has no trigger).
    • RequestMouseIcon — consumed in ThirdPersonCameraController:90 but never fired. The "reveal cursor when a GUI opens" feature is therefore inert (guiRequestsMouse is always false).
    • OnServerHealthChanged — fired in HealthManager:78 but never consumed.
    • PlayHookEndSound — neither fired nor consumed (guide already notes it's legacy).
  • Why: Half-wired signals read as working features but do nothing; they mislead future work and hide the fact that (e.g.) the cursor-reveal path needs a producer before any crafting UI can use it.
  • Fix: Remove the truly dead ones; for RequestMouseIcon, add the missing producer when a cursor-needing UI is built (and note it's currently a no-op).

Junk​

[J1] No server-side proximity/aim validation on junk collection​

  • Severity: Medium · Category: Exploit · Confidence: Confirmed
  • Location: JunkService.server.luau:244 (ClaimJunkForPlayer) / :278 (FinalizeJunkForPlayer)
  • What: ReqJunkClaim/ReqJunkFinalize validate only that the junk id exists, isn't collected, isn't reserved by someone else, and a 1.1s per-player cooldown. There is no distance/aim check — by design the server doesn't track junk positions. A crafted client can claim+finalize any active junk id anywhere on the map (through walls, no aiming) at the cooldown rate.
  • Why: Bypasses the entire intended grab mechanic; lets an exploiter auto-harvest the whole junk stream. Rate-limited, so it's not unlimited, but it removes skill/positioning from the economy.
  • Fix: Either have the server track an approximate junk position (it can integrate the same odometer + spawn position it already has) and validate distance to the claimer, or bound claims to the junk's spawn region. Note the documented trade-off that the server intentionally avoids per-junk position tracking — closing this means accepting some of that cost.

[J2] Client junk leak on "claim without finalize"​

  • Severity: Medium · Category: Correctness / Leak · Confidence: Confirmed
  • Location: JunkController.client.luau:179 (BeginJunkRetract) + :239 (JunkCollected)
  • What: On BeginJunkRetract, the junk is removed from the sim and stored in retractingJunks, awaiting JunkCollected to return it to the pool. If finalize never succeeds (server reservation times out at 5s, collector disconnects, or the finalize RF returns false), JunkCollected never fires for that id: the pooled model is orphaned in JunksVisuals (invisible-frozen, never returned) and the retractingJunks entry leaks.
  • Why: Each occurrence permanently removes one model from the per-model pool (max 60). Under sustained play the pool can exhaust, after which new junk of that model silently fails to render.
  • Fix: Add a timeout (≈ reservation timeout + margin) that returns any still-retracting junk to the pool.

[J3] Dead state: distanceTravelled, TRAIN_SPEED, junk Yield​

  • Severity: Low · Category: Dead code · Confidence: Confirmed
  • Location: JunkService.server.luau:20-22, :319, :376
  • What: distanceTravelled is accumulated every Heartbeat but never read. Yield is stored per active junk but never used (yield is realized at shred time from JunkConfig, not at grab time).
  • Fix: Remove both (and the TRAIN_SPEED/isTrainMoving accumulator that only feeds the dead distanceTravelled).

[J4] Fragile JunkId guard​

  • Severity: Low · Category: Correctness · Confidence: Confirmed
  • Location: JunkController.client.luau:129
  • What: if model:GetAttribute("JunkId") then model:SetAttribute("JunkId", id) end. The guard passes only because the pool's reset sets JunkId = -1 (truthy). If the reset ever changes to clear the attribute, junk gets no id and becomes uncollectable. The guard serves no purpose.
  • Fix: model:SetAttribute("JunkId", id) unconditionally.

[J5] Per-frame table allocations​

  • Severity: Low · Category: Performance · Confidence: Confirmed
  • Location: JunkService.server.luau:327; GrabHook.client.luau:292
  • What: toRemove = {} allocated every Heartbeat/RenderStep. Junk despawn can remove keys during the pairs traversal instead (Luau permits setting an existing key to nil mid-iteration), avoiding the temp table.
  • Fix: Remove in place; or reuse a module-level scratch table with table.clear.

[J6] One missing tool folder aborts ALL tool initialization​

  • Severity: Medium · Category: Correctness · Confidence: Confirmed
  • Location: JunkToolManager.luau:74
  • What: Inside the per-junk loop, a missing parentFolder triggers return, aborting InitializeTools entirely. Every junk processed after the failing one gets no Tool created → those junk types can never be awarded on grab.
  • Fix: continue (skip the one) instead of return.

[J7] WaitForChild with no timeout hangs on missing world folder​

  • Severity: Medium · Category: Correctness · Confidence: Confirmed
  • Location: SpawnHelper.luau:15-21 (same anti-pattern in TeleportToSpawn.client.luau:9-15)
  • What: workspace:WaitForChild("SpawnVolumes") (no timeout) yields forever if the folder is absent, so the server hangs at require — and the if not folder then <create fallback> end block is unreachable dead code (WaitForChild never returns nil). The fallback also wouldn't assign back to folder.
  • Fix: Use FindFirstChild (or WaitForChild(name, timeout)) and make the fallback actually create-and-assign.

Placement​

[P1] Global placeable theft / griefing via Stash/Move​

  • Severity: High · Category: Exploit · Confidence: Confirmed
  • Location: PlaceableActionsServer.server.luau:89 (handleAction)
  • What: ReqStashPlaceable/ReqMovePlaceable validate type, PlacedObjects ancestry, attribute, template, cooldown, and an atomic claim — but no proximity and no ownership. A crafted client can enumerate workspace.PlacedObjects and stash/move any placement in the server from anywhere, destroying other players' builds and collecting the resulting Tools into its own Backpack.
  • Why: This is item theft + griefing at server scale. The doc frames it as "anyone nearby can stash" and relies on the per-placeable ProximityPrompt for locality — but that prompt is client-side and trivially bypassed by invoking the RemoteFunction directly. Contrast with PlacementServer, which does enforce server distance checks.
  • Fix: Add a server-side distance check (player HRP → model pivot, within prompt range + tolerance), and/or record a placement owner and restrict stash/move (the doc notes ownership tracking as a future option — this is the case for it).

[P2] Duplicated isGhostLocked state​

  • Severity: Low · Category: Consistency · Confidence: Confirmed
  • Location: BuildModeGuiController.client.luau:31 and PlacementClient.client.luau:63
  • What: Two independent isGhostLocked booleans kept in sync only by RequestGhostLockToggle. They can desync if either is ever toggled without firing the signal.
  • Fix: Single source of truth (let PlacementClient own it and broadcast lock state to the GUI).

Placement is otherwise the strongest system in the codebase — PlacementServer's origin/place distance checks, cooldown, isolated per-request validator, and server-side collision re-check are exemplary.

Stamina / Sprint​

[S1] Inert buff + restore subsystem​

  • Severity: Low · Category: Dead code / Incomplete · Confidence: Confirmed
  • Location: StaminaBuffManager.ApplyBuff:123, StaminaManager.RestoreStamina:169
  • What: ApplyBuff and RestoreStamina have no callers. The whole buff pipeline (StaminaBuffSync packet, buff icons in config, SprintController buff consumption, OnServerStaminaBuffStateChanged) is wired but never triggered — there is no buff-pickup source.
  • Why: Reads as a working feature; it's actually inert until something calls ApplyBuff.
  • Fix: Keep if buffs are imminent (document as pending); otherwise treat as scaffolding.

[S2] Doc overstates client prediction​

  • Severity: Low · Category: Consistency / Doc · Confidence: Confirmed
  • Location: SprintController.client.luau:126
  • What: The guide says the client "predicts drain/regen." The client never decrements currentStamina locally — it only consumes the 10 Hz StaminaStateSync. Behavior is fine (sync is fast), but it's consumption, not prediction.
  • Fix: Reword the doc, or add real local prediction if the 0.1 s granularity ever shows.

[S3] Client-authoritative WalkSpeed​

  • Severity: Low · Category: Exploit (inherent) · Confidence: Confirmed
  • Location: SprintController.client.luau:57 (updateSpeed)
  • What: Sprint speed is applied via humanoid.WalkSpeed on the client with no server reconciliation — the standard Roblox speed-exploit surface. Noted because the rest of the project is otherwise careful about server authority.
  • Fix: Out of scope for a quick fix, but if movement integrity matters, add server-side speed sanity checks.

GrabHook​

[G1] math.random used in integer domain for float pitch​

  • Severity: Medium · Category: Correctness (latent) · Confidence: Confirmed
  • Location: GrabHook.client.luau:149
  • What: math.random(GrabHookConfig.Sounds.MinSoundPitchShift, MaxSoundPitchShift) — math.random(m, n) returns an integer. It only works today because both are 1.0. Set the pitch range to fractional values (which the field names invite) and this errors / silently truncates. The pickup-sound path in the same file uses the correct float idiom (min + math.random()*(max-min), :183).
  • Fix: Use the float idiom for the fire pitch too.

The J1 exploit and J2 leak both surface through GrabHook (it initiates the claim/finalize flow), but the fixes live in JunkService/JunkController.

Shredder​

[SH1] Documented eject cap is not implemented (unbounded ejection)​

  • Severity: Medium · Category: Performance + Doc hallucination · Confidence: Confirmed (code); perf impact Suspected (load-dependent)
  • Location: config keys ShredderConfig.luau:79 & :86; eject loop ShredderServer.server.luau:268
  • What: MAX_ANIMATED_EJECT_ITEMS and DIRECT_GRANT_BATCH_SIZE are defined and documented (guide describes a cap on animated ejects with direct-grant overflow) but are referenced nowhere. ejectMaterials animates the entire material sequence with no cap. A large pile (dozens of high-tier junks → hundreds/thousands of materials) spawns that many Tool clones + SplineMove tweens + ProximityPickupServer.RegisterItem calls within MAX_STREAM_DURATION.
  • Why: Risks a server-wide frame spike / instance churn; and the docs claim a safeguard that doesn't exist.
  • Fix: Implement the cap (animate up to MAX_ANIMATED_EJECT_ITEMS, direct-grant the remainder in DIRECT_GRANT_BATCH_SIZE slices), or delete the dead config and correct the guide.

[SH2] ShredderClient uses TweenService (CLAUDE.md violation)​

  • Severity: Medium · Category: Consistency (explicit rule) · Confidence: Confirmed
  • Location: ShredderClient.client.luau:18, :169
  • What: The toast fade-out uses TweenService:Create, directly against CLAUDE.md ("Do not use TweenService for client-side animations — use MotionMaster instead"). It's the only TweenService use in the project. TrainClient's near-identical toast correctly uses MotionMaster (TrainClient.client.luau:88).
  • Fix: Replace with MotionMaster.Create(...) (mirror TrainClient).

Health​

[H1] Combat API has no callers​

  • Severity: Low · Category: Dead code / Incomplete · Confidence: Confirmed
  • Location: HealthManager.luau:226 (ApplyDamage/HealPlayer/GetHealth)
  • What: Damage/heal/query API is fully built and validated but unused (combat is a TODO). Intentional; flagged so it isn't assumed live.

[H2] Doc/memory say the health bar is TODO; it's actually wired​

  • Severity: Low · Category: Doc drift · Confidence: Confirmed
  • Location: HealthStaminaGuiController.client.luau:50
  • What: The guide/memory state the health bar is "scaffolded/commented/TODO." It's implemented — the controller consumes OnHealthValueChanged and animates the bar.
  • Fix: Update Project-Maintenance-Guide.md and the project-state memory.

[H3] HealthManager doesn't reconcile external Humanoid damage​

  • Severity: Low–Medium · Category: Correctness · Confidence: Confirmed (code); impact Suspected
  • Location: HealthManager.luau:187 (regen loop)
  • What: The manager mirrors its record → Humanoid.Health but never reads Humanoid → record. Damage from non-HealthManager sources (fall damage, default hazards) lowers the Humanoid but not the tracked record; the HUD then shows the stale full record, and regen won't run because the record thinks it's full.
  • Why: Latent until any damage source other than ApplyDamage exists.
  • Fix: Either disable Roblox-native damage sources, or listen to Humanoid.HealthChanged and reconcile.

Train Fuel​

The cleanest system audited — algebraic fuel model, nonce-guarded scheduling, careful server validation (engine/lever tag + prompt-distance), serialized refuel, and correct handling of the Lua 0 or x truthiness edge in commitEvent. No correctness/exploit findings.

[T1] Duplicated "has energy tool" scan​

  • Severity: Low · Category: Consistency · Confidence: Confirmed
  • Location: TrainClient.client.luau:162-181
  • What: The Backpack/Character energy-tool scan is inlined twice in the hold handler (and conceptually mirrors the server's gatherEnergyTools).
  • Fix: Extract a small local helper.

Proximity Pickup / Drops​

[PP1] Merge + keepModel loses items​

  • Severity: Medium · Category: Correctness / Item loss · Confidence: Confirmed
  • Location: merge ProximityPickupServer.luau:76; keepModel callback DroppedToolService.server.luau:102-104
  • What: Default-dropped Tools are registered with keepModel=true and a callback that moves the single tool to the Backpack (ignores Quantity). _TryMerge merges two same-type unclaimed items by summing Quantity and destroying the absorbed one. If two dropped tools merge, the survivor's Quantity becomes 2 but its keepModel callback returns only one tool → the player permanently loses one.
  • Why: Silent item loss whenever a player drops two identical materials near each other (within MERGE_RADIUS = 2 studs) inside the MERGE_DELAY window.
  • Fix: Exclude keepModel records from _TryMerge, or make keepModel callbacks honor Quantity (clone the template for the extra count).

[PP2] MaterialPickupService is orphaned and internally broken​

  • Severity: Medium · Category: Correctness / Dead-or-broken · Confidence: Confirmed (code); "Material" folder absence Suspected
  • Location: MaterialPickupService.server.luau:9
  • What: It registers CraftMaterial-tagged models that lack the PickupItem tag — but both real producers (ShredderServer:384-398 and CraftMaterialDropService:117-129) add PickupItem before CraftMaterial, so it never fires for them. Even if it did, its callback calls JunkToolManager.GetToolFromJunk(ItemType, ItemTier, "Material"), which needs a JunkTools/Tier{N}/Material folder (not created by JunkToolManager, which only builds Metal/Wood/Energy) and an ItemTier attribute that material handles never set — so it would warn and grant nothing.
  • Why: Confusing dead/broken parallel path; a maintainer could wire something to it expecting it to work.
  • Fix: Remove it, or repair it to the actual material scheme (Wood/Metal templates from CraftingMaterials, no tier).

[PP3] Duplicated landing-loop​

  • Severity: Low · Category: Consistency (DRY) · Confidence: Confirmed
  • Location: DroppedToolService.server.luau:45 and CraftMaterialDropService.server.luau:60
  • What: Two near-identical "poll GetTouchingParts until on a tagged surface and at rest, then register" loops.
  • Fix: Extract a shared helper (e.g. in a small DropLanding module).

[PP4] Self-defeating nil assert​

  • Severity: Low · Category: Correctness · Confidence: Confirmed
  • Location: ProximityPickupServer.luau:126
  • What: assert(part, "[...]" .. part:GetFullName()) — when part is nil the message expression indexes nil first, throwing a generic "attempt to index nil" instead of the intended assert text.
  • Fix: Drop part:GetFullName() from the message (or guard before building it).

[PP5] No mobile drop control​

  • Severity: Low · Category: UX / Consistency · Confidence: Confirmed
  • Location: DropController.client.luau:9
  • What: Drop is bound to G with createTouchButton = false — mobile players cannot drop materials, even though the rest of the UI has mobile parity.
  • Fix: Provide a mobile button (or enable the CAS touch button).

[PP6] Pickup zone has no owner restriction​

  • Severity: Low · Category: Design (decision needed) · Confidence: Confirmed
  • Location: ProximityPickupServer.luau:163 (zone Touched)
  • What: Any player who touches a pickup zone claims the item; shredder/drop output is grabbable by anyone until the 45 s auto-collect returns it to the owner.
  • Why: May be intended (shared loot) or a griefing vector (steal a shredder's output). Flagged as a design decision, not a bug.

Camera​

[CAM1] Frame-rate-dependent character rotation​

  • Severity: Low · Category: Correctness / Consistency · Confidence: Confirmed
  • Location: ThirdPersonCameraController.client.luau:151
  • What: hrp.CFrame:Lerp(target, CameraConfig.RotationLerpSpeed) uses a fixed per-frame alpha, so turn speed scales with FPS — unlike the 1 - exp(-k*dt) smoothing used in PlacementSystem/CameraBoom/TrainFuelGui.
  • Fix: local a = 1 - math.exp(-k * dt) with a tuned k.

The cursor-reveal dead signal (RequestMouseIcon) is covered under [C3].

Sound​

[SND1] ReplicateSoundAtLocation relays arbitrary, unrate-limited client sound​

  • Severity: Medium · Category: Exploit · Confidence: Confirmed
  • Location: ReplicatedSoundService.server.luau:6
  • What: The server relays any client's {Location, SoundConfig{Id, Volume, Pitch}} to all other clients with no validation and no rate limit. Packet typing constrains field types (Id: string, Volume: U8, Pitch: F16) but not values/content. A crafted client can inject an arbitrary SoundId (loud/inappropriate audio) and spam the call, playing it for everyone.
  • Why: Audio griefing + spam-driven client lag. The guide itself flags "consider spam-rate constraints."
  • Fix: Per-player rate limit, and restrict Id to an allowlist (e.g. the known config sound IDs) rather than relaying arbitrary strings.

[SND2] Pooled sound returned using TimeLength before it loads​

  • Severity: Low–Medium · Category: Correctness · Confidence: Confirmed (code); impact partly Suspected
  • Location: SoundController.client.luau:71
  • What: Return-to-pool is scheduled at task.delay(newSound.TimeLength + 0.01, ...), but Sound.TimeLength is 0 until the asset loads. For a not-yet-loaded sound this returns it to the pool almost immediately, cutting it off and churning the pool. Currently masked only because GrabHook preloads its sounds.
  • Fix: Wait for load (if not sound.IsLoaded then sound.Loaded:Wait() end) before reading TimeLength, or key the return off Sound.Ended.

Misc​

[M1] Eager client preload + legacy asset URL in GrabHookConfig​

  • Severity: Low · Category: Performance / Consistency · Confidence: Confirmed
  • Location: GrabHookConfig.luau:68 (legacy http://www.roblox.com/asset/?id= texture URL), :89-96 (PreloadAsync at require)
  • What: ContentProvider:PreloadAsync runs at module-require on the client (yields the first requirer); the beam texture uses the deprecated http://www.roblox.com/asset/?id=161381649 form rather than rbxassetid://.
  • Fix: Move preload to an explicit init/loading step; switch the texture to rbxassetid://.

3. Cross-cutting observations​

  • Authority is applied unevenly. Placement and Shredder do thorough server-side proximity + validation; PlaceableActions (P1), junk collection (J1), and sound relay (SND1) trust the client by comparison. Aligning the looser systems to the stricter pattern is the highest-value theme.
  • Half-wired features. Buffs (S1), combat (H1), the cursor-reveal signal (C3), and dynamic junk multipliers (C3) are all built-but-inert. None are bugs, but together they make it hard to tell what actually runs. A short "pending wiring" list (in docs or memory) would help.
  • Animation library drift. The project standard is MotionMaster; TweenPlus is used in several controllers (SprintController, HealthStaminaGuiController, PlacementSystem color tween) and TweenService appears once (SH2, an explicit CLAUDE.md violation). Decide whether TweenPlus is sanctioned; fix SH2 regardless.
  • Docs have drifted. The shredder eject cap (SH1), the health bar status (H2), and the RequestDrop packet (C2) are all out of sync between code and the maintenance guide.
  • Two WaitForChild-without-timeout fallbacks are unreachable (J7) — a recurring misunderstanding worth a quick sweep for other instances.

  1. [P1] Server proximity/ownership check on Stash/Move (High exploit).
  2. [PP1] Stop item loss on merge + keepModel (Medium correctness).
  3. [J6] continue instead of return in JunkToolManager (Medium correctness).
  4. [J7] Fix the WaitForChild-no-timeout hang in SpawnHelper/TeleportToSpawn (Medium correctness).
  5. [G1] Fix the latent math.random float-pitch bug (Medium correctness).
  6. [SND1] Rate-limit + allowlist the sound relay (Medium exploit).
  7. [J1] Add server-side proximity validation to junk collection (Medium exploit).
  8. [J2] Reclaim leaked retracting junk (Medium leak).

Tier 2 — hallucination/consistency cleanup 9. [SH1] Implement or remove the eject cap; fix the docs. 10. [PP2] Remove or repair MaterialPickupService. 11. [SH2] ShredderClient → MotionMaster. 12. [SND2] Sound return keyed off load/Ended. 13. [C2]/[H2] Doc sync (RequestDrop, health bar status). 14. [C3] Resolve dead signals.

Tier 3 — low-risk polish 15. The remaining Low items (J3, J4, J5, P2, S1–S3, H3, T1, PP3–PP6, CAM1, M1) — batch as a cleanup pass.
