Workbench Crafting

A placed Workbench station lets players craft weapons, armor, and placeables from config-defined recipes in a single server-authoritative round-trip. Crafting is instant (no hold duration) and per-player. The station is placed in the world by the existing placement system and interacted with through a ProximityPrompt; Stash/Move of the Workbench itself is handled by the existing PlaceableActions system.

Data flow​

Client (WorkbenchGuiController)             Server (WorkbenchService)
──────────────────────────────────────────────────────────────────────

── OPEN ─────────────────────────────────────────────────────────────
Player walks within INTERACT_DISTANCE
  ProximityPrompt fires (CraftPromptPart)
  GUI opens; recipe grid populated from WorkbenchConfig.Recipes
  TechTreeUnlocked folder checked → grey any gated recipe
    whose RequiresNode value is not yet in the folder

── SELECT RECIPE ────────────────────────────────────────────────────
Player clicks a recipe tile
  Detail panel shows DisplayName, Description, Tier badge,
  Cost rows (Wood / Metal — exactly two rows max), RequiresNode note

── CRAFT ────────────────────────────────────────────────────────────
Player clicks Craft button
  ──── ReqCraft(bench: Instance, recipeId: String) ─────────────►
  Server (WorkbenchService) validates, in order:
    look up recipe in WorkbenchConfig
      (else UNKNOWN_RECIPE)
    verify bench is a tagged Workbench Model
      (else INVALID_TARGET)
    re-check proximity
      (INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE)
      (else TOO_FAR)
    CRAFT_COOLDOWN gate (per-player timestamp)
      (else COOLDOWN)
    check RequiresNode gate in TechTreeUnlocked
      (else LOCKED)
    CraftOutputDispatcher.isFeasible(recipe.Output)
      → verify output slot is usable BEFORE consuming any materials
      (else OUTPUT_FAILED)
    player holds enough cost materials
      (else INSUFFICIENT_MATERIALS)
  on pass: consume materials from player Backpack, then
    CraftOutputDispatcher.grant(player, recipe.Output)
      Kind == "Weapon"    → clone from WeaponTemplates
      Kind == "Armor"     → ArmorManager.SetTier(player, output.Tier)
      Kind == "Placeable" → grant PlaceableTools Tool
    record cooldown timestamp
  ◄── (success: Boolean8, code: NumberU8) ──────────────────────────
  if success:
    Signals.OnItemCrafted:Fire(recipeId)
    GUI shows success FX / SoundManager.PlaySFX(CraftSuccess)
  else:
    show failure toast / SoundManager.PlaySFX(CraftFail)

Client / Server / Shared​

Shared — WorkbenchResultCodes.luau (ReplicatedStorage/SharedModules/) is a frozen result-code enum identical in role to TechTreeResultCodes. Every reject reason (NONE, UNKNOWN_RECIPE, INVALID_TARGET, TOO_FAR, COOLDOWN, LOCKED, OUTPUT_FAILED, INSUFFICIENT_MATERIALS) is defined here so neither side ever uses bare string literals in business logic.

Shared — Configs/WorkbenchConfig.luau (ReplicatedStorage/SharedModules/Configs/) is the single tuning surface: interaction constants, output template folder names, category lists, sound keys, and the Recipes table. See Config knobs below.

Shared — WorkbenchValidation.luau (ReplicatedStorage/SharedModules/) is a pure, stateless validator with no Roblox service calls. It runs on both client (button-greying, cost display) and server (authority). Exported functions mirror the pattern from TechTreeState: recipe existence, gate check, material sufficiency.

Server — WorkbenchService.server.luau (ServerScriptService/) is the sole owner of the authoritative ReqCraft handler. It resolves the bench instance, re-checks proximity, runs WorkbenchValidation, calls CraftOutputDispatcher.isFeasible before touching any materials, then consumes materials and calls CraftOutputDispatcher.grant. Manages the per-player cooldown timestamp.

Server — CraftOutputDispatcher.luau (ServerStorage/SharedModules/) handles the three output kinds:

  • Kind == "Weapon" — clones the named Tool from ServerStorage/WeaponTemplates into the player's Backpack.
  • Kind == "Armor" — calls ArmorManager.SetTier(player, output.Tier), updating ArmorState/<UserId>.ArmorBaseReduction in ReplicatedStorage.
  • Kind == "Placeable" — grants the named Tool from ReplicatedStorage/PlaceableTools/<Name> into the player's Backpack.

isFeasible(output) verifies the target output slot is usable (e.g. the template exists, the tier is valid) before materials are consumed. A misconfigured recipe never costs the player materials.

Client — WorkbenchGuiController.client.luau (StarterPlayer/StarterPlayerScripts/) opens via the bench CraftPromptPart ProximityPrompt. Builds the recipe grid from WorkbenchConfig.Recipes and greys any recipe whose RequiresNode is not present in ReplicatedStorage/TechTreeUnlocked. Fires ReqCraft on the Craft button and fires Signals.OnItemCrafted on a confirmed success. The CloseButton closes the GUI. The DropdownButton is driven by the reusable Dropdown widget, which fires Signals.RequestWorkbenchCategory on selection to re-filter the grid. Uses a Janitor per GUI open/close lifecycle.

Recipe schema​

Recipes are declared in WorkbenchConfig.Recipes as a { [string]: Recipe } table keyed by a string recipe ID.

export type Output =
    { Kind: "Weapon",   ToolName: string }
  | { Kind: "Armor",    Tier: number }
  | { Kind: "Placeable", PlaceableName: string }

export type Recipe = {
    Category:    string,    -- one of RecipeCategories ("weapons"|"ammo"|"armor"|"workstation")
    DisplayName: string,
    Description: string,
    Tier:        number,    -- 1..5 flavor/quality badge only; NOT a prerequisite ladder
    Icon:        string,    -- rbxassetid:// string for the grid tile and detail panel
    Cost:        { Wood: number?, Metal: number? },
    RequiresNode: string?,  -- TechTree nodeId gate; nil = always available
    Output:      Output,
}

Tier is a purely cosmetic quality badge displayed as a star rating in the GUI. It has no prerequisite chain and imposes no unlock order — any recipe with RequiresNode = nil is available to craft at any time regardless of Tier. The only unlock gate is RequiresNode.

The Cost table is limited to Wood and Metal because the GUI renders exactly two material rows. Adding a third material requires a GUI layout change and a matching config key.

Tech-Tree gate seam​

TechTreeService publishes unlocked node IDs into a ReplicatedStorage/TechTreeUnlocked folder (a BoolValue per unlocked node, named by nodeId) in parallel to the existing TechTreeBuffs folder. This folder is written by the server when a node unlocks and is read by:

  • WorkbenchService (server): authoritative gate check. A craft request whose recipe has a non-nil RequiresNode is rejected with LOCKED if the corresponding BoolValue is absent or false. Because the folder is written by the server, clients cannot forge an unlock.
  • WorkbenchGuiController (client): greying. Recipes with a locked RequiresNode are rendered as unavailable in the grid so players know they need to unlock the tech node first. The client reads this folder but never writes it.

See Tech Tree for the full TechTreeService data flow and the TechTreeBuffs folder contract.

Studio setup​

  1. Tag the Workbench Model. In ReplicatedStorage/PlaceableItems/Workbench, tag the root Model with the CollectionService tag Workbench (the same tag the Shredder scans for — one Model serves as both crafting station and shredder). Give it a BasePart named CraftPromptPart (anywhere under the Model — PromptResolver finds it recursively) containing a ProximityPrompt. Set the Model's PrimaryPart. The shredder half uses a sibling ShredPromptPart.

  2. Create ServerStorage/WeaponTemplates. Add a folder named WeaponTemplates inside ServerStorage. Place craftable weapon Tools here (e.g. clones of Pistol and SMG from StarterPack). These are separate from the StarterPack copies — the Workbench clones from here into the player's Backpack, so stat changes or visual differences can live here independently.

  3. Ensure craftable placeables exist. Each recipe with Output.Kind == "Placeable" needs a Tool at ReplicatedStorage/PlaceableTools/<PlaceableName>. The Workbench itself already follows this convention as a grid-placeable item.

  4. Material templates are shared. ReplicatedStorage/CraftingMaterials already holds Wood and Metal Tool templates (shared with the Shredder and Tech Tree systems). No duplication is needed.

  5. Wire TechTreeUnlocked. TechTreeService creates and writes this folder automatically at runtime. No manual Studio setup is required for the gate to function. If testing in isolation (without a running TechTreeService), create a Folder named TechTreeUnlocked in ReplicatedStorage and add BoolValue children named after whichever node IDs you want to treat as unlocked.

Gotchas / anti-exploit​

Server re-checks proximity on every craft

The client proximity prompt is never trusted. WorkbenchService re-runs the distance check using INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE on every ReqCraft call. A player exploiting from range receives TOO_FAR.

Feasibility is checked before materials are consumed

CraftOutputDispatcher.isFeasible(recipe.Output) runs (and must succeed) before any material Tool is removed from the player's Backpack. A recipe that references a missing weapon template or an invalid armor tier therefore fails without costing the player anything. Misconfigured recipes are safe to ship; they only result in a visible craft failure.

Tech-Tree gate is read from server-written state

The TechTreeUnlocked folder is written exclusively by TechTreeService on the server. A client cannot create or modify entries in that folder. The server re-reads the folder on every ReqCraft call, so a client that somehow fakes the UI greying cannot bypass the gate.

Cost is limited to Wood and Metal

The GUI renders exactly two material rows. Cost may only specify Wood and/or Metal. Adding a third material type (e.g. Energy) requires a GUI layout change alongside the config key — otherwise the cost is silently unchecked on the client (though the server will still validate it).

Tier is a flavor badge, not a prerequisite ladder

Tier (1–5) drives the star-rating display only. There is no inter-recipe prerequisite chain derived from Tier values. The sole unlock gate is RequiresNode. Do not attempt to use Tier as a crafting order enforcer — it will not work without code changes.

Known edge case: respawn mid-craft (v1)

If a player's Backpack disappears between the feasibility check passing and CraftOutputDispatcher.grant executing (e.g. the player respawns during that narrow window), materials may be consumed but the grant returns OUTPUT_FAILED. The client receives a failure response and the player loses the materials. This is an accepted v1 limitation — the window is sub-frame in practice. A future refund path or a pre-grant Backpack re-check is the recommended fix.
