Settings (User Preferences)

A generic, server-authoritative user-preferences system. Every persisted preference — the four audio bus volumes (MasterVolume, MusicVolume, SFXVolume, AmbienceVolume) and camera sensitivity today, anything else in the future — is one entry in a single typed registry, validated by one shared schema, and synced/saved through one packet pair. There is no per-setting packet, no per-setting DataStore key, and no bespoke client-side state machine; adding a setting is a config-table edit, not a new subsystem.

Data flow​

Join:
SettingsManager.onPlayerAdded(player)
  └─> PlayerStore:StartSessionAsync (ProfileStore, STORE_NAME = "PlayerSettings")
        ├─> migrateLegacyVolumes(profile)   -- copies old Volumes{bus} -> Settings{key}, idempotent
        ├─> profile:Reconcile()             -- fills missing keys from SettingsConfig.GetDefaults()
        ├─> profile.Data.Settings = SettingsSchema.Sanitize(profile.Data.Settings)
        └─> Packets.SyncSettings:FireClient(player, profile.Data.Settings)
              └─> SettingsClient (Packets.SyncSettings.OnClientEvent)
                    └─> for each key: SettingsSchema.Validate -> applyAndNotify
                          ├─> SettingsAppliers.Apply(key, value)  -- e.g. Groups.SetVolume
                          └─> Signals.OnSettingChanged:Fire(key, value)   (no re-save)

Manual change (GUI calls SettingsClient.Set):
SettingsClient.Set(key, value)
  └─> SettingsSchema.Validate(key, value) -- reject unknown key / wrong type / out of range
        └─> applyAndNotify(key, coerced)
              ├─> SettingsAppliers.Apply(key, coerced)      -- immediate local effect
              └─> Signals.OnSettingChanged:Fire(key, coerced)
        └─> scheduleSave(key, coerced)    -- debounced 0.25s, coalesces rapid changes
              └─> Packets.SaveSetting:Fire(key, coerced)
                    └─> SettingsManager (Packets.SaveSetting.OnServerEvent)
                          └─> SettingsSchema.Validate(key, value) -- server re-validates, never trusts client
                                └─> profile.Data.Settings[key] = coerced   -- ProfileStore autosaves

Client / Server / Shared​

Shared — SettingsConfig (ReplicatedStorage/SharedModules/Configs/SettingsConfig.luau)

Pure data, no client dependencies, so the server can require it directly. SettingsConfig.Definitions is the single registry — one entry per setting key, typed as:

export type Definition = {
    type: "number" | "boolean" | "enum",
    default: any,
    category: string,
    label: string,
    order: number,
    min: number?,
    max: number?,
    step: number?,
    options: { string }?,
}

SettingsConfig.GetDefaults() returns a fresh { [string]: any } map of every key to its default — this seeds both a brand-new ProfileStore profile and profile:Reconcile() for existing ones. SettingsConfig.VolumeBusByKey maps the four volume setting keys (MasterVolume, MusicVolume, SFXVolume, AmbienceVolume) to their SoundConfig/Groups bus name (Master, BGM, SFX, Ambience) — the one place that mapping is declared, reused by both the migration step and SettingsAppliers. SettingsConfig.STORE_NAME ("PlayerSettings") is the ProfileStore name and must not change without a migration plan, since it is also where the legacy Volumes table is read from.

Shared — SettingsSchema (ReplicatedStorage/SharedModules/SettingsSchema.luau)

The single validator, called identically by server and client so the two sides can never disagree on what's valid:

  • SettingsSchema.Validate(key, value): (boolean, any) — looks key up in SettingsConfig.Definitions (unknown key is rejected, acting as an allowlist). For "number", rejects non-numbers and NaN, then clamps to [min, max] (open-ended if either bound is nil). For "boolean", requires an exact boolean. For "enum", requires the value to be a member of options. Returns (true, coercedValue) on success, (false, nil) on failure.
  • SettingsSchema.Sanitize(map): { [string]: any } — builds a complete settings map: starts from SettingsConfig.GetDefaults(), then overlays every entry in map that passes Validate. Anything invalid or no longer in the registry (a setting that was removed) is silently dropped. Used by SettingsManager on join so the synced map is never missing a key or carrying a stale one.

Server — SettingsManager (ServerStorage/SharedModules/SettingsManager.luau)

The authority. Owns one ProfileStore session per player (PlayerStore:StartSessionAsync(tostring(player.UserId), ...)), following the same lifecycle pattern as CoinManager/XPManager: kicks the player if the session fails to start, ends the session and re-kicks on OnSessionEnd, and ends the session on PlayerRemoving.

On join (onPlayerAdded), before profile:Reconcile() runs, migrateLegacyVolumes(profile) does a one-time, idempotent copy: for every key in SettingsConfig.VolumeBusByKey, if Settings[key] is still unset and the legacy profile.Data.Volumes[bus] is a valid number, it's validated and copied into Settings[key]. Once a key exists in Settings it is never overwritten from Volumes again, so this is safe to leave running indefinitely — it is a no-op for any profile that has already migrated or that never had legacy Volumes data. The legacy Volumes table itself is left in place (not cleared) after migration.

SettingsManager.Initialize() (called once per server) wires Packets.SaveSetting.OnServerEvent: looks up the player's profile (drops the message if none — e.g. a setting saved before session start finished), checks key is a string, re-validates (key, value) through SettingsSchema.Validate, and on success writes profile.Data.Settings[key] = coerced. There is no explicit save call — ProfileStore autosaves the profile. Any invalid or unknown-key message is silently dropped; the server never trusts the client's claim that a value is valid.

Client — SettingsClient (StarterPlayer/StarterPlayerScripts/SettingsClient.luau)

The only module the settings GUI talks to. Holds a local cache of every setting's current value and exposes:

  • SettingsClient.Get(key): any — returns the cached value, or the definition's default if never set.
  • SettingsClient.Set(key, value): boolean — validates via SettingsSchema; on success applies + announces immediately (see applyAndNotify below) and schedules a debounced save; returns false without any side effect if validation fails.
  • SettingsClient.GetAll(): { [string]: any } — a full snapshot keyed by every key in SettingsConfig.Definitions.
  • SettingsClient.GetDefinition(key): SettingsConfig.Definition? — the raw definition, for a GUI to read min/max/step/label/options when building a control.
  • SettingsClient.GetByCategory(): { [string]: { { key, definition } } } — every definition grouped by category and sorted by order within each group; this is what a settings menu iterates to build its tabs/sections (today: "Audio" with 4 entries order 1-4, "Controls" with 1 entry).
  • SettingsClient.Init() — connects Packets.SyncSettings.OnClientEvent once; idempotent (a second call is a no-op). Called once by SettingsController.client.luau at startup.

Internally, applyAndNotify(key, value) is the shared path for both the join-sync handler and Set: it writes the cache, calls SettingsAppliers.Apply(key, value), then fires Signals.OnSettingChanged:Fire(key, value). The join-sync path calls only applyAndNotify (never scheduleSave), which is what prevents applying the server's own synced values from looping back into another save.

scheduleSave(key, value) debounces persistence per key: the latest value for that key is stashed in a pending table, and a single task.delay(0.25, ...) per key sends the trailing value via Packets.SaveSetting:Fire(key, value). Rapid changes to the same key (e.g. dragging a volume slider) collapse into one network send 0.25s after the drag settles, rather than one send per frame.

Client — SettingsAppliers (StarterPlayer/StarterPlayerScripts/SettingsAppliers.luau)

A client-only key -> (value) -> () registry, kept deliberately separate from SettingsConfig so the shared config module stays free of client-only dependencies (Groups, UserSettings()) that the server must never require. Built once at require time:

  • The four volume keys are wired generically by iterating SettingsConfig.VolumeBusByKey and calling Groups.SetVolume(bus, value) for each.
  • CameraSensitivity writes UserGameSettings.MouseSensitivity = value directly (engine range 0..4, matching the definition's min/max).

SettingsAppliers.Apply(key, value) looks up and calls the applier for key, or no-ops silently if the key has no client-side effect (a setting can exist purely for server-side or analytics purposes without ever needing an entry here).

Adding a new setting​

Two steps, at most:

  1. Add one entry to SettingsConfig.Definitions — pick a unique key, a type ("number" | "boolean" | "enum"), a default, a category + label for the GUI, an order within that category, and the relevant bounds (min/max/step for "number", options for "enum"). That's enough for the setting to round-trip end to end: it will seed into new profiles, sync on join, validate, and persist.
  2. If the setting has a direct client-side effect, add a matching entry to SettingsAppliers's appliers table — a one-argument function that applies value. Skip this step entirely for settings with no client effect (e.g. a server-only gameplay toggle, or something a future system reads via SettingsClient.Get on demand instead of reacting to OnSettingChanged).

No packet, schema, or ProfileStore change is needed for a new setting — SettingsSchema.Validate and SettingsManager are fully generic over the Definitions table.

Gotchas​

Never call SettingsAppliers or SettingsManager's internals directly

GUI code should only ever call SettingsClient.Get/Set/GetAll/GetDefinition/GetByCategory and listen to Signals.OnSettingChanged. Calling SettingsAppliers.Apply directly skips validation, caching, and persistence — the value will apply visually but never save and will be wiped out by the next join-sync. Calling into SettingsManager from client code is not possible (it's a server-only module) and calling Packets.SaveSetting:Fire directly skips client-side validation and the cache, which desyncs SettingsClient.Get from what the server actually has.

  • The join-sync path never re-saves. SettingsClient.Init()'s Packets.SyncSettings.OnClientEvent handler calls applyAndNotify directly, not Set — this is intentional and must stay that way, or applying the server's own synced values would immediately re-fire a save back to the server in a feedback loop.
  • SettingsManager.Initialize() re-validates every SaveSetting message. A modified or out-of-date client can fire any (key, value) pair; the server drops anything that fails SettingsSchema.Validate (unknown key, wrong type, out-of-range number) rather than trusting the client's own clamping.
  • Legacy Volumes data is migrated, not deleted. migrateLegacyVolumes copies old per-bus volumes into the generic Settings map once, but the old Volumes table is left on the profile afterward. Don't write new code that reads profile.Data.Volumes — it is dead weight kept only for the migration step, not a second source of truth.
  • Removing a Definitions entry doesn't delete saved data, but does stop syncing it. SettingsSchema.Sanitize drops any key no longer present in Definitions from the map it returns, so a removed setting simply disappears from SyncSettings/GetAll going forward — it does not actively scrub the old key from the ProfileStore document.
