Perks

A level-driven permanent progression system that lets players spend points on persistent buffs backed by ProfileStore. Two independent point pools — Personal (buffs the owner only) and Party (buffs are resolved as the server-max of all players) — each grow by exactly 1 point per XP level. Points are derived, never stored; only PerkLevels (a { [perkId]: number } map) persists. Respecs are free.

Point economy​

  • Each level-up grants 1 Personal point AND 1 Party point.
  • Available points = playerLevel - sum(spent in that pool).
  • Points cannot go negative; the pool is floored at 0.
  • Respec costs nothing and returns all points in the chosen pool.
  • Points carry across places because PerkManager uses the same DataStore key (PlayerPerks) everywhere in the universe.

Party-max resolution​

Party perks (Salvage Luck, Fuel Efficiency, Thrift, Shield Capacity, Heavy Ordnance) apply to the entire server, but only the highest level held by any single player is active. If Player A has Salvage Luck 6 and Player B has Salvage Luck 3, the server resolves at 6. PerkEffectsDispatcher recomputes the max on every allocate, respec, player join, and player leave.

Buff contract​

PerkEffectsDispatcher is the sole writer of the buff folders. Other systems read only — never write.

Armor damage mitigation. Crafted armor (see ArmorConfig / ArmorManager) publishes a per-player ArmorState/<UserId>.ArmorBaseReduction — the base fraction of incoming damage removed by the player's current armor tier. The Armor perk no longer reduces damage on its own; it is an efficiency multiplier on that base. HealthManager.applyDamageInternal reads both per hit and computes reduction = clamp(ArmorBaseReduction * (1 + ArmorEfficiency), 0, 0.75), then scales amount by (1 - reduction) as the final step before subtracting from health. With no armor (tier 0 → base 0) the perk contributes nothing. Because the attacker's DamageBonus is already applied upstream in WeaponServer, attacker bonus and defender mitigation multiply independently: base * (1 + DamageBonus) * (1 - reduction). Coverage is every path routed through CombatService/HealthManager (Melee/Bullet/AOE and NPC hits); damage written directly to Humanoid.Health bypasses the sink and is not mitigated (see Health).

Client / Server / Shared​

Shared — PerkConfig.luau is the single tuning surface: 12 perk declarations with Category, BuffKey, PerLevel, MaxLevel, DisplayName, Description, display Order, and an optional ValueKind. Tune values here — do not hard-code them in logic. PerkConfig.STORE_NAME is the ProfileStore key, identical across all places.

ValueKind controls GUI effect-string formatting in PerkClient.effectFor: nil/"percent" (the default, used by every perk except Net Cast) renders Description with %d replaced by the whole-percent bonus (floor(PerLevel * level * 100 + 0.5)); "count" (used only by Net Cast) renders %d as a raw total, baseline 1 plus the bonus (1 + floor(PerLevel * level + 0.5), i.e. 1 + NetCapacityBonus) instead of a percentage — so "Grab up to %d junk at once" reads as "Grab up to 3 junk at once" at level 2 (1 baseline + 2 bonus), not a percent value.

Shared — PerkResultCodes.luau is the frozen result-code enum (OK=0, NO_PROFILE=1, UNKNOWN_PERK=2, AT_MAX_LEVEL=3, NO_POINTS=4). Used by both the server handler and the client UI.

Shared — PerkState.luau is a pure, side-effect-free module with three functions: spent(perkLevels, category), available(perkLevels, category, playerLevel), and canAllocate(perkLevels, perkId, playerLevel). The server uses it for authoritative validation; the client uses it to gate the + button.

Server — PerkManager.luau owns the PlayerPerks ProfileStore (one session per player). AllocatePoint and Respec validate, mutate PerkLevels, fire OnPerkStateChanged, and replicate. Initialize wires PlayerAdded, PlayerRemoving, packet handlers, and OnPlayerLevelUp re-replicate. GetPerkLevels(player) returns the live reference for PerkEffectsDispatcher.

Server — PerkSystemLoader.server.luau calls PerkManager.Initialize() once per server.

Server — PerkEffectsDispatcher.server.luau is the sole writer of both buff folders. It listens to OnPerkStateChanged, PlayerAdded, and PlayerRemoving, then calls publishPersonal (per-player attributes) and publishParty (server-max across all players). Also bridges Junk Rarity to Signals.ApplyTierMultiplier (which JunkService already consumes).

Client — PerkClient.luau is the GUI-agnostic data layer (owns no GUI). It caches the authoritative PerkStateSync snapshot, watches the replicated PartyPerkBuffs folder, and exposes queries returning PerkView descriptors (GetPerks/GetActivePerks/GetAvailablePoints/GetPerk), commands with optimistic prediction (Allocate/Respec/CanRespec), and a Changed signal. "Active" is category-aware: a Personal perk is active at the player's Level > 0; a Party perk is active at its server-wide ActivePartyLevel > 0. Perk screens are authored separately, require PerkClient, and subscribe to Changed to repaint.

Client — PerkController.client.luau is a one-line bootstrap that calls PerkClient.Init() once on join so the data layer is warm before any GUI opens.

Gotchas​

Points are derived, not stored

PerkLevels is the only persisted data. Available points = level - spent. Never add a separate stored point counter — it will desync.

Party perk levels shown in the GUI are per-player, not the resolved active level

The + button and level display in the Party tab show how many points this player has invested. The (active N) sub-label shows the server-resolved max. Both are expected: a player at level 3 in a party where someone else is at level 7 sees Lv 3/10 (active 7).

PerkEffectsDispatcher must run before PerkManager on join

PerkEffectsDispatcher seeds its folder at boot. PerkManager fires OnPerkStateChanged after profile load, which triggers a republish. The ordering is correct because both are ServerScriptService scripts and PerkManager.Initialize() is called from PerkSystemLoader, which yields on ProfileStore:StartSessionAsync before firing the signal.

HPBonus subscription attaches once at join

HealthManager subscribes to the HPBonus attribute change in PlayerAdded, not CharacterAdded. If PerkBuffs/<UserId> does not exist at join time (the dispatcher hasn't seeded yet), the subscription is skipped for that session. In practice the dispatcher seeds synchronously at boot, so the folder exists before any player's PlayerAdded fires normally.
