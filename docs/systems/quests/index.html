Quests (Daily & Weekly)

A rotating, ProfileStore-backed quest system layered on top of the coin/XP economy. Four buckets — Personal/Party × Daily/Weekly — rotate on a global, deterministic schedule so every player and every server in a given period sees the same active quests. A fifth, non-rotating Season scope (see Season quests) additionally feeds the Battle Pass. Progress is server-authoritative; rewards pay coins (via CoinManager.AddCoins) and exp (via XPManager.AddXP), plus an optional Reward.BPExp battle pass feed. The system is split shared/server/client exactly like Perks: a pure shared module for period math + set selection, a server manager owning the profile and authority, and a GUI-agnostic client read-model.

Buckets​

Each period (Daily or Weekly) rotates in a fixed count of quests per category, set by QuestConfig.Counts:

ScopePersonalParty
Daily12
Weekly11
  • Personal quests credit only the player who performed the action (e.g. collecting junk).
  • Party quests credit every player in the server for ownerless world events (enemy kills, train distance) — a shared team objective, but the reward is still claimed and paid out per player.

Global rotation​

The active quest ids for a scope are never stored — they're recomputed deterministically by QuestState.selectQuests(scope, periodIndex) from the period index alone: a seeded Fisher-Yates shuffle (distinct large-prime seeds per category so Personal and Party picks don't correlate) over the sorted id pool for that scope+category, sliced to Counts, then re-sorted for stable display order. Given the same periodIndex, every machine — client or server, any server in the universe — produces the identical set. Only progress, claimed flags, period indices, and lifetime stats persist on the PlayerQuests profile; the set itself is derived, not saved.

Period math​

Period indices come from os.time() (UTC), never client input:

  • Daily rolls at 00:00 local (QuestConfig.DailyResetOffset): QuestState.dayIndex(now) = floor((now - DailyResetOffset) / 86400).
  • Weekly rolls Monday 00:00 local (QuestConfig.WeeklyResetOffset, a 4-day base offset — the Unix epoch was a Thursday, so shifting 4 days aligns week starts to Mondays): QuestState.weekIndex(now) = floor((now - WeeklyResetOffset) / 604800).
  • Both offsets are derived from QuestConfig.ResetTimezoneOffset — a fixed seconds-from-UTC offset that defines the timezone "midnight" is measured in (pre-launch default: US Eastern, -5 * 3600). It's a fixed offset, so it does not track daylight saving. Set it to 0 for pure UTC resets. DailyResetOffset = -ResetTimezoneOffset; WeeklyResetOffset = 345600 - ResetTimezoneOffset.
  • QuestState.dailyExpiresAt / weeklyExpiresAt compute the unix timestamp the current period ends at, sent to the client for a live countdown (no client-side period math needed).

Season quests​

A fifth Scope = "Season" exists alongside Daily/Weekly, dedicated to feeding the Battle Pass. It doesn't rotate like the other scopes — QuestState.selectQuests("Season", periodIndex) returns the entire curated set (Personal ids then Party ids, each sorted), not a Counts-limited shuffle-and-slice — so every Season quest is active for the whole month. Its period index is BattlePassState.seasonIndex(now) (a calendar-month index), not a quest-owned index, so a season's quests reset in lockstep with the battle pass season itself: the profile's SeasonPeriod/SeasonProgress/SeasonClaimed fields follow the exact same ensureCurrent rollover/auto-grant-sweep pattern as Daily/Weekly. The shipped pool (SeasonJunk, SeasonKills, SeasonDistance) pays Coins = 0, Exp = 0 and a large BPExp (3000 each) — Season quests exist purely to move the battle pass track, not the coin/XP economy.

Any quest, of any scope, can additionally carry an optional Reward.BPExp: number? — daily/weekly quests in the shipped pool pay smaller BPExp amounts alongside their normal coins/exp, so ordinary questing keeps the pass moving too, not just the Season set.

Attribution​

Two entry points on QuestManager, mirroring XPManager.AddXP / AddPartyXP:

  • QuestManager.ReportProgress(actor, metricKey, amount) — an actor-driven metric (junk collection). Bumps the actor's own Lifetime metric total, advances the actor's Personal quests for that metric, and fans the same amount out to every online player's Party quests for that metric (a Personal action still counts toward the team's Party objectives).
  • QuestManager.ReportPartyProgress(metricKey, amount) — an ownerless world metric (enemy died, train distance ticked). No single actor, so only Party quests advance, but every online player's own Lifetime metric total is bumped and every player is individually replicated.

Either path calls ensureCurrent first (rolls any elapsed period before applying progress) and only replicates (QuestStateSync) to players whose progress actually changed.

Claim + auto-grant sweep​

  • Manual claim — Packets.ReqClaimQuest(questId) invokes QuestManager.ClaimQuest(player, questId), which validates (profile loaded → quest exists → quest is in the currently active set for its scope → progress ≥ target → not already claimed) and returns (ok, reasonCode, coinsGranted, expGranted). The claimed flag is set before the reward is granted, so a re-entrant/duplicate call cannot double-pay — the second call fails fast with ALREADY_CLAIMED.
  • Auto-grant sweep — ensureCurrent (called on join, before every progress report/claim, and on the periodic rollover tick) detects when a scope's stored period index differs from the current index. Before resetting that scope's Progress/Claimed maps to the new period, it walks the old set (QuestState.selectQuests(scope, oldPeriodIndex)) and grants the reward for any quest that was completed but never claimed. Nothing is lost — a player who finishes a quest right before rotation and never opens the claim UI is still paid.
  • Both paths share one grantReward function, which — after paying coins/exp — fires Signals.OnQuestRewardGranted(player, quest.Reward). This is how the Battle Pass accrues EXP: BattlePassManager connects to this signal and reads reward.BPExp off the payload, so it sees every grant regardless of whether it came from a manual claim or an auto-grant sweep.

Sources​

QuestSourcesLoader.server.luau (gameplay-only — safe to run in the lobby place, where these events simply never fire) wires the three QuestConfig.Metrics to their gameplay triggers:

MetricCategoryTrigger
EnemyKillsPartyHumanoid.Died on any CollectionService-tagged QuestConfig.ENEMY_TAG ("EnemyNPC") model — one Janitor per tracked enemy.
DistanceTravelledPartyA recurring task.wait(QuestConfig.DISTANCE_TICK_SECONDS) loop credits QuestConfig.DISTANCE_PER_TICK while Signals.SetTrainState reports the train running.
JunkCollectedPersonalSignals.OnJunkCollected — fired by JunkService once per successful finalized junk grab (collector, junkId).

Adding a quest that reuses one of these Metric keys needs no source code change — only a new entry in QuestConfig.Quests. Wiring a brand-new metric needs one new source hookup in QuestSourcesLoader (see Tune Quests).

Perk seam​

profile.Data.Lifetime is a { [key]: number } table that is never reset by rollover — distinct from the per-period Progress maps. advancePlayer bumps Lifetime["QuestsCompleted"] by 1 on every below-target → at-target transition, and both ReportProgress/ReportPartyProgress bump Lifetime["metric:" .. metricKey] by the raw reported amount. QuestManager.GetLifetimeStat(player, key) reads it (0 if absent). This is a deliberate seam for a future PerkConfig unlock criterion (e.g. "unlock this perk after QuestsCompleted >= 25) — not wired to any perk this cycle.

Client​

QuestClient.luau is a GUI-agnostic read-model, same shape as PerkClient: it caches the authoritative QuestStateSync snapshot, recomputes the active set client-side with the same QuestState.selectQuests the server uses (so client and server never disagree on which quests are active), and exposes QuestView descriptors (Id, Scope, Category, DisplayName, Description, Icon, Metric, Target, Progress, IsComplete, IsClaimed, IsClaimable, RewardCoins, RewardExp, ExpiresAt) via GetQuests/GetActiveQuests/GetCompletedQuests/GetQuest, plus GetLifetimeStat and a Claim(questId) fire-and-forget command. A Changed signal fires on every snapshot update for consumers to repaint. No GUI ships this cycle — a future screen requires QuestClient and subscribes to Changed, exactly like PerkClient.

Data flow​

sequenceDiagram
    participant Source as QuestSourcesLoader
    participant Manager as QuestManager (server)
    participant Client as QuestClient (owning client)

    Note over Source,Manager: REPORT
    Source->>Manager: ReportProgress(actor, metric, amt) / ReportPartyProgress(metric, amt)
    Manager->>Manager: ensureCurrent() — roll elapsed periods first
    Manager->>Manager: advancePlayer() bumps Progress[questId] (clamped to Target)
    alt progress changed
        Manager->>Client: QuestStateSync(periods, expiry, progress, claimed, lifetime)
    end

    Note over Manager: COMPLETE (progress[questId] >= Target)
    Manager->>Manager: bumpLifetime("QuestsCompleted", 1) on the below→at-target transition
    Client->>Client: QuestView.IsClaimable becomes true (IsComplete and not IsClaimed)

    Note over Client,Manager: CLAIM
    Client->>Manager: ReqClaimQuest(questId)
    Manager->>Manager: validate (active set, progress >= Target, not claimed)
    Manager->>Manager: claimed[questId] = true (BEFORE grant — idempotent guard)
    Manager->>Manager: CoinManager.AddCoins(.., "Quest:"..questId); XPManager.AddXP(..); Signals.OnQuestRewardGranted:Fire(player, reward)
    Manager-->>Client: (ok, reasonCode, coinsGranted, expGranted)
    Manager->>Client: QuestStateSync (reconciled snapshot)

Client / Server / Shared​

Shared — QuestConfig.luau is the single tuning surface: STORE_NAME, period offsets, rollover/tick cadence, the Metrics key registry, Counts per scope/category, and the Quests pool (Scope — "Daily" | "Weekly" | "Season", Category, Metric, Target, DisplayName, Description, optional Icon, Reward { Coins, Exp, BPExp? }).

Shared — QuestState.luau is pure, side-effect-free: dayIndex/weekIndex/dailyExpiresAt/weeklyExpiresAt (period math) and selectQuests (deterministic global rotation), plus isComplete/isClaimable helpers. Both server and client require it directly so they never disagree.

Shared — QuestResultCodes.luau is the frozen result-code enum returned by ClaimQuest (OK=0, NO_PROFILE=1, UNKNOWN_QUEST=2, NOT_ACTIVE=3, NOT_COMPLETE=4, ALREADY_CLAIMED=5).

Server — QuestManager.luau owns the PlayerQuests ProfileStore profile (one session per player, key = UserId), place-agnostic like PerkManager (runs in both lobby and gameplay places so the lobby can display quests and pay out claims). Exposes ReportProgress, ReportPartyProgress, ClaimQuest, GetLifetimeStat, and Initialize (wires the profile lifecycle, the ReqClaimQuest handler, and the ROLLOVER_CHECK_SECONDS live-rollover tick). Registers a flush callback with PersistenceRegistry for BindToClose safety.

Server — QuestSystemLoader.server.luau calls QuestManager.Initialize() once per server (place-agnostic).

Server — QuestSourcesLoader.server.luau is gameplay-only: wires EnemyKills, DistanceTravelled, and JunkCollected into QuestManager.ReportProgress/ReportPartyProgress (see Sources). Does not call Initialize.

Client — QuestClient.luau is the GUI-agnostic data layer (see Client above).

Gotchas​

Changing STORE_NAME orphans saved quest data

QuestConfig.STORE_NAME ("PlayerQuests") is the ProfileStore key for progress, claimed flags, and the never-reset Lifetime table. Changing it points every player at a brand-new, empty profile — all prior quest progress and lifetime stats are orphaned (not deleted, just unreachable). It must stay identical in the lobby and gameplay places for the cross-place session handoff to share the same record.

Personal progress from ReportProgress also advances Party quests

ReportProgress(actor, metricKey, amount) is not Personal-only — it fans the same amount out to every online player's Party quests for that metric, then additionally advances the actor's Personal quests. A quest author reusing a Personal-sourced metric (JunkCollected) for a new Party quest gets it "for free" — no new source wiring needed.

The active set query needs the correct period index

QuestState.selectQuests takes a periodIndex, not a timestamp. Always derive it via QuestState.dayIndex/weekIndex(os.time()) (server) or read it from the cached QuestStateSync snapshot (client, via QuestClient) — never hardcode or guess an index.
