Train Fuel

A single global fuel value (0–100) governs the train's state for all players. The server computes fuel algebraically from the last event rather than polling each frame; every state transition snapshots the current fuel, switches the drain rate, and schedules the next deterministic transition via a nonce-guarded task.delay. Clients receive a snapshot and predict the bar locally.

Data flow​

Server (TrainFuelManager)                       Client (TrainClient / TrainFuelGuiController)
─────────────────────────────────────────────────────────────────────────────────────────────
Initialize():
  fuelAtLastEvent = INITIAL_FUEL (80)
  isBraked = INITIAL_BRAKED (true)        ──── TrainStateSync:Fire(fuel, rate,
  hasStarted = false                             isBraked, isStalled, serverTime) ──►
  currentRate = 0 (frozen until un-brake)
  reschedule()  ← no task.delay while frozen
                                                  Signals.OnTrainStateChanged:Fire(...)
                                                  snap = { fuel, rate, isBraked,
                                                           isStalled, serverTime }

PlayerAdded:
  ──── TrainStateSync:FireClient(player, ...) ──────────────────────────────────►

── BRAKE TOGGLE ──────────────────────────────────────────────────────────────────
Player triggers lever ProxPromptPart prompt
  ──── ReqToggleBrake(lever) ──────────►  validate: lever tag, proximity
                                           isBraked = !isBraked
                                           if first un-brake: hasStarted = true
                                             Signals.SetTrainStarted:Fire(true)
                                           commitEvent()
                                             snapshot fuel
                                             currentRate = rateForState()
                                             scheduleNonce++
                                             reschedule() → task.delay(timeToEmpty)
                                             TrainStateSync:Fire(...)
                                             Signals.SetTrainState:Fire(running)
  ◄── (success, isBraked, code) ────────
  update lever ActionText ("Stop Train" / "Resume Train")

── REFUEL ────────────────────────────────────────────────────────────────────────
Player triggers engine ProxPromptPart prompt
  ──── ReqRefuelTrain(engine) ─────────►  validate: engine tag, proximity, not full
                                           gather Energy tools, sort smallest first
                                           consume tools until MAX_FUEL
                                           if stalled & fuel > 0: clear stall
                                           commitEvent(newFuel)
  ◄── (success, fuelAdded, code) ────────

── STALL / GAME OVER (natural) ─────────────────────────────────────────────────────
task.delay(timeToEmpty) fires → onStall()
  isStalled = true
  commitEvent(0)  ← exact 0, no float drift
  reschedule() → task.delay(GAME_OVER_DELAY)
                                            bar color = STALLED_COLOR

task.delay(GAME_OVER_DELAY) fires → onGameOver()
  TrainGameOver.Trigger(TrainGameOverReason.FUEL_DEPLETED)   ← reason 1
  Signals.OnTrainGameOver:Fire(1)

── COMBAT FUEL-KILL (immediate, no grace) ──────────────────────────────────────────
TrainShieldManager.ApplyDamage(amount) while currentShield == 0:
  ApplyFuelDamage(amount * TrainConfig.FUEL_DAMAGE_FACTOR, source)
    guard: hasStarted, not HasFired(), amount > 0
    newFuel = max(0, getFuel() - amount)
    if newFuel > 0:
      commitEvent(newFuel)            ← just lowers fuel, natural stall timer shortens
    else:
      isStalled = true; gameOverFired = true   ← suppress the natural grace timer
      commitEvent(0)
      TrainGameOver.Trigger(TrainGameOverReason.FUEL_DESTROYED_BY_ATTACK)  ← reason 2, immediate
      Signals.OnTrainGameOver:Fire(2)

── CLIENT HUD LOOP ───────────────────────────────────────────────────────────────
RunService.RenderStepped:
  predicted = snap.fuel - snap.rate * (serverTime_now - snap.serverTime)
  displayedFuel ≈ predicted (exponential smoothing, k=8)
  bar.Size = UDim2.new(pct, 0, 1, 0)
  bar color: green (running) / amber (braked) / red (stalled)

Client / Server / Shared​

Client — TrainClient.client.luau Registers engine (TrainEngine-tagged) and lever (TrainBrakeLever-tagged) models via CollectionService. On engine Triggered it calls ReqRefuelTrain; surfaced error codes NO_ENERGY and FUEL_FULL fire Signals.RequestNotification toasts (warn / info respectively). On lever Triggered it calls ReqToggleBrake fire-and-forget — brake state replicates back via TrainStateSync. On PromptButtonHoldBegan it checks whether the player holds an Energy tool and shows a warning toast if not. Receives TrainStateSync and bridges it to Signals.OnTrainStateChanged.

Client — TrainFuelGuiController.client.luau Reads the authored StarterGui.TrainFuelGui (never creates UI). Subscribes to Signals.OnTrainStateChanged to update snap. On every RenderStepped it computes predictedFuel from snap.fuel - snap.rate * elapsed and smooths displayedFuel toward it with frame-rate-independent exponential smoothing (k = 8). Sets FuelBar.Size and FuelText.Text, and colors the bar green/amber/red based on snap.isBraked / snap.isStalled.

Server — TrainFuelManager.luau Initialize() is called by TrainFuelSystemLoader.server.luau. All fuel arithmetic is algebraic: getFuel() = fuelAtLastEvent - currentRate * elapsed. commitEvent snapshots fuel under the old rate before switching, so the transition is seamless. A scheduleNonce guards task.delay callbacks — any subsequent commitEvent increments the nonce, and stale callbacks no-op when their captured nonce no longer matches. isRefueling is a boolean mutex that serializes concurrent refuel requests so two simultaneous players cannot both read the same pre-commit snapshot. On SetTrainState, JunkService is notified to adjust floating junk speed. ApplyFuelDamage(amount, source?) is the combat fuel-damage sink called by TrainShieldManager once the shield is down — see Game-over reasons below.

Server — TrainGameOver.luau (shared with shield) HasFired(), Trigger(reason: number?), GetReason(), Reset() — idempotent game-over gate. Trigger stores the TrainGameOverReason code (default NONE if omitted) and fires Signals.OnTrainGameOver(reasonCode) exactly once; subsequent calls are no-ops. Reset clears the fired flag and stored reason for a future round restart (not yet wired).

Shared — TrainGameOverReason.luau Frozen numeric enum identifying how a round ended: NONE = 0, FUEL_DEPLETED = 1 (natural fuel-out), FUEL_DESTROYED_BY_ATTACK = 2 (combat fuel-kill). Lives in ReplicatedStorage/SharedModules so both client and server can read it.

Shared — TrainConfig.luau Single config table for fuel rates, tier recharge values, collision tags, and prompt names. Both client and server require it.

Game-over reasons​

There are exactly two ways a round ends, both funneled through the shared TrainGameOver.Trigger(reason) so the game-over sequence fires exactly once regardless of which path gets there first:

ReasonCodeTrigger pathGrace?
FUEL_DEPLETED1Natural fuel-out. Fuel algebraically reaches 0 → onStall() marks the train stalled and broadcasts the 0 → after TrainConfig.GAME_OVER_DELAY (180s) elapses with no refuel, onGameOver() calls TrainGameOver.Trigger(TrainGameOverReason.FUEL_DEPLETED).Yes — GAME_OVER_DELAY seconds to refuel before it's final.
FUEL_DESTROYED_BY_ATTACK2Combat fuel-kill. TrainShieldManager.ApplyDamage routes hits to TrainFuelManager.ApplyFuelDamage once the shield is at 0; if that hit drives fuel to exactly 0, TrainGameOver.Trigger(TrainGameOverReason.FUEL_DESTROYED_BY_ATTACK) fires immediately.No — immediate, no GAME_OVER_DELAY.

TrainGameOverReason is a frozen enum module (ReplicatedStorage/SharedModules/TrainGameOverReason.luau). TrainGameOver.Trigger(reason: number?) records the reason (GetReason() returns it) and fires Signals.OnTrainGameOver(reasonCode) — a Signal.Signal<number> — exactly once per round; the events system is the intended consumer. Both code paths still only log and fire the signal — the real game-over mechanic (round reset / respawn / UI) remains out of scope and is a placeholder, same as before.

ApplyFuelDamage​

TrainFuelManager.ApplyFuelDamage(amount: number, source: any?) is the combat fuel-damage sink. amount is fuel units already converted by TrainConfig.FUEL_DAMAGE_FACTOR — callers (currently only TrainShieldManager.ApplyDamage, once the shield is at 0) multiply the raw attack damage by the factor before calling.

Guards (all must pass or the call is a no-op):

  • hasStarted must be true (pre-game freeze, same as ApplyDamage)
  • TrainGameOver.HasFired() must be false
  • amount must be > 0 and not NaN

If the hit leaves fuel above 0, it just commits the new (lower) level — the natural stall timer simply shortens, no special-casing needed. If the hit drives fuel to exactly 0, it's an immediate game over: isStalled and gameOverFired are set before commitEvent(0) so reschedule() arms no grace timer and rateForState() returns 0, then TrainGameOver.Trigger(TrainGameOverReason.FUEL_DESTROYED_BY_ATTACK) fires with no GAME_OVER_DELAY wait.

Key files​

  • src/ServerStorage/SharedModules/TrainFuelManager.luau — authoritative fuel state, algebraic model, all state transitions, ReqRefuelTrain / ReqToggleBrake handlers, ApplyFuelDamage combat sink
  • src/StarterPlayer/StarterPlayerScripts/TrainClient.client.luau — prompt registration, refuel/brake requests, error notifications, TrainStateSync → OnTrainStateChanged bridge
  • src/StarterPlayer/StarterPlayerScripts/TrainFuelGuiController.client.luau — client-side fuel prediction, exponential smoothing, HUD bar + color updates
  • src/ServerStorage/SharedModules/TrainGameOver.luau — idempotent game-over gate, shared with shield (Trigger/GetReason/Reset)
  • src/ReplicatedStorage/SharedModules/TrainGameOverReason.luau — frozen enum (NONE/FUEL_DEPLETED/FUEL_DESTROYED_BY_ATTACK)
  • src/ReplicatedStorage/SharedModules/Configs/TrainConfig.luau — fuel constants, drain rates, tier recharge table, Studio tag names, FUEL_DAMAGE_FACTOR

Gotchas​

Frozen-start phase

While hasStarted = false (before the first brake release), the drain rate is forced to 0 and no task.delay stall timer is scheduled. Any code path that reads currentRate or calls getFuel() before the first un-brake will see a frozen value — this is intentional. Do not bypass the hasStarted gate.

Game-over is a placeholder

Both onGameOver() (natural) and the immediate combat-kill path in ApplyFuelDamage funnel through TrainGameOver.Trigger, which only logs and fires Signals.OnTrainGameOver. No round reset, respawn, or UI is triggered. Do not ship this system without replacing the placeholder with a real mechanic.

Combat fuel-kill skips the grace delay

Unlike natural stall-out, a fuel-zeroing hit via ApplyFuelDamage ends the round immediately — GAME_OVER_DELAY is not consulted on that path. There is no window for the player to refuel after the killing blow. See Game-over reasons.

Algebraic drift note: commitEvent captures now() once and uses it for both lastEventTime and the serverTime field broadcast in TrainStateSync. If you add any task.wait or async work between the snapshot and the broadcast, the client's extrapolation baseline will drift. Keep commitEvent synchronous.

Nonce guard: every commitEvent increments scheduleNonce. Stall and game-over task.delay callbacks capture the nonce at schedule time and return early if it has changed. Do not call reschedule directly — always go through commitEvent.

Refuel mutex (isRefueling): the mutex is a simple boolean, not a queue. A second refuel request while one is in-flight returns NO_ENERGY even if the player has tools. This is intentional to avoid double-spending; the player can try again immediately after.

Studio model requirements: the TrainEngine-tagged and TrainBrakeLever-tagged roots (each a Model or BasePart) must contain a BasePart named "ProxPromptPart" with a child ProximityPrompt. The prompt's MaxActivationDistance and the engine's ActionText are authored in Studio; only the lever's ActionText is set by script. Both client and server resolve the prompt part recursively via ReplicatedStorage/SharedModules/PromptResolver, so it may be nested at any depth, not only as a direct child. The part's Studio name must match TrainConfig.PROMPT_PART_NAME.
