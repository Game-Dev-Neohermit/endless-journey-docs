Enemy Spawner

A generic, server-authoritative combatant spawner for the pirate-encounter and outpost gameplay loops. Given a named spawn group and a wave request, EnemySpawner selects attachment-authored spawn points with cumulative-inverse weighting, jitters each position within a configurable disc, validates the candidate through SpawnVerification (ground snap, wall/headroom clearance, enemy spacing), clones the archetype Model from ServerStorage.EnemyAssets, and returns a WaveHandle that fires OnCleared once the last enemy dies. The server is the sole authority; spawned Models replicate to clients natively via Roblox replication — no packets are required. The spawner owns only the act of spawning: it does not own when spawning happens, does not implement AI or pathfinding, does not manage the cutscene or boarding state machine, and does not model outpost-stop trigger detection. Orchestrators call SpawnWave and react to WaveHandle.OnCleared.

Authoring contract​

EnemySpawnGroup​

A spawn group is a Model in the DataModel tagged with the CollectionService tag EnemySpawnGroup. The group's identity is its GroupName string attribute; if the attribute is absent the model's .Name is used. The tag is all that is required — any Model (a pirate ship, an outpost building, a plain Part wrapped in a Model) becomes a valid group.

Because spawn-point attachments are descendants of the group Model, their .WorldPosition moves automatically with the model's CFrame. Placing the group on a moving ship and then calling SpawnWave will place enemies relative to the ship's current pose at spawn time, with no code changes.

EnemySpawnPoint​

Each spawn point is an Attachment tagged EnemySpawnPoint, parented anywhere beneath the group model. Two optional per-point attributes control selection and jitter:

AttributeTypeDefaultPurpose
Radiusnumberarchetype DefaultRadius → DEFAULT_POINT_RADIUSRadial jitter disc radius in studs
Weightnumber1Base selection weight before the cumulative-inverse falloff

Points are visually editable in Studio — add, remove, or move an attachment and the spawner picks it up immediately (the cache is rebuilt on first use per group, and a CollectionService.GetInstanceRemovedSignal listener invalidates the group if the root model is untagged or removed).

EnemyAssets folder​

Enemy Model assets live in ServerStorage/EnemyAssets/. Each child Model must have:

  • A Humanoid (authoritative stats are applied at spawn time from the archetype config, but the Humanoid must exist for health/death tracking)
  • A PrimaryPart or HumanoidRootPart (used for pivot placement and SpawnVerification spacing tests)

At module load, EnemySpawnerConfig validates every archetype's Model name against EnemyAssets children and emits a warn for any missing model. Building before art is ready is fully supported: register a placeholder dummy (any Model with a Humanoid) in EnemyAssets under the expected name.

Public API​

EnemySpawner is a server-only module (ServerStorage/SharedModules/EnemySpawner.luau). Call EnemySpawner.Init() once from the system loader before using the rest of the API.

EnemySpawner.Init()

Called once by EnemySpawnerSystemLoader.server.luau at server start. Creates workspace.ActiveEnemies if absent and wires the group-cache invalidation listener.

EnemySpawner.SpawnWave(groupName: string, request: SpawnRequest): WaveHandle

Spawns request.count enemies across the named group's points using the selection algorithm below. composition is either a single archetype name ("PirateGrunt") or a weighted table ({ PirateGrunt = 3, PirateBrute = 1 }) — the weight table is rolled per enemy. If request.interval > 0, spawns are staggered in a task.spawn loop (drip-feed); the WaveHandle is returned immediately and OnCleared waits for both all spawns to be attempted and all registered enemies to die. If request.seed is set, the internal Random is re-seeded for deterministic reproduction.

export type SpawnRequest = {
    count: number,
    composition: string | { [string]: number },
    interval: number?,   -- seconds between spawns; nil/0 = all at once
    seed: number?,       -- optional deterministic RNG seed
}
EnemySpawner.SpawnAt(groupName: string, pointName: string, archetypeName: string): Model?

Direct escape hatch: place exactly one archetype at the named attachment (matched by Attachment.Name), still subject to verification. Returns the placed Model or nil if verification fails after MaxRetries or the point/archetype is not found.

EnemySpawner.ResetGroup(groupName: string)

Clears the group's cumulative per-point spawn counts. Call this at the start of each new encounter so point weighting begins fresh. Deaths do not reduce a point's count; only ResetGroup does.

Per-enemy spawn algorithm​

For each enemy in a wave the spawner runs:

  1. Select a point — weighted random over the group's EnemySpawnPoint attachments. Effective weight is point.Weight / (cumulativeCount + 1) ^ WeightFalloff, where cumulativeCount is the number of enemies spawned from that point this encounter. Points that have spawned fewer enemies this encounter are proportionally more likely; a point with count 0 carries its full base weight. Counts are per-encounter — ResetGroup resets them; enemy deaths do not.

  2. Jitter — candidate position = point world position + a uniform random offset within a disc of the point's Radius on the XZ plane. The disc uses sqrt(NextNumber()) * radius so the distribution is uniform over the area rather than biased toward the centre.

  3. Verify — the candidate is passed to SpawnVerification with the archetype's body size, an ignore list containing the group model and the ActiveEnemies folder, and the current list of living enemies.

  4. Retry-then-skip — steps 2–3 repeat up to Verification.MaxRetries times. If no valid position is found, the enemy is skipped (a warn is emitted) and the wave continues. The wave never hard-fails; it never places a broken enemy.

  5. Place — if the global cap (GLOBAL_MAX_ENEMIES) is already met, the enemy is skipped with a warn. Otherwise the archetype Model is cloned from ServerStorage.EnemyAssets, archetype stats are applied (Humanoid.MaxHealth/Health/WalkSpeed), the model is tagged EnemyNPC (or FriendlyNPC if archetype.Faction == "Friendly") so Factions resolves it for CombatService and NpcCollisionService, the model is pivoted to the verified ground-snapped CFrame, parented to workspace.ActiveEnemies, and the point's cumulative count is incremented. The spawned model is registered with the wave handle, and Signals.OnEnemySpawned fires with the placed position and archetype name.

SpawnVerification​

SpawnVerification (ReplicatedStorage/SharedModules/SpawnVerification.luau) is a stateless pure-geometry validator with no server-only dependencies. It lives in SharedModules so it is independently testable and reusable from a future client-side preview. All v1 callers are server-side.

SpawnVerification.Verify(
    candidate: Vector3,
    bodySize: Vector3,
    ignoreList: { Instance },
    livingEnemies: { Model }
): VerifyResult   -- { ok: boolean, position: Vector3?, reason: string? }

Checks are run cheapest-first with short-circuit on failure:

  1. Ground below — workspace:Raycast straight down from candidate + (0, 2, 0) up to MaxGroundDrop studs, excluding ignoreList. No hit returns { ok = false, reason = "void" }. On hit, the Y position is snapped to the floor: snapped.Y = hit.Position.Y + bodySize.Y / 2.

  2. Clear of walls / headroom — workspace:GetPartBoundsInBox of HeadroomSize centred on the snapped position, excluding ignoreList. Any solid collidable part returns { ok = false, reason = "blocked" }. This catches both embedded-in-wall and under-floor cases.

  3. Spacing — if any model in livingEnemies has its pivot within MinEnemySpacing studs of the snapped position, returns { ok = false, reason = "crowded" }.

A successful check returns { ok = true, position = snapped } where position is the ground-snapped placement CFrame origin.

WaveHandle lifecycle​

SpawnWave returns a WaveHandle backed by a Janitor. The handle tracks every spawned enemy's death and removal.

export type WaveHandle = {
    OnCleared: Signal<()>,         -- fires once: all enemies dead AND wave complete
    GetAlive: (self) -> number,    -- count of enemies still alive
    GetEnemies: (self) -> { Model }, -- list of enemies still alive
    Despawn: (self) -> (),         -- destroy remaining enemies + remove from tracking
    Destroy: (self) -> (),         -- Despawn + Janitor teardown
}

Each spawned enemy's Humanoid.Died and AncestryChanged (for despawn-without-death) are connected via the handle's Janitor. OnCleared fires once when the alive count reaches zero and the wave has been marked complete (all drip-feed spawns attempted). Killing enemies before the last drip-feed slot fires will not trigger OnCleared prematurely.

Typical orchestrator pattern:

local wave = EnemySpawner.SpawnWave("PirateShip", {
    count = 6,
    composition = { PirateGrunt = 3, PirateBrute = 1 },
    interval = 0.5,
})
wave.OnCleared:Connect(function()
    resumeEncounter()
end)

Despawn lets an orchestrator abort a wave early (encounter cancelled, train resumes) and cleanly destroy remaining enemies. Calling Despawn when all enemies are already dead is safe (no-op). Destroy implies Despawn and additionally tears down the Janitor, disconnecting all event connections.

Config knobs​

All tuning lives in src/ReplicatedStorage/SharedModules/Configs/EnemySpawnerConfig.luau. The module is accessible from both client and server; the archetype validation block is guarded by RunService:IsServer() since ServerStorage is inaccessible on the client.

FieldDefaultEffect
GLOBAL_MAX_ENEMIES40Hard cap on total active enemies across all groups. Exceeding the cap skips spawns with a warn. Lower temporarily to verify the cap in Studio.
DEFAULT_POINT_RADIUS6Fallback jitter disc radius (studs) when neither the point Radius attribute nor the archetype DefaultRadius is set.
WeightFalloff1.0Exponent k in effectiveWeight = baseWeight / (count + 1) ^ k. At 1.0 weight halves each time a point is used. Raise to flatten selection (less adaptive); lower toward 0 to disable cumulative penalisation.
Verification.MaxGroundDrop25Maximum downward raycast distance (studs) to find a floor below the candidate. Candidates with no solid ground within this distance are rejected as "void".
Verification.HeadroomSizeVector3.new(3, 6, 3)Box dimensions used for the wall/headroom overlap check centred on the snapped candidate. Should match or slightly exceed the tallest enemy body.
Verification.MinEnemySpacing4Minimum distance (studs) between a new candidate and any already-living enemy pivot. Candidates closer than this are rejected as "crowded".
Verification.MaxRetries8Number of jitter re-rolls before an enemy is skipped with a warn. Higher values increase spawn success at the cost of time per enemy.
Archetypes(see below)Per-archetype table: Model (child name in EnemyAssets), Health, WalkSpeed, DefaultRadius, optional Faction ("Enemy" / "Friendly"; defaults to "Enemy").

Archetype example​

EnemySpawnerConfig.Archetypes = {
    PirateGrunt = { Model = "PirateGrunt", Health = 100, WalkSpeed = 14, DefaultRadius = 6 },
    PirateBrute = { Model = "PirateBrute", Health = 300, WalkSpeed = 10, DefaultRadius = 4 },
}

Adding a new archetype: add an entry here, create the corresponding Model in ServerStorage/EnemyAssets/, and the spawner picks it up at next load. No code changes elsewhere are needed.

Studio setup​

EnemySpawnGroup model​

  1. Select any Model in the workspace (pirate ship, outpost, or a plain wrapped Part).
  2. Tag it EnemySpawnGroup via the Studio Tag Editor (or CollectionService:AddTag).
  3. Optionally set a GroupName string attribute on the model root. If absent, model.Name is used.

EnemySpawnPoint attachments​

Under the group model, insert one or more Attachment instances:

  1. Insert an Attachment anywhere in the model hierarchy (directly on a Part, inside a nested model, etc.).
  2. Tag it EnemySpawnPoint.
  3. Optionally add a Radius (number) attribute for this point's jitter disc.
  4. Optionally add a Weight (number) attribute to bias selection toward or away from this point.

The attachment's position in Studio is the spawn point's world-space origin at runtime. Move attachments freely; the spawner reads .WorldPosition live at spawn time.

EnemyAssets folder​

In Studio, create a folder named EnemyAssets inside ServerStorage. Under it, place enemy Models. Each model must have a Humanoid and a PrimaryPart (or HumanoidRootPart). The name of the model must match the Model field in the corresponding archetype entry in EnemySpawnerConfig.Archetypes.

Minimum viable setup for testing before art is ready:

  • Insert a default Roblox Dummy (rig_type = R15 or R6) into ServerStorage/EnemyAssets/.
  • Rename it to PirateGrunt.
  • The archetype validation at load will stop warning; SpawnWave will clone the dummy.

Collision and combat wiring​

No additional Studio wiring is required for collision passthrough or combat. Spawned enemies are tagged EnemyNPC (or FriendlyNPC), and:

  • NpcCollisionService adds them to the Character collision group so players pass through them.
  • CombatService.ApplyToModel resolves them via Factions so weapon hits deal damage.

Both services detect the tags automatically on CollectionService.GetInstanceAddedSignal.

Gotchas​

WaveHandle OnCleared requires both conditions

OnCleared fires only when the alive count is zero AND all drip-feed spawns have been attempted (MarkComplete has been called internally). In an instant wave (interval = 0) this means OnCleared can fire during SpawnWave itself, before it returns, if no enemies are placed (e.g. every enemy was skipped). Always set up OnCleared connections before calling SpawnWave, or use the returned handle and do not assume it is deferred.

Cumulative counts survive across waves; ResetGroup does not

EnemySpawner.ResetGroup(groupName) resets the per-point counts for the named group so point selection begins fresh. If you call SpawnWave a second time without resetting, previously-used points start at a cumulative disadvantage. For repeating encounter patterns (waves 1, 2, 3…), decide explicitly whether to reset between waves or let cumulative weighting carry across the full encounter.

GLOBAL_MAX_ENEMIES counts workspace.ActiveEnemies children

The cap is the live child count of workspace.ActiveEnemies. If enemies are not parented there (e.g. manually cloned models outside the spawner), they do not count toward the cap, which may allow over-cap situations. Always spawn enemies through EnemySpawner; do not manually parent enemy models into ActiveEnemies.

SpawnVerification is in SharedModules but is server-only in v1

SpawnVerification is in ReplicatedStorage/SharedModules/ so it has no server-only dependencies and can be used from a future client-side preview (e.g. displaying valid spawn zones in a director tool). In v1, all calls happen server-side via EnemySpawner. Do not call it on the client in production without auditing the ignoreList and livingEnemies arguments for client-visible data.

Archetype validation warns but does not error

If a model is missing from EnemyAssets at load time, EnemySpawnerConfig emits a warn but does not error. The spawner itself will also warn (and skip the enemy) at spawn time if the model is still absent. Register placeholder models early to keep the Output clean during development.

Future directions​

  • Off-screen spawn preference — an additional weighting term in step 1 of the selection algorithm that demotes EnemySpawnPoints currently inside any player's camera frustum. Enemies would appear from behind cover or at the edge of vision. The term slots into the effective-weight formula without changing the rest of the algorithm.
  • Reachability pre-check — PathfindingService:CreatePath from the verified candidate position to the nearest player, rejecting candidates in sealed-off areas. This is the deferred line-of-sight check in SpawnVerification, done properly. Build alongside the enemy pathfinding AI system.
  • Encounter director — a layer above the spawner that scales count/composition/interval by wave number, player count, or Tech Tree progress. The spawner stays a dumb placement service; the director owns escalation and pacing. Lives as a separate module; EnemySpawner requires no changes.
