Tech Tree

A cooperative, server-wide, session-only (no DataStore) tech tree lets players pool crafted materials (Wood/Metal) into research nodes at one fixed bench. Eligibility is always-open: any node whose prerequisite is unlocked and which is not yet unlocked accepts submissions. A node auto-unlocks the instant its full cost is met. Because refunds go to a shared ground pile, there is no per-player contribution tracking — one shared pool per node.

Data flow​

Server (TechTreeService)                        Client (TechTreeGuiController)
──────────────────────────────────────────────────────────────────────────────

── JOIN / SNAPSHOT ──────────────────────────────────────────────────────────
GUI opens or client initialises
  ──── ReqTechSnapshot() ──────────────►  return { unlocked, pools }
  ◄── { unlocked, pools } ──────────────
  cache.unlocked / cache.pools updated
  all rows refreshed

── SUBMIT ───────────────────────────────────────────────────────────────────
GUI stepper: chosen[matType] up/down
  max = min(held, TechTreeState.remaining)
  ──── ReqTechSubmit(nodeId, matType, amount) ──►
                                            validate proximity
                                              (INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE)
                                            TechTreeState.validateSubmit(state, nodeId, matType, amount)
                                            countMaterial(player, matType) >= amount
                                            consumeMaterial(player, matType, amount)
                                            pools[nodeId][matType] += amount
                                            if TechTreeState.isComplete(state, nodeId):
                                              unlocked[nodeId] = true
                                              Signals.OnNodeUnlocked:Fire(nodeId)
                                              TechNodeUpdate:Fire(nodeId, metalSubmitted, woodSubmitted, true)
                                            else:
                                              TechNodeUpdate:Fire(nodeId, metalSubmitted, woodSubmitted, false)
  ◄── (success, reasonCode) ──────────────
                                           ◄── TechNodeUpdate(nodeId, metalSubmitted, woodSubmitted, isUnlocked)
  cache updated; all rows refreshed
  Signals.OnTechTreeStateChanged:Fire()

── AUTO-UNLOCK EFFECT ────────────────────────────────────────────────────────
  Signals.OnNodeUnlocked:Fire(nodeId)
  ──► TechEffectsDispatcher:
        node.Effect.Type == "StatBuff"      →  applyStatBuff (accumulates on
          ReplicatedStorage/TechTreeBuffs attribute; fully wired)
        node.Effect.Type == "FuelEfficiency" →  applyFuelEfficiency (writes drain
          multiplier into TechTreeBuffs.FuelEfficiency; fully wired)
        node.Effect.Type == anything else
          →  warn + no-op (node authored ahead of wiring)
  Next tier becomes eligible because TechTreeState.isEligible now passes

── CANCEL ───────────────────────────────────────────────────────────────────
Player clicks Cancel button
  ──── ReqTechCancel(nodeId) ──────────►  validate proximity + pool not empty
                                            snapshot pool; zero pools[nodeId]
                                            TechNodeUpdate:Fire(nodeId, 0, 0, false)
                                            MaterialEjector.Eject(bench, snapshot, config)
                                              arc pieces to ProximityPickup floor pile
  ◄── (success, reasonCode) ──────────────
  cache updated; all rows refreshed

Client / Server / Shared​

Shared — TechTreeState.luau is a pure, stateless validator with no Roblox service calls — the single source of rules that both sides share. The client uses it to grey buttons and display accurate cost progress; the server uses it to authorise every request. Exported functions: newState, getNode, isUnlocked, isEligible, submitted, remaining, isComplete, and validateSubmit. validateSubmit checks node existence, unlock status, prereq, material membership, positive amount, and over-submission — it does not check whether the player physically holds the tools (that is a server-only concern layered on top). TechTreeResultCodes.luau is the companion frozen result-code enum; every packet response reason (e.g. TOO_FAR, EXCEEDS_REMAINING, ALREADY_UNLOCKED, NOTHING_TO_REFUND) is defined there and shared by both sides so string literals never appear in business logic.

Server — TechTreeService.server.luau is the sole owner of the authoritative unlocked / pools state. It handles ReqTechSubmit (proximity check → validateSubmit → tool count → consume → credit pool → auto-unlock on isComplete), ReqTechCancel (proximity check → snapshot and zero pool → eject), and ReqTechSnapshot (returns full { unlocked, pools } for late joiners). Broadcasts per-node deltas with TechNodeUpdate and fires Signals.OnNodeUnlocked on auto-unlock. Session-only: no DataStore.

Server — TechEffectsDispatcher.server.luau connects Signals.OnNodeUnlocked and dispatches on node.Effect.Type. The StatBuff handler is fully wired: it accumulates the numeric Effect.Amount onto the matching attribute of a shared ReplicatedStorage/TechTreeBuffs folder so other systems can read the running total. The FuelEfficiency handler is also fully wired: applyFuelEfficiency writes current * (1 / Multiplier) into TechTreeBuffs.FuelEfficiency, which TrainFuelManager reads as a drain multiplier. Any unknown effect type warns and no-ops, which lets future nodes be authored in config before their gameplay logic is written.

TechTreeService also publishes each unlocked node ID into a parallel ReplicatedStorage/TechTreeUnlocked folder (a BoolValue per unlocked node, named by nodeId). This folder is written by the server and read by the Workbench Crafting system for both server-side authorisation (gate check in WorkbenchService) and client-side greying (in WorkbenchGuiController). It is unforgeable from the client.

Server — MaterialEjector.luau is a general-purpose ejection mechanism with no knowledge of the tech tree. Its public API is MaterialEjector.Eject(bench, counts, config) where counts is a { [string]: number } material-to-quantity map and config carries all arc tuning constants. Internally it clones Tool Handle parts, animates each through a Catmull-Rom spline via MotionMaster.SplineMove from the bench TrajectoryPoints → SpawnPoint to a scattered position near LandingPoint, then registers each piece with ProximityPickupServer so players can collect them. Items beyond MAX_ANIMATED_EJECT_ITEMS are placed directly at the landing point without an animation. If TrajectoryPoints or its children are missing, the ejector degrades gracefully and drops pieces at the bench pivot instead of erroring.

Client — TechTreeGuiController.client.luau builds the TechTreeGui ScreenGui dynamically (one row per node, sorted by branch then tier). It opens via the bench TechPromptPart ProximityPrompt and closes via a header button. Steppers clamp chosen to min(held, TechTreeState.remaining) so the player can never queue more than they hold or more than is needed. The GUI repaints on TechNodeUpdate arrival by updating the local cache and calling refreshRow for all nodes — a node unlock can make its child eligible, so every row is checked. The Signals.OnTechTreeStateChanged signal is fired after each repaint for any other client code that needs to react. The server is always truth; the client never mutates cache directly except via received packets.

Studio setup​

One Model tagged TechTreeBench with its PrimaryPart set. It requires three children:

  1. A child Model named TrajectoryPoints (tagged PlacementIgnore) holding two BasePart children: SpawnPoint (the output mouth of the bench, arc start) and LandingPoint (the floor drop zone, arc end).
  2. A child BasePart named TechPromptPart holding a ProximityPrompt — triggers the GUI open/close. The prompt's MaxActivationDistance is set to TechTreeConfig.INTERACT_DISTANCE by the client controller at runtime.
  3. ReplicatedStorage/CraftingMaterials (not a bench child) must contain Wood and Metal Tool templates with IsCraftMaterial = true and ItemType attributes set. These are shared with the Shredder.

The Nodes table defines each researchable upgrade. Each node has Branch (string grouping), Tier (number, controls prereq chain), DisplayName, Description, Cost (material type → amount, e.g. { Metal = 25 }), Prereq (prior-tier node ID or nil at T1), and Effect ({ Type: string, ... }). The shipped example nodes are Durability_T1 ("Scrap Plating", StatBuff MaxHP +50, cost Metal 25) and Durability_T2 ("Iron Barricades", StatBuff MaxHP +150, cost Metal 100, prereq Durability_T1) — both fully wired through TechEffectsDispatcher. The MaxHP attribute name is kept as-is; its consumer is TrainShieldManager, which reads it as additive shield capacity: maxShield = (BASE_SHIELD + TechTreeBuffs.MaxHP) * (1 + TrainShieldBonus). See Train Shield. Fuel_T1 ("Combustion Engine", FuelEfficiency multiplier, cost Metal 80 + Wood 10) is now fully wired: TechEffectsDispatcher.applyFuelEfficiency writes a drain multiplier (current * (1 / Multiplier)) into TechTreeBuffs.FuelEfficiency, which TrainFuelManager reads on every drain tick.

Fuel-efficiency stacking rule: TrainFuelManager combines the Tech Tree multiplier with the Fuel Efficiency party perk multiplicatively:

effectiveRate = baseRate × max(0.1, TechTreeBuffs.FuelEfficiency × max(0.1, 1 − FuelEfficiencyBonus))

FUEL_DRAIN_FLOOR = 0.1 prevents the combined multiplier from ever reaching zero regardless of perk or node levels.

Gotchas​

Server re-checks proximity on every request

The client GUI proximity is never trusted. Both ReqTechSubmit and ReqTechCancel run isNearBench on the server using INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE. A player who submits via a modified client from too far away receives TOO_FAR.

Over-submission is rejected server-side

validateSubmit rejects any amount that would exceed the remaining cost for that material (EXCEEDS_REMAINING). The stepper max in the UI is purely a courtesy — the server enforces the ceiling authoritatively. Submitting exactly the remaining amount is the only legal final submission.

Validate-then-consume ordering

The server calls validateSubmit and countMaterial before touching the player's backpack. If either check fails, nothing is consumed. This means the player never loses tools to a rejected request.

Concurrent last-unit submit

Roblox RemoteFunction.OnServerInvoke callbacks run on the same thread (no Luau parallelism here), so two simultaneous last-unit submits are serialised. The second one arrives after the first has already set unlocked[id] = true, so validateSubmit returns ALREADY_UNLOCKED and consumes nothing.

Effect idempotency

The unlocked flag is set before OnNodeUnlocked fires, and unlockNode guards against double entry. This means OnNodeUnlocked fires exactly once per node per session — StatBuff cannot double-apply even if the signal had multiple listeners.

TechNodeUpdate packet shape is fixed to two materials

TechNodeUpdate carries metalSubmitted and woodSubmitted as positional fields. Adding a third craft material to any node's Cost requires widening this packet to an Any material-to-count map and updating both the server broadcast helper (poolCounts) and the client OnClientEvent handler.

Cancel with an empty pool is rejected; missing geometry degrades gracefully

ReqTechCancel on a node with no pool returns NOTHING_TO_REFUND and fires no arc. If the bench is missing its TrajectoryPoints model or either named part, MaterialEjector falls back to dropping pieces at the bench pivot position — it never errors the cancel.
