Train Shield

A single global shield pool governs the train's structural integrity for all players. Unlike fuel, the shield has no continuous drain — it is event-driven: damage events deplete it, and players restore it by feeding Energy tools into a ShieldConsole. Depleting the shield to 0 is no longer a game over — once the shield is down, further attacks bleed through to fuel (see ApplyDamage / fuel bleed-through below). The server is the sole authority; clients receive snapshots and update the diegetic shield monitor.

Data flow​

Server (TrainShieldManager)                     Client (TrainShieldController / TrainShieldGuiController)
────────────────────────────────────────────────────────────────────────────────────────────────────────

── INITIALIZE ───────────────────────────────────────────────────────────────────────────────────────
Initialize():
  maxShield = computeMax()                ──── TrainShieldSync:Fire(currentShield,
  currentShield = maxShield                     maxShield) ──────────────────────────►
  bind ReqRechargeShield.OnServerInvoke
  task.spawn(subscribeBuffs)                    Signals.OnTrainShieldChanged:Fire(...)
                                                TrainShieldGuiController:
                                                  shieldSnap updated (see below)

── PLAYER JOIN ──────────────────────────────────────────────────────────────────────────────────────
PlayerAdded:
  ──── TrainShieldSync:FireClient(player, currentShield, maxShield) ──────────────────►

── RECHARGE ─────────────────────────────────────────────────────────────────────────────────────────
Player triggers ShieldConsole ProxPromptPart prompt
  ──── ReqRechargeShield(console) ─────►  isRecharging mutex: serialize concurrent requests
                                           validate: console tag "ShieldConsole", proximity
                                           GatherEnergyTools(player): sort smallest first
                                           consume tools until currentShield == maxShield
                                           broadcast()
  ◄── (success, shieldAdded, code) ───────

── DAMAGE ───────────────────────────────────────────────────────────────────────────────────────────
future combat/hazard system calls:
  ApplyDamage(amount, source?)
    guard: hasStarted, not HasFired(), amount > 0
    if currentShield > 0:
      currentShield = max(0, currentShield - amount)   ← hit that zeroes it discards the excess
      broadcast()
    else:
      TrainFuelManager.ApplyFuelDamage(amount * TrainConfig.FUEL_DAMAGE_FACTOR, source)
      (may end the round — see Train Fuel: Combat fuel-kill)

── BUFF CHANGE ──────────────────────────────────────────────────────────────────────────────────────
TechTreeBuffs.MaxHP attribute changed  OR
PartyPerkBuffs.TrainShieldBonus changed
  → recomputeMax():
      ratio = currentShield / oldMax
      newMax = computeMax()
      currentShield = clamp(floor(ratio * newMax + 0.5), 0, newMax)
      broadcast()

── CLIENT HUD UPDATE ────────────────────────────────────────────────────────────────────────────────
TrainShieldController receives TrainShieldSync:
  Signals.OnTrainShieldChanged:Fire(currentShield, maxShield)
TrainShieldGuiController (per TrainShieldMonitor-tagged part):
  shieldSnap.current/max updated (shared across all monitors)
  each monitor's displayedShieldPct eased toward shieldSnap on RenderStepped
  Online (>25%) / Critical (<=25%, exits >28%) + Shield image swap

Client / Server / Shared​

Client — TrainShieldController.client.luau Receives TrainShieldSync from the server and bridges it to Signals.OnTrainShieldChanged. Also surfaces the ShieldConsole-tagged model's ProximityPrompt so players can interact — on Triggered it calls ReqRechargeShield: on success it plays SoundManager.PlaySFX("ShieldRecharge"); NO_ENERGY and SHIELD_FULL error codes fire Signals.RequestNotification toasts (warn / info respectively).

Client — TrainShieldGuiController.client.luau Drives the diegetic shield monitor — a SurfaceGui clone parented onto every BasePart tagged TrainConfig.SHIELD_MONITOR_TAG ("TrainShieldMonitor"), discovered via CollectionService. This replaces the old on-screen shield HUD entirely. See Shield monitor (SurfaceGui) below for the full behavior.

Server — TrainShieldManager.luau Initialize() is called by TrainShieldSystemLoader.server.luau. Owns the authoritative currentShield and maxShield values. Handles ReqRechargeShield.OnServerInvoke with an isRecharging boolean mutex. ApplyDamage is the single damage entry point for the shield; it is a no-op before hasStarted and after TrainGameOver.HasFired(). See ApplyDamage below for the absorb/bleed-through split. subscribeBuffs uses WaitForChild to attach GetAttributeChangedSignal listeners to both buff folders, and calls recomputeMax once after attach to catch any missed signals during the WaitForChild window.

Server — TrainShieldSystemLoader.server.luau Thin bootstrap that calls TrainShieldManager.Initialize() once per server.

Server — EnergyToolHelper.luau (shared with fuel) GetEnergyTier(tool), GatherEnergyTools(player), ConsumeTool(player, tool) — server-only helpers shared by both TrainFuelManager and TrainShieldManager. Single source of truth for Energy tool scanning and consumption. No duplication between the two systems.

Server — ProximityValidation.luau (shared with fuel) FindPromptPart(root, partName), IsPlayerNear(player, promptPart, prompt, tolerance) — server-only helpers for console/engine proximity checks. Shared between refuel and shield recharge.

Server — TrainGameOver.luau (shared with fuel) HasFired(), Trigger(reason: number?), GetReason(), Reset() — idempotent game-over gate shared by both fuel-out paths. Shield depletion no longer triggers game over directly — only TrainFuelManager (natural stall-out or combat fuel-kill via shield bleed-through) calls Trigger. Trigger stores the TrainGameOverReason code, fires Signals.OnTrainGameOver(reasonCode) exactly once, and is a no-op on subsequent calls; Reset clears the flag and reason for round restart. See Train Fuel for the two reason codes.

Shared — TrainConfig.luau Shield knobs alongside fuel knobs. See Config knobs below.

Shield monitor (SurfaceGui)​

The shield HUD is diegetic, not on-screen: TrainShieldGuiController clones the ReplicatedStorage.GuiAssets.TrainShieldGui SurfaceGui template onto every BasePart tagged TrainConfig.SHIELD_MONITOR_TAG ("TrainShieldMonitor"), discovered via CollectionService:GetTagged plus GetInstanceAddedSignal/GetInstanceRemovedSignal for live tag changes. The clone is created client-side, so each player drives their own independent copy of the monitor face on the same shared surface — there is no server/replication involvement in the GUI itself. Each registered monitor owns a Janitor that destroys the clone and disconnects its RunService.RenderStepped render loop when the tag is removed from the part.

The monitor drives two readouts:

  • Shield — displayedShieldPct is eased every frame toward the latest Signals.OnTrainShieldChanged snapshot (current / max, exponential smoothing). The status reads "Online" (cyan) while above 25%, and flips to "Critical" (red) at or below 25%, with hysteresis: once Critical, it doesn't return to Online until the displayed percentage rises back above 28%. Entering/exiting Critical also swaps the Shield ImageLabel's asset between a normal and a critical image, in addition to recoloring the percentage text and status label.
  • Fuel reserve — extrapolated from Signals.OnTrainStateChanged exactly like the separate on-screen TrainFuelGui HUD (server snapshot + drain rate, predicted forward from workspace:GetServerTimeNow()). Cyan normally, turning red at or below 25% fuel. This is purely a second readout on the same monitor face — it does not replace or change TrainFuelGui.

The on-screen TrainFuelGui HUD (StarterGui, ScreenGui) is unchanged by this rework; it continues to run independently. No server, packet, or signal changes were made — the monitor consumes the same Signals.OnTrainShieldChanged and Signals.OnTrainStateChanged signals the old HUD and TrainFuelGui already used.

Max formula​

maxShield = (BASE_SHIELD + TechTreeBuffs.MaxHP) * (1 + PartyPerkBuffs.TrainShieldBonus)
  • Tech Tree additive: each Durability node unlock accumulates onto TechTreeBuffs.MaxHP (Durability_T1 +50, Durability_T2 +150). This is added to BASE_SHIELD before the perk multiplier.
  • Party perk multiplicative: TrainShieldBonus = 0.05 * maxLevel across all players (server-max resolution). Applied as a multiplier on top of the Tech Tree + base sum.
  • Ratio-preserving recompute: when either buff changes, recomputeMax preserves the current fill ratio (currentShield / oldMax) and rounds to the nearest integer. A player at 60% shield before an upgrade stays at ~60% after.

See Tech Tree and Perks for the upstream buff systems.

ApplyDamage / fuel bleed-through​

TrainShieldManager.ApplyDamage(amount, source?) is the single damage entry point for the train — all incoming attack/hazard damage, whether it lands on the shield or bleeds through to fuel, is routed through this one call. It is designed for future combat or hazard systems to call; no system calls it yet.

Guards (all must pass or the call is a no-op):

  • hasStarted must be true (pre-game freeze — shield cannot be damaged before first brake release)
  • TrainGameOver.HasFired() must be false (no double-trigger after game over)
  • amount must be > 0 and not NaN

Behavior branches on the current shield value:

  • Shield > 0 (absorbs): currentShield = max(0, currentShield - amount), then broadcasts. The hit that drives the shield exactly to 0 discards its excess — none of that hit's damage carries over to fuel. Reaching 0 this way does not end the round; the round continues with the shield depleted.
  • Shield == 0 (bleeds through): the entire hit converts to fuel damage: TrainFuelManager.ApplyFuelDamage(amount * TrainConfig.FUEL_DAMAGE_FACTOR, source). See Train Fuel — Combat fuel-kill for what happens when this drains fuel to 0 (immediate game over, no grace).

This replaces the old behavior where the shield reaching 0 triggered TrainGameOver.Trigger("shield depleted") directly. Shield depletion is no longer a game-over condition by itself — it just removes the train's damage buffer, exposing fuel to combat damage.

The TrainCore tag (TrainConfig.CORE_TAG = "TrainCore") is reserved for the physical train model that future combat systems will tag; ApplyDamage does not read it directly — callers are expected to check that damage originated from a TrainCore-adjacent event before calling.

Studio setup​

ShieldConsole model​

Each ShieldConsole-tagged root (a Model or BasePart) must contain:

  • A child BasePart named "ProxPromptPart" with a child ProximityPrompt. The prompt part is resolved recursively via ReplicatedStorage/SharedModules/PromptResolver, so it may be nested at any depth. The prompt's MaxActivationDistance is authored in Studio; the server adds TrainConfig.PROXIMITY_TOLERANCE studs of slack when validating.

Tag the model with ShieldConsole via CollectionService (or the Studio Tag Editor). Multiple consoles are supported — each is registered independently by TrainShieldController.

TrainShieldGui template + monitor parts​

The monitor face is an authored SurfaceGui template at ReplicatedStorage.GuiAssets.TrainShieldGui; TrainShieldGuiController never creates UI in code, only clones the template. Element names inside the template are load-bearing — TrainShieldGuiController resolves them with WaitForChild and will error on startup if any are missing or renamed.

Tag every BasePart that should display a monitor with TrainConfig.SHIELD_MONITOR_TAG ("TrainShieldMonitor") via CollectionService (or the Studio Tag Editor). The template is cloned onto each tagged part client-side, so multiple monitors and multiple players are all supported — every player renders their own copy of every tagged monitor independently.

TrainCore tag (optional)​

Tag the train's structural model with "TrainCore" via CollectionService. Currently unused by TrainShieldManager (which exposes ApplyDamage as a callable API) but reserved for future combat systems that need to resolve which hits count as train damage.

Gotchas​

Recharge mutex is not a queue

isRecharging is a boolean, not a queue. A second recharge request while one is in-flight returns SHIELD_FULL or NO_ENERGY (whichever applies) — not a queued success. The player can try again immediately after. This matches the fuel system's isRefueling behavior.

Pre-game freeze

hasStarted is false until Signals.SetTrainStarted fires (i.e. the first brake release on the fuel side). ApplyDamage is a no-op until then. This matches the fuel system's freeze behavior. Do not try to damage the shield before the train is started.

Passive regen is off by default

SHIELD_REGEN_ENABLED = false and SHIELD_REGEN_PER_SEC = 0. No regen loop exists yet. To add passive regen, implement a RunService.Heartbeat-based loop in TrainShieldManager gated on SHIELD_REGEN_ENABLED. Do not add regen without also updating this page and the config map.

Shield depletion is no longer a game over

Reaching 0 shield used to call TrainGameOver.Trigger("shield depleted") directly — it no longer does. The shield can sit at 0 indefinitely; only fuel reaching 0 (natural stall-out or combat bleed-through) ends the round. See Train Fuel — game-over reasons.

Game-over is still a placeholder

TrainGameOver.Trigger (invoked from the fuel side) currently only prints to output and fires Signals.OnTrainGameOver. No round reset, respawn, or UI is triggered. Do not ship without replacing it with a real mechanic.

typeof guard on OnServerInvoke

ReqRechargeShield.OnServerInvoke receives (player, console) where console is client-supplied. The handler runs a typeof(console) == "Instance" guard before attempting to acquire the isRecharging lock, so a malformed invocation (e.g. nil or a non-Instance) is rejected cleanly without erroring.
