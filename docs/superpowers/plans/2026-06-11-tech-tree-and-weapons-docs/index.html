# Tech Tree

Author these sections (prose in the train-fuel.md voice; all data below is verified and must appear):

Intro (2–4 sentences): Cooperative, server-wide, session-only (no DataStore) tech tree. Players pool crafted materials (Wood/Metal) into nodes at one fixed bench. Eligibility is always-open (any node whose prereq is unlocked and which is not yet unlocked accepts submissions); a node auto-unlocks the instant its full cost is met. Because refunds go to a shared ground pile, there is no per-player contribution tracking — one shared pool per node.

## Data flow — ASCII diagram, Server column ↔ Client column, packet names on arrows. Cover four flows:

  • Submit: GUI stepper → ReqTechSubmit(nodeId, materialType, amount) → server validates proximity (INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE) + TechTreeState.validateSubmit + player actually holds amount Tools → consume exactly amount → pools[id][mat] += amount → if every material now meets cost: clear pool, unlocked[id]=true, fire OnNodeUnlocked, broadcast TechNodeUpdate(..., isUnlocked=true); else broadcast updated counts → respond (success, reasonCode).
  • Auto-unlock effect: OnNodeUnlocked(nodeId) → TechEffectsDispatcher reads Effect from config → applies it (StatBuff wired; others warn + no-op) → next tier lights up because isEligible now passes.
  • Cancel: ReqTechCancel(nodeId) → validate proximity + pool > 0 → snapshot + zero pool → broadcast TechNodeUpdate(..., 0, 0, false) → MaterialEjector.Eject(bench, snapshot) arcs materials to a ProximityPickup floor pile. Node stays open.
  • Join: client → ReqTechSnapshot() → server returns full { unlocked, pools }.

## Client / Server / Shared — one bold-headed paragraph each:

  • Shared — TechTreeState.luau (pure validator; single rule source — client greys buttons, server authorizes; the four functions confirmed in Step 1).
  • Server — TechTreeService.server.luau (owns unlocked / pools, handles ReqTechSubmit / ReqTechCancel / ReqTechSnapshot, consumes Tools, fires OnNodeUnlocked, broadcasts deltas).
  • Server — TechEffectsDispatcher.server.luau (connects OnNodeUnlocked; switches on Effect.Type; one StatBuff wired; unknown types warn + no-op so future nodes are declarable now).
  • Server — MaterialEjector.luau (shared mechanism: MotionMaster.SplineMove arc from the bench TrajectoryPoints → registers each piece with ProximityPickupServer, auto-collect fallback; no tech-tree knowledge).
  • Client — TechTreeGuiController.client.luau (drives authored StarterGui.TechTreeGui, proximity-opens, steppers max = min(held, remaining), repaints on OnTechTreeStateChanged; server is truth).

## Gotchas — :::caution blocks + prose:

  • Server re-checks proximity on every submit/cancel; client GUI proximity is never trusted.

  • Over-submission is clamped server-side (validateSubmit rejects amount that would exceed remaining) — the stepper max is enforced authoritatively, not just in UI.

  • Validate-then-consume: the server counts the player's Tools first and consumes nothing on rejection.

  • Concurrent last-unit submit: server events are single-threaded; the second submit sees the node already unlocked → ALREADY_UNLOCKED, consumes nothing.

  • Effect idempotency: the unlocked guard means OnNodeUnlocked fires exactly once per node — StatBuff cannot double-apply.

  • TechNodeUpdate is typed to the two current materials (metalSubmitted, woodSubmitted); adding a third craft material requires widening this packet (to an Any material→count map).

  • Cancel with an empty pool is rejected (NOTHING_TO_REFUND), no arc. Missing bench / TrajectoryPoints degrades gracefully (drop at origin), never errors the cancel.

# Weapons

Sections (health.md / train-fuel.md voice; data below verified):

Intro: Client-predicts / server-authoritative combat with a shared validator (WeaponValidation). All damage is applied server-side; client hit claims are never trusted. Weapons are Roblox Tools equipped from the Backpack; the server infers the weapon from the equipped Tool, so fire packets carry only origin/direction.

## Categories — verbatim table (from WeaponConfig.luau):

| Category | Weapons | Delivery | Damage type |
|---|---|---|---|
| Melee | ClassicSword (combo: 3 hits + finisher) | server re-runs hitbox from server CFrame | `Melee` |
| Gun (hitscan) | Pistol, SMG, AR, SR | server `workspace:Raycast`, server hit wins | `Bullet` |
| Gun (projectile) | RocketLauncher | server-owned replicated `ServerProjectile`; AOE on impact | `AOE` |
| Throwable (fuse) | Grenade | replicated `ServerProjectile`, bounces, AOE on fuse expiry | `AOE` |
| Throwable (manual) | C4 | replicated `ServerProjectile`, sticks; AOE on `ReqDetonate` | `AOE` |

## Data flow — ASCII, Server ↔ Client, packet names on arrows. Cover:

  • Melee: input → canFire gate → swing anim (MotionMaster) + predicted FX → ReqMeleeSwing(aimDir) → server fire-rate (WeaponState) + meleeHitbox from server CFrame → CombatService.ApplyHit (Melee) → broadcast WeaponImpact.
  • Hitscan gun: canFire + local ammo predict → muzzle flash + tracer → ReqFireWeapon(origin, dir) → server validates fire-rate + ammo + origin tolerance + spread bound → workspace:Raycast capped at MaxDistance → CombatService.ApplyHit (Bullet, ×HeadshotMultiplier on Head) → broadcast WeaponFired + WeaponAmmoSync to owner.
  • Rocket / Throwable: ReqFireWeapon (rocket) / ReqThrowProjectile(origin, dir) (grenade, C4) → server validates → spawns replicated ServerProjectile → on impact/fuse CombatService.ApplyAOE (aoeFalloff to AOERadius) → broadcast ExplosionAt.
  • C4 detonate: ReqDetonate() → server detonates all of that player's active C4, AOE per charge, destroys instances.

## Client / Server / Shared — bold-headed paragraphs:

  • Client — WeaponController.client.luau (watches equipped Tool, reads WeaponConfig[name].Category, owns input/lifecycle, dispatches to a handler).
  • Client — WeaponHandlers/ (MeleeHandler combo stepping, GunHandler hitscan + rocket cosmetic + ammo prediction, ThrowableHandler grenade/C4, TrajectoryPreview client-local green-neon arc while a throwable is equipped — no packets).
  • Client — WeaponEffectsController.client.luau (consumes WeaponFired / WeaponImpact / ExplosionAt; ignores the local shooter, who draws its own tracer).
  • Shared — WeaponValidation.luau (pure math both sides run; functions confirmed in Step 1).
  • Server — WeaponServer.server.luau (receives packets, per-category validation, applies damage).
  • Server — CombatService.luau (damage router: Player → HealthManager.ApplyDamage, "NPC"-tagged Humanoid → direct, else ignore; friendly-fire prevention).
  • Server — WeaponState.luau (per-player authoritative mag / reserve / cooldown / reload window).
  • Server — ServerProjectile.luau (server-owned replicated physics projectile for rocket / grenade / C4).

## Gotchas / anti-exploit — :::caution + prose:

  • Server enforces fire-rate (60/RPM for guns, melee ChainWindow/Recovery/ResetCooldown); early requests dropped.

  • Ammo + reload timing are server-authoritative (WeaponState); fire at empty mag rejected; mid-reload fire rejected.

  • Claimed origin must be within tolerance of the player's muzzle/character; spread dir must lie within Spread of aim; hitscan acceptance + ray length capped at MaxDistance. LOS is implicit (server does its own cast).

  • Friendly-fire prevention: players do not damage teammates (confirm exact rule in CombatService).

  • NPC pass-through: the "NPC" CollectionService tag both gates Humanoid damage and places NPC parts in the Character collision group so thrown charges pass through (see NpcCollisionService). No tag → no damage, no pass-through.

  • HealthManager mirrors its record → Humanoid.Health but does not read Humanoid → record; route player damage through HealthManager.ApplyDamage (via CombatService), never raw Humanoid writes.
