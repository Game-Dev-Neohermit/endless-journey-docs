Janitor Cleanup Adoption Implementation Plan

For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

Goal: Adopt the Janitor library as the project's single cleanup primitive and migrate the five hand-rolled connection-tracking sites to it, fixing two latent connection leaks along the way.

Architecture: Add howmanysmall/janitor as a Wally dependency, then replace each manual { RBXScriptConnection } array + disconnect loop with a Janitor that owns one lifecycle scope. Keyed collections store one Janitor per entry. No project wrapper — Janitor is used directly.

Tech Stack: Luau (--!strict), Rojo, Wally (howmanysmall/janitor@1.18.3), Roblox Studio for verification.

Design spec: docs/superpowers/specs/2026-06-01-janitor-cleanup-adoption-design.md

Conventions for this plan (read first)​

This repo has no automated test suite — verification is manual in Studio. Per project preferences:

  • Do NOT run rojo build — the user syncs live with Studio.
  • Do NOT run selene as a verification step.
  • Do NOT run manual playtests via the Roblox Studio MCP — Studio verification is the user's responsibility. Hand the branch back for the user to test in Studio.
  • All git commits in this plan MUST be authored using the Claude Haiku model (project preference). The executing agent should delegate each commit to a Haiku subagent (or the configured Haiku commit path) using the exact commit message given in the step.

The static gate available to the agent is the Luau type-check via the LSP/sourcemap. After a code change, regenerate the sourcemap if package structure changed and confirm the edited file has no new type errors:

rojo sourcemap default.project.json -o sourcemap.json --include-non-scripts

Use the LSP tool (or read the file) to confirm no new diagnostics in the edited file. This is the per-task verification gate in place of unit tests.

Janitor API reference (used throughout)​

local Janitor = require(ReplicatedStorage.Packages.Janitor)

local j = Janitor.new()                                  -- create
j:Add(instance.Event:Connect(fn), "Disconnect")          -- connection (default cleanup is "Disconnect")
j:Add(hoverHandle, "Stop")                               -- arbitrary object, calls :Stop()
j:Add(part, "Destroy")                                   -- instance
j:Cleanup()                                              -- run all cleanups; Janitor stays reusable
j:Destroy()                                              -- run all cleanups; Janitor no longer usable

The exported type is Janitor.Janitor. For a connection, "Disconnect" is Janitor's default for RBXScriptConnection, but this plan passes it explicitly for clarity.

### Cleanup / lifecycle (Janitor)

Any scope that owns connections or instances (a per-character binding, a
per-entity registration, a UI binding, a tool equip) MUST use **Janitor**
(`ReplicatedStorage.Packages.Janitor`, Wally dep `howmanysmall/janitor`).
Do **not** hand-roll `{ RBXScriptConnection }` arrays with manual disconnect
loops.

Pattern — one Janitor owns one lifecycle scope:

```lua
local Janitor = require(ReplicatedStorage.Packages.Janitor)
local janitor = Janitor.new()
janitor:Add(inst.Event:Connect(fn), "Disconnect")
janitor:Add(part, "Destroy")
janitor:Cleanup()  -- tear down, reuse (e.g. on respawn)
janitor:Destroy()  -- tear down, discard

Keyed collections store one Janitor per entry — { [key]: { ..., cleaner: Janitor.Janitor } } — and unregister an entry with entry.cleaner:Destroy().

Exception: singleton top-level controller connections that live for the whole session (they never churn) do not need a Janitor.
