Audit Tier 1 Fixes — Implementation Plan

Task 2: [PP1] Stop item loss on merge + keepModel​

_TryMerge sums Quantity and destroys the absorbed item, but keepModel callbacks (default Backspace-dropped Tools) move only the single surviving tool, ignoring Quantity — so merging two identical dropped tools loses one. Exclude keepModel records from merging.

Files:

  • Modify: src/ServerStorage/SharedModules/ProximityPickupServer.luau (_TryMerge)

  • Step 1: Skip keepModel on both sides of the merge

In _TryMerge, after fetching newItem and its guards, add an early-out; and inside the loop, skip keepModel survivors:

local function _TryMerge(newItemId: string)
	if not ProximityPickupConfig.MERGE_ENABLED then
		return
	end

	local newItem = activeItems[newItemId]
	if not newItem or newItem.State ~= "Unclaimed" then
		return
	end
	-- keepModel items ARE the inventory object; their pickup callback moves the single
	-- physical tool and cannot represent Quantity > 1, so merging them would destroy one.
	if newItem.KeepModel then
		return
	end
	if not newItem.Metadata.ItemType then
		return
	end

	for existingId, existingItem in activeItems do
		if existingId == newItemId then
			continue
		end
		if existingItem.State ~= "Unclaimed" then
			continue
		end
		if existingItem.KeepModel then
			continue
		end
		if existingItem.Metadata.ItemType ~= newItem.Metadata.ItemType then
			continue
		end
		if not existingItem.Part or not newItem.Part then
			continue
		end
		if (existingItem.Part.Position - newItem.Part.Position).Magnitude > ProximityPickupConfig.MERGE_RADIUS then
			continue
		end

		existingItem.Metadata.Quantity = (existingItem.Metadata.Quantity or 1) + (newItem.Metadata.Quantity or 1)
		newItem.Zone:Destroy()
		if newItem.Part and newItem.Part.Parent then
			newItem.Part:Destroy()
		end
		activeItems[newItemId] = nil
		return
	end
end
  • Step 2: Studio verification — dropped tools no longer vanish

Play, obtain two identical craft-material Tools (e.g. two Wood), drop both with Backspace within ~2 studs of each other, wait ~1.5s (past MERGE_DELAY), then walk over them. Expected: you receive two Wood tools back (before the fix you'd get one).

  • Step 3: Studio verification — shredder-output merging still consolidates

Shred a junk pile so several same-type materials land close together. Walk over the pile. Expected: you receive the full count (keepModel=false shredder materials still merge correctly via the Claim path).

  • Step 4: Commit
git add src/ServerStorage/SharedModules/ProximityPickupServer.luau
git commit -m "fix(pickup): exclude keepModel items from merge to prevent item loss (PP1)"

  • Step 2: Add the reach check at the top of ClaimJunkForPlayer

Insert immediately after the if not junk or junk.Collected then return false end guard:

	-- Server-side proximity: reconstruct the junk's current position from its spawn
	-- position + how far the shared odometer has advanced since it spawned (junk moves
	-- along MOVE_DIRECTION at the shared speed, same integration the client uses).
	local character = player.Character

	end

Task 4: [J2] Reclaim leaked retracting junk on the client​

If a claim's BeginJunkRetract fires but JunkCollected never arrives (finalize fails / collector disconnects / reservation times out), the pooled model is orphaned and retractingJunks leaks, eventually exhausting the pool. Add a reclaim timeout.

Files:

  • Modify: src/StarterPlayer/StarterPlayerScripts/JunkController.client.luau (BeginJunkRetract handler)

  • Step 1: Add a reclaim-timeout constant

Near the top of the file, beside retractingJunks:

-- Junks currently being retracted (removed from simulation, awaiting JunkCollectedEvent)
local retractingJunks: { [number]: ActiveJunk } = {}

-- Safety net: if JunkCollected never arrives (finalize failed / collector left), return the
-- orphaned model to its pool. Must exceed the server reservation timeout (5s) + round trip.
local RETRACT_RECLAIM_TIMEOUT = 8
  • Step 2: Schedule the reclaim when tracking a retracting junk

In the BeginJunkRetract.OnClientEvent handler, immediately after retractingJunks[junkId] = entry:

	-- Track as retracting so JunkCollectedEvent can clean up the pool
	retractingJunks[junkId] = entry

	-- Safety net: reclaim to the pool if JunkCollected never arrives.
	task.delay(RETRACT_RECLAIM_TIMEOUT, function()
		local stale = retractingJunks[junkId]
		if stale then
			retractingJunks[junkId] = nil
			local pool = pools[stale.PoolName]
			if pool then
				CleanupJunkModel(stale.Model)
				pool:InsertObject(stale.Model)
			end
		end
	end)
  • Step 3: Studio verification — normal collection unaffected

Grab junk normally. Expected: model returns to pool on JunkCollected (no visible change; the timeout simply never fires because the entry is already cleared).

  • Step 4: Studio verification — orphaned junk is reclaimed

Simulate a stuck retract: in a two-client Studio test, have one client claim a junk, then before finalize completes force the failure (e.g. stop the collector's character). After RETRACT_RECLAIM_TIMEOUT, confirm the junk model is back in ReplicatedStorage.Pools (not stuck frozen in workspace.JunksVisuals). Quick proxy check: print #workspace.JunksVisuals:GetChildren() before and ~10s after — it should not be permanently inflated.

Task 8: [SND1] Rate-limit + allowlist the sound relay​

ReplicateSoundAtLocation relays any client's sound (arbitrary SoundId, no rate limit) to everyone. Add a per-player rate limit and an allowlist built from the configs that legitimately replicate sound.

Files:

  • Modify: src/ServerScriptService/ReplicatedSoundService.server.luau

  • Step 1: Rewrite the relay with validation

Replace the entire file body with:

local ReplicatedStorage = game:GetService("ReplicatedStorage")
local Players = game:GetService("Players")

local SharedModules = ReplicatedStorage.SharedModules
local Packets = require(SharedModules:WaitForChild("Packets"))
local CustomTypes = require(SharedModules:WaitForChild("CustomTypes"))
local GrabHookConfig = require(SharedModules.Configs:WaitForChild("GrabHookConfig"))
local ProximityPickupConfig = require(SharedModules.Configs:WaitForChild("ProximityPickupConfig"))

-- Allowlist of sound IDs clients may replicate. Sourced from the configs that legitimately
-- fire ReplicateSoundAtLocation, so adding a new replicated sound only means adding it to a config.
local ALLOWED_SOUND_IDS: { [string]: true } = {}
for _, id in {
	GrabHookConfig.Sounds.FireSoundId,
	GrabHookConfig.Sounds.LoopSoundId,
	GrabHookConfig.Sounds.CooldownOverSoundId,
	ProximityPickupConfig.PICKUP_SOUND_ID,
} do
	if type(id) == "string" and id ~= "" then
		ALLOWED_SOUND_IDS[id] = true
	end
end

-- Per-player rate limit (anti-spam).
local MIN_INTERVAL = 0.05 -- seconds between accepted relays per player
local lastSoundTime: { [Player]: number } = {}

Packets.ReplicateSoundAtLocation.OnServerEvent:Connect(function(player: Player, data: CustomTypes.SoundData)
	local now = os.clock()
	local last = lastSoundTime[player]
	if last and (now - last) < MIN_INTERVAL then
		return
	end

	-- Validate payload shape and allowlist the sound id.
	if typeof(data) ~= "table" or typeof(data.SoundConfig) ~= "table" then
		return
	end
	local id = data.SoundConfig.Id
	if type(id) ~= "string" or not ALLOWED_SOUND_IDS[id] then
		return
	end

	lastSoundTime[player] = now

	local players = Players:GetPlayers()
	local senderIndex = table.find(players, player)
	if senderIndex then
		table.remove(players, senderIndex)
	end

	for i = 1, #players do
		task.spawn(function()
			Packets.ReplicateSoundAtLocation:FireClient(players[i], data)
		end)
	end
end)

Players.PlayerRemoving:Connect(function(player: Player)
	lastSoundTime[player] = nil
end)
  • Step 2: Studio verification — legit replicated sounds still play for others

Two-client Studio test: fire the GrabHook on client A. Expected: client B hears the fire/loop sound at the location (unchanged for allowlisted IDs).

  • Step 3: Studio verification — injected/spam sounds are rejected

From the command bar (client A), fire ReplicateSoundAtLocation with an arbitrary SoundId not in any config, and also fire it in a tight loop. Expected: client B hears nothing for the unknown id, and rapid-fire requests are dropped after the first per 0.05s window.

  • Step 4: Commit
