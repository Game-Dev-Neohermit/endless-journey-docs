Perk System — Combat & Economy Wiring (Spec 2) Implementation Plan

For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

Goal: Wire three already-implementable perks into existing server chokepoints — Player Damage (DamageBonus), Coin Gain (CoinGainBonus), and Fuel Efficiency (FuelEfficiencyBonus, stacking multiplicatively with the Tech Tree's now-resolved FuelEfficiency node) — using only the buff folders Spec 1 already publishes.

Architecture: No new modules, packets, GUI, or persistence. Each perk is a surgical multiplier read at one server-side chokepoint that already exists: a scaledDamage helper at every WeaponServer damage call site, a scale at the top of CoinManager.AddCoins, and an effective-drain multiplier in TrainFuelManager. The Tech Tree's FuelEfficiency effect (currently a warn+no-op) gains a handler that writes a drain multiplier into TechTreeBuffs.FuelEfficiency, which TrainFuelManager reads as a second, multiplicative factor.

Tech Stack: Roblox / Luau, Rojo sync. Reads Spec 1's replicated buff folders (ReplicatedStorage/PerkBuffs/<UserId>, ReplicatedStorage/PartyPerkBuffs) and the Tech Tree's ReplicatedStorage/TechTreeBuffs. No external libraries.

Testing note: This project has no automated test suite — verification is done in Roblox Studio (per CLAUDE.md). Each task ends with a concrete Studio observation and a commit. Do not run rojo build or selene as verification (project preference); the user syncs live with rojo serve.

Prerequisite: Spec 1 (Perk Framework) is merged. PerkConfig declares DamageBonus, CoinGainBonus, and FuelEfficiencyBonus; PerkEffectsDispatcher already publishes all three buff attributes (personal DamageBonus/CoinGainBonus into PerkBuffs/<UserId>, party FuelEfficiencyBonus into PartyPerkBuffs). This spec only adds consumers.

Reference spec: docs/superpowers/specs/2026-06-12-perk-combat-economy-wiring-design.md

-- Perk (Spec 2): scale a base damage by the ATTACKING player's DamageBonus.
-- Applied AFTER any headshot multiplier so the two multipliers compose
-- predictably. Server-side read of the replicated buff folder the server itself

local function scaledDamage(player: Player, base: number): number
	local buffs = ReplicatedStorage:FindFirstChild("PerkBuffs")
	local holder = buffs and buffs:FindFirstChild(tostring(player.UserId))
	local bonus = holder and (holder:GetAttribute("DamageBonus") :: number?) or 0
	return base * (1 + bonus)
end

Task 2: Coin gain multiplier (CoinGainBonus) in CoinManager​

Files:

  • Modify: src/ServerStorage/SharedModules/CoinManager.luau

AddCoins(player, amount, reason?) is the single award API every earner calls. Scaling here means every current and future earner inherits the bonus with no per-earner change. ReplicatedStorage is already required (line 20).

  • Step 1: Scale amount inside AddCoins — replace the body of AddCoins (lines ~66-80) so the scale happens after the profile check and before the MAX_BALANCE clamp:
function CoinManager.AddCoins(player: Player, amount: number, reason: string?)
	if amount <= 0 then
		return
	end
	local profile = Profiles[player]
	if not profile then
		return
	end
	-- Perk (Spec 2): scale by the player's CoinGainBonus. math.max(1, math.floor(...))
	-- guarantees a legitimate >=1 reward never rounds down to 0 and that fractional
	-- coins never accrue. Server-side read of the replicated buff folder — unforgeable.
	local buffs = ReplicatedStorage:FindFirstChild("PerkBuffs")
	local holder = buffs and buffs:FindFirstChild(tostring(player.UserId))
	local bonus = holder and (holder:GetAttribute("CoinGainBonus") :: number?) or 0
	amount = math.max(1, math.floor(amount * (1 + bonus)))
	local newBalance = math.min(profile.Data.Coins + amount, CoinConfig.MAX_BALANCE)
	profile.Data.Coins = newBalance
	if reason then
		print(("[CoinManager] +%d coins to %s (%s) → %d"):format(amount, player.Name, reason, newBalance))
	end
	replicate(player)
end

TechTreeConfig.Fuel_T1 declares Effect = { Type = "FuelEfficiency", Multiplier = 2 }, but the dispatcher has no handler (warns + no-ops). Add a handler that stores a drain multiplier into TechTreeBuffs.FuelEfficiency: Multiplier = 2 means "twice as efficient" → drain × 0.5, so the handler writes 1 / Multiplier. Absent attribute = 1 (no reduction). Multiple fuel nodes stack multiplicatively. TrainFuelManager (Task 4) reads this as one factor of its effective drain.

  • Step 1: Add the handler — insert after applyStatBuff (after line 37, before the EFFECT_HANDLERS table):
local function applyFuelEfficiency(effect: TechTreeConfig.Effect)
	local mult = effect.Multiplier :: number?
	if type(mult) ~= "number" or mult <= 0 then
		warn("[TechEffectsDispatcher] FuelEfficiency missing/invalid Multiplier")
		return
	end
	-- Store a *drain* multiplier: Multiplier = 2 ("twice as efficient") -> 0.5 drain.
	-- Absent = 1 (no reduction). Multiple fuel nodes compound multiplicatively.
	local current = (buffsFolder:GetAttribute("FuelEfficiency") :: number?) or 1
	buffsFolder:SetAttribute("FuelEfficiency", current * (1 / mult))
end
  • Step 2: Register the handler — add it to the EFFECT_HANDLERS table (lines ~39-41):
local EFFECT_HANDLERS: { [string]: (TechTreeConfig.Effect) -> () } = {
	StatBuff = applyStatBuff,
	FuelEfficiency = applyFuelEfficiency,
}

Task 4: Fuel efficiency consumer (FuelEfficiencyBonus × Tech Tree) in TrainFuelManager​

Files:

  • Modify: src/ServerStorage/SharedModules/TrainFuelManager.luau

Fuel is computed algebraically — every state change snapshots fuel and sets currentRate via rateForState() (called in both commitEvent and Initialize). Multiplying inside rateForState() is therefore the single chokepoint that covers running and braked drain, the stall scheduler (reschedule derives timeToEmpty from currentRate), and the client broadcast (TrainStateSync sends currentRate). ReplicatedStorage is already required (line 19).

Effective rule: effectiveRate = baseRate × techMult × max(FLOOR, 1 − FuelEfficiencyBonus), where techMult is TechTreeBuffs.FuelEfficiency (default 1) and FuelEfficiencyBonus is PartyPerkBuffs.FuelEfficiencyBonus (default 0). The floor stops fuel from ever reaching zero drain.

  • Step 1: Add the drainMultiplier helper — insert immediately before rateForState (before line 81, after isRunning):
local FUEL_DRAIN_FLOOR = 0.1 -- perk reduction can never drop drain below 10%

-- Effective drain multiplier = Tech Tree fuel multiplier × perk reduction.
-- TechTreeBuffs.FuelEfficiency stores a drain multiplier (0.5 = half drain); absent = 1.
-- PartyPerkBuffs.FuelEfficiencyBonus is a fraction reduced (0.4 = -40% drain); absent = 0.
-- The two stack multiplicatively and neither silently overrides the other.
local function drainMultiplier(): number
	local techFolder = ReplicatedStorage:FindFirstChild("TechTreeBuffs")
	local techMult = (techFolder and techFolder:GetAttribute("FuelEfficiency") :: number?) or 1
	local partyFolder = ReplicatedStorage:FindFirstChild("PartyPerkBuffs")
	local bonus = (partyFolder and partyFolder:GetAttribute("FuelEfficiencyBonus") :: number?) or 0
	local perkMult = math.max(FUEL_DRAIN_FLOOR, 1 - bonus)
	return techMult * perkMult
end
  • Step 2: Apply the multiplier in rateForState — replace the running/braked branches (lines ~81-90) so both scale by drainMultiplier() (the 0 returns for frozen/stalled stay untouched — zero stays zero):
local function rateForState(): number
	if not hasStarted then
		return 0 -- frozen pre-game phase: no drain, no scheduled stall
	elseif isStalled then
		return 0
	elseif isBraked then
		return TrainConfig.STOPPED_DRAIN_PER_SEC * drainMultiplier()
	end
	return TrainConfig.RUNNING_DRAIN_PER_SEC * drainMultiplier()
end
  • Step 3: Add the live re-snapshot helpers — insert in the -- [[ PUBLIC ]] section, just before function TrainFuelManager.Initialize() (before line 347). commitEvent is already defined above; these reference it as an upvalue:
-- A mid-run drain-buff change must re-snapshot fuel under the new rate, or the
-- algebraic model would keep extrapolating the old rate forever (the subscription
-- is load-bearing, not cosmetic). Skip while frozen/stalled so we don't disturb the
-- pre-game freeze or reset the game-over timer.
local function onDrainBuffChanged()
	if not hasStarted or isStalled then
		return
	end
	commitEvent()
end

-- The buff folders are created by other server scripts (PerkEffectsDispatcher,
-- TechEffectsDispatcher), so wait for them before subscribing.
local function subscribeDrainBuffs()
	local partyFolder = ReplicatedStorage:WaitForChild("PartyPerkBuffs", 30)
	if partyFolder then
		partyFolder:GetAttributeChangedSignal("FuelEfficiencyBonus"):Connect(onDrainBuffChanged)
	end
	local techFolder = ReplicatedStorage:WaitForChild("TechTreeBuffs", 30)
	if techFolder then
		techFolder:GetAttributeChangedSignal("FuelEfficiency"):Connect(onDrainBuffChanged)
	end
end
  • Step 4: Kick off the subscription in Initialize — add at the end of TrainFuelManager.Initialize, after the final Packets.TrainStateSync:Fire(...) (line ~372):
	-- Re-snapshot when a fuel-drain buff changes mid-run (perk allocate/respec,
	-- party-max change on join/leave, Tech node unlock).
	task.spawn(subscribeDrainBuffs)

  • Step 5: Verify (Studio Play) — Un-brake the train so fuel starts draining; note the HUD fuel-bar drain speed. Open the perk panel → Party tab → raise Efficiency (FuelEfficiencyBonus) to Lv 10 (0.4 → drain × 0.6); the bar should immediately slow (the live re-snapshot) without needing a brake toggle. Confirm PartyPerkBuffs.FuelEfficiencyBonus = 0.4 in Explorer. Then unlock Fuel_T1 (Task 3, TechTreeBuffs.FuelEfficiency = 0.5) — drain should slow further to × 0.5 × 0.6 = × 0.30 of baseline, confirming the two stack multiplicatively. Respec the perk → drain speeds back up live. Max perk + node still drains slowly (never zero — FUEL_DRAIN_FLOOR).
