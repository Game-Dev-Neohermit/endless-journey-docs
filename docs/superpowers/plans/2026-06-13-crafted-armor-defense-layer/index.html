Crafted Armor — Defense Layer & Perk Rework Implementation Plan

For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

Goal: Add a server-authoritative per-player armor tier that grants a base % incoming-damage reduction, and rework the existing Armor perk from a standalone reduction into an efficiency multiplier on that base, combined and clamped at the single HealthManager damage sink.

Architecture: A new ArmorConfig (tier table + cap) and a new ArmorManager (owns its own PlayerArmor ProfileStore session, single writer of ReplicatedStorage/ArmorState/<UserId>.ArmorBaseReduction, exposes SetTier as the seam for the future workbench-crafting spec). HealthManager.applyDamageInternal reads both the armor base and the perk efficiency per hit, computes clamp(armorBase * (1 + efficiency), 0, 0.75), and scales damage. The Armor perk's BuffKey is renamed ArmorReduction → ArmorEfficiency (the existing dispatcher auto-publishes the new key, no dispatcher edit).

Tech Stack: Roblox / Luau / Rojo. New: ReplicatedStorage/SharedModules/Configs/ArmorConfig.luau, ServerStorage/SharedModules/ArmorManager.luau, ServerScriptService/ArmorSystemLoader.server.luau. Edited: HealthManager.luau, PerkConfig.luau. ProfileStore (ServerStorage/SharedModules/ProfileStore.luau) consumed, not modified.

Context the implementer must know​

  • Spec: docs/superpowers/specs/2026-06-13-crafted-armor-defense-layer-design.md. Read it first.
  • No automated test suite exists. Per CLAUDE.md, verification happens in Roblox Studio. "Verify" steps below are Studio observations, not test commands. Do not add a test framework.
  • Do not run rojo build or selene — the user syncs live with Studio and has asked to skip both as verification steps.
  • Per-system ProfileStore convention (important deviation from the spec wording). The spec says "add an ArmorTier field to the player profile template." In this codebase there is no single shared profile — each system owns its own store (PerkManager → PlayerPerks, XPManager → its own, CoinManager → its own). So ArmorManager owns a new PlayerArmor store with template { ArmorTier = 0 }, mirroring PerkManager. This is the established pattern; do not try to graft ArmorTier onto PlayerPerks.
  • ArmorManager is the single writer of ReplicatedStorage/ArmorState. This mirrors how PerkEffectsDispatcher is the single writer of PerkBuffs. Armor is not a perk, so it gets its own folder rather than sharing PerkBuffs.
  • perkId stays "Armor"; only the BuffKey string changes. Persisted PerkLevels reference the perk by id ("Armor"), not by BuffKey, so the rename needs no data migration — existing leveled perks keep working, they just publish under the new attribute name.
  • The dispatcher needs no edit. PerkEffectsDispatcher.publishPersonal writes holder:SetAttribute(perk.BuffKey, ...) for every Personal perk, so changing BuffKey in PerkConfig automatically publishes PerkBuffs/<UserId>.ArmorEfficiency and stops publishing ArmorReduction.
  • HealthManager already has a perkBonus(player, key) helper (around line 75) that reads PerkBuffs/<UserId>.<key>. Reuse it for the efficiency read. Add a sibling helper for the ArmorState read.
  • Bootstrap pattern: each server system has a *SystemLoader.server.luau in ServerScriptService that requires its manager and calls .Initialize() (see HealthSystemLoader.server.luau, PerkSystemLoader.server.luau). Add one for armor.
  • HealthManager.ApplyDamage is live — it is already called by CombatService (which WeaponServer and NpcCollisionService route through), so this change affects real combat immediately.

  • Step 1: Write ArmorConfig.luau

Create src/ReplicatedStorage/SharedModules/Configs/ArmorConfig.luau with exactly:

--!strict

--[=[
	@class ArmorConfig
	Single tuning surface for crafted player armor. Each tier provides a base
	% incoming-damage reduction; the Armor perk (`ArmorEfficiency`) multiplies it.
	Tier is the persisted unit (see `ArmorManager`); base reduction is always
	derived from this table, so retuning a tier retroactively updates every player
	holding it. Per project convention, tune armor here, not in code.
]=]

export type ArmorTier = {
	BaseReduction: number, -- fraction of incoming damage removed at this tier
	DisplayName: string,
}

local ArmorConfig = {}

-- Hard cap on TOTAL post-perk reduction, enforced at the HealthManager sink.
-- Matches the Player Armor perk cap so stacking can never reach immunity.
ArmorConfig.MaxReductionCap = 0.75

-- ProfileStore key for persisted armor tier (its own store, per-system convention).
ArmorConfig.STORE_NAME = "PlayerArmor"

-- Tier 0 = unarmored. Values are gameplay placeholders — tune freely.
ArmorConfig.Tiers = {
	[0] = { BaseReduction = 0.00, DisplayName = "Unarmored" },
	[1] = { BaseReduction = 0.10, DisplayName = "Scrap Plate" },
	[2] = { BaseReduction = 0.18, DisplayName = "Riveted Mail" },
	[3] = { BaseReduction = 0.25, DisplayName = "Reinforced Rig" },
} :: { [number]: ArmorTier }

return ArmorConfig

Task 2: Create ArmorManager and its loader​

  • Step 1: Write ArmorManager.luau

Create src/ServerStorage/SharedModules/ArmorManager.luau with exactly:

--!strict

--[=[
	@class ArmorManager
	@server
	Authority for a player's crafted-armor tier. Owns the `PlayerArmor` ProfileStore
	(one session per player, key = UserId) and is the single writer of
	`ReplicatedStorage/ArmorState/<UserId>.ArmorBaseReduction` — the tier's base
	% incoming-damage reduction that `HealthManager` reads at the damage sink. Tier
	is the only persisted value; base reduction is derived from `ArmorConfig`. The
	workbench-crafting spec drives tier changes through `ArmorManager.SetTier`.
]=]

local Players = game:GetService("Players")
local ReplicatedStorage = game:GetService("ReplicatedStorage")
local ServerStorage = game:GetService("ServerStorage")

local SharedModules = ReplicatedStorage.SharedModules
local ArmorConfig = require(SharedModules.Configs:WaitForChild("ArmorConfig"))
local ProfileStore = require(ServerStorage.SharedModules:WaitForChild("ProfileStore"))

local PROFILE_TEMPLATE = {
	ArmorTier = 0,
}

local PlayerStore = ProfileStore.New(ArmorConfig.STORE_NAME, PROFILE_TEMPLATE)
local Profiles: { [Player]: any } = {}

local ArmorManager = {}
local initialized = false

local function ensureFolder(name: string): Folder
	local f = ReplicatedStorage:FindFirstChild(name)
	if not f then
		f = Instance.new("Folder")
		f.Name = name
		f.Parent = ReplicatedStorage
	end
	return f :: Folder
end

local armorState = ensureFolder("ArmorState")

-- Base reduction for a tier; 0 for unknown/missing tiers.
local function baseReductionForTier(tier: number): number
	local entry = ArmorConfig.Tiers[tier]
	return entry and entry.BaseReduction or 0
end

-- Publish this player's current tier base reduction to ArmorState/<UserId>.
local function publish(player: Player)
	local profile = Profiles[player]
	if not profile then
		return
	end
	local holder = armorState:FindFirstChild(tostring(player.UserId)) :: Folder?
	if not holder then
		holder = Instance.new("Folder")
		holder.Name = tostring(player.UserId)
		holder.Parent = armorState
	end
	holder:SetAttribute("ArmorBaseReduction", baseReductionForTier(profile.Data.ArmorTier))
end

--[=[
	@within ArmorManager
	Set the player's crafted-armor tier. Returns false (no-op) if the profile is
	missing or the tier is not declared in `ArmorConfig.Tiers`. This is the seam the
	workbench-crafting system calls. Persists the tier and republishes the attribute.
]=]
function ArmorManager.SetTier(player: Player, tier: number): boolean
	local profile = Profiles[player]
	if not profile then
		return false
	end
	if type(tier) ~= "number" or ArmorConfig.Tiers[tier] == nil then
		return false
	end
	profile.Data.ArmorTier = tier
	publish(player)
	return true
end

--[=[
	@within ArmorManager
	The player's persisted armor tier (0 if no profile is loaded).
]=]
function ArmorManager.GetTier(player: Player): number
	local profile = Profiles[player]
	return (profile and profile.Data.ArmorTier) or 0
end

--[=[
	@within ArmorManager
	The base % incoming-damage reduction for the player's current tier (0 if none).
]=]
function ArmorManager.GetBaseReduction(player: Player): number
	return baseReductionForTier(ArmorManager.GetTier(player))
end

local function onPlayerAdded(player: Player)
	local profile = PlayerStore:StartSessionAsync(tostring(player.UserId), {
		Cancel = function()
			return player.Parent ~= Players
		end,
	})

	if profile == nil then
		player:Kick("Armor profile failed to load — please rejoin.")
		return
	end

	profile:AddUserId(player.UserId)
	profile:Reconcile()

	profile.OnSessionEnd:Connect(function()
		Profiles[player] = nil
		player:Kick("Armor profile session ended — please rejoin.")
	end)

	if player.Parent == Players then
		Profiles[player] = profile
		publish(player)
	else
		profile:EndSession()
	end
end

--[=[
	@within ArmorManager
	Wire profile lifecycle and publish the initial armor state. Call once.
]=]
function ArmorManager.Initialize()
	if initialized then
		return
	end
	initialized = true

	for _, player in Players:GetPlayers() do
		task.spawn(onPlayerAdded, player)
	end
	Players.PlayerAdded:Connect(onPlayerAdded)
	Players.PlayerRemoving:Connect(function(player)
		local profile = Profiles[player]
		if profile then
			profile:EndSession()
		end
		local holder = armorState:FindFirstChild(tostring(player.UserId))
		if holder then
			holder:Destroy()
		end
	end)
end

return ArmorManager

  • Step 3: Replace the "Armor damage mitigation" paragraph in docs/systems/perks.md

Replace the entire paragraph beginning **Armor damage mitigation.** (line ~48) with:

**Armor damage mitigation.** Crafted armor (see [`ArmorConfig`](../reference/config-map.md) / `ArmorManager`) publishes a per-player `ArmorState/<UserId>.ArmorBaseReduction` — the base fraction of incoming damage removed by the player's current armor tier. The **Armor perk** no longer reduces damage on its own; it is an *efficiency multiplier* on that base. `HealthManager.applyDamageInternal` reads both per hit and computes `reduction = clamp(ArmorBaseReduction * (1 + ArmorEfficiency), 0, 0.75)`, then scales `amount` by `(1 - reduction)` as the final step before subtracting from health. With no armor (`tier 0 → base 0`) the perk contributes nothing. Because the attacker's `DamageBonus` is already applied upstream in `WeaponServer`, attacker bonus and defender mitigation multiply independently: `base * (1 + DamageBonus) * (1 - reduction)`. Coverage is every path routed through `CombatService`/`HealthManager` (Melee/Bullet/AOE and NPC hits); damage written directly to `Humanoid.Health` bypasses the sink and is not mitigated (see [Health](health.md#gotchas)).
