Melee Combo System — Design Spec

Status: Approved (brainstorm 2026-06-06) Builds on: Weapon System design and the shipped Plan 1 — Foundation + Melee (feat/weapon-system, commits 8f6c552…eba823e). Supersedes: the Plan 1 single-swing melee model (flat SwingCooldown).

1. Purpose & scope​

Replace the current "every swing is identical, gated by one flat cooldown" melee with a single left-click combo string per weapon — a chain of hits (e.g. LC→LC→LC→LC) that escalates and ends in a finisher, then briefly locks out before restarting. The number of hits and their stats are fully data-driven per weapon (tune in config; no code change to add/remove hits).

In scope: combo data model, shared advancement validator, client prediction with input buffering, server authority, per-player combo state, a HUD signal, migration of ClassicSword.

Out of scope (explicitly): right-click / alternate strings (schema leaves room — see §4), movement/WalkSpeed effects (none), animation-cancel/branch graphs, knockback/stun, directional or charged attacks. These are non-goals for this iteration.

2. Decisions (from brainstorm)​

TopicDecision
Input modelBuffered click-to-advance — a click during a swing queues the next hit, which fires the instant the current hit's Recovery elapses.
Per-hit dataRich per-hit — each step requires its own timing; Damage/Range/HitboxSize/Anim/Sounds are optional overrides of weapon-level defaults.
AuthorityServer authoritative, no correction. Server derives the combo index from its own clock; ReqMeleeSwing stays payload-less. Client prediction drives animation only and self-heals.
MovementFree — swinging does not touch WalkSpeed (no Sprint/Stamina coupling).
RCLC-only now, RC-ready schema — combos are keyed by InputKind; only Primary is populated.
Combo endBrief post-combo cooldown (ResetCooldown) before the chain can restart at hit 1.

3. Relationship to the existing system / breaking changes​

This reshapes the melee core built in Plan 1. The client-predicts/server-authoritative split, CombatService damage routing, WeaponState per-player record, Tool-dispatch WeaponController, WeaponDebug visualizer, and the ReqMeleeSwing/WeaponImpact packets all stay. Changes are localized to the melee config schema, WeaponValidation, MeleeHandler, WeaponServer, and WeaponState.

Breaking: MeleeWeaponConfig.SwingCooldown is removed. A single-swing weapon is now expressed as a one-step combo whose Recovery equals the old cooldown. There is no dual code path — every melee weapon has a Combos.Primary.

WeaponDebug.DrawBox is already called per-swing by MeleeHandler; with per-step hitboxes it will automatically visualize each combo step's box (a nice free win for tuning).

4. Config schema (WeaponTypes)​

export type InputKind = "Primary" | "Secondary" -- Secondary (RC) reserved; unused this iteration

export type ComboStep = {
    -- Required combo-timing (no sensible single default, so always per-step):
    Recovery: number,     -- min seconds before the NEXT hit may execute. Paces the swing AND is the
                          -- server anti-exploit min-interval. The next buffered hit fires at this boundary.
    ChainWindow: number,  -- seconds after this hit during which the combo stays alive; past it, the next
                          -- swing restarts at hit 1. INVARIANT: ChainWindow >= Recovery.
                          -- Ignored on the final step (restart is governed by ComboDef.ResetCooldown).

    -- Optional overrides; omitted fields fall back to the weapon-level default:
    Damage: number?,
    Range: number?,
    HitboxSize: Vector3?,
    AnimId: string?,
    SwingSound: string?,
    ImpactSound: string?,
}

export type ComboDef = {
    Steps: { ComboStep },     -- ordered; combo length = #Steps
    ResetCooldown: number?,   -- brief lockout after the finisher before restarting at hit 1 (default 0)
}

export type MeleeWeaponConfig = BaseWeaponConfig & {
    Category: "Melee",
    -- Weapon-level DEFAULTS, used by any step that omits its own value:
    Range: number,
    HitboxSize: Vector3,   -- X = width, Y = height; depth comes from the step's (or default) Range
    SwingSound: string,
    ImpactSound: string,
    SwingAnimId: string?,
    -- Combo strings keyed by input. Only Primary (LC) is read this iteration.
    Combos: { [InputKind]: ComboDef },
}

BaseWeaponConfig.Damage is the default per-hit damage for melee (a step's Damage overrides it). DamageType stays weapon-level ("Melee").

ClassicSword migration (4-hit escalating, brief reset):

ClassicSword = {
    Category = "Melee", DisplayName = "Classic Sword", ToolName = "ClassicSword",
    Damage = 25, DamageType = "Melee",
    Range = 8, HitboxSize = Vector3.new(5, 6, 0),
    SwingSound = "MeleeSwing", ImpactSound = "MeleeImpact",
    SwingAnimId = nil,
    Combos = {
        Primary = {
            Steps = {
                { Recovery = 0.30, ChainWindow = 0.55 },                        -- hit 1: 25 dmg (default)
                { Recovery = 0.30, ChainWindow = 0.55 },                        -- hit 2: 25
                { Recovery = 0.35, ChainWindow = 0.55 },                        -- hit 3: 25
                { Recovery = 0.55, ChainWindow = 0.75, Damage = 45, Range = 10 }, -- finisher: slower, harder, longer
            },
            ResetCooldown = 0.25,
        },
    },
}

5. Shared validator (WeaponValidation)​

One pure function decides advancement for both sides, so prediction and authority can't drift. Keeps the existing canFire/queryMeleeTargets/meleeHitbox/resolveHumanoidModel helpers.

export type ComboState = { index: number, lastHitTime: number } -- index 0 = no active combo

-- Returns the 1-based step index THIS swing should execute, and whether it's accepted.
-- `accepted == false` means "not yet" (client buffers the click; server drops the request).
function WeaponValidation.resolveComboSwing(
    state: ComboState,
    combo: ComboDef,
    now: number,        -- os.clock() timestamp from the calling side
    tolerance: number   -- jitter slack so legit hits aren't dropped (server); ~0 on client
): (number?, boolean)
    local steps = combo.Steps
    local count = #steps
    local idx = state.index
    local elapsed = now - state.lastHitTime

    if idx >= 1 and idx <= count then
        if idx >= count then
            -- finished the full combo → restart at 1 once ResetCooldown elapses
            if elapsed < (combo.ResetCooldown or 0) - tolerance then
                return nil, false
            end
            return 1, true
        end
        local step = steps[idx]
        if elapsed < step.Recovery - tolerance then
            return nil, false        -- too soon: still in this hit's recovery
        end
        if elapsed > step.ChainWindow then
            return 1, true           -- chain expired → fresh combo
        end
        return idx + 1, true         -- continue the chain
    end

    return 1, true                   -- no active combo → start
end

Plus a resolver for per-step values with weapon-default fallback (used by both sides), returning a flat struct so callers read named fields:

export type ResolvedStep = {
    Damage: number,
    Range: number,
    HitboxSize: Vector3,
    SwingSound: string,
    ImpactSound: string,
    AnimId: string?,
}

-- Each field falls back to the weapon-level default when the step omits it.
function WeaponValidation.resolveStep(config: MeleeWeaponConfig, step: ComboStep): ResolvedStep

Notes

  • Advancement is independent of whether the swing hit anything — you can chain in the air; damage applies only to whatever is in that step's hitbox.
  • Config invariant ChainWindow >= Recovery per non-final step (otherwise the chain expires before you're allowed to continue). Document in the config; not runtime-enforced.

6. Client flow (MeleeHandler)​

Per equipped Tool (Janitor-scoped), maintain a local ComboState and a single buffered-click slot.

On LC (Tool.Activated):

  1. now = os.clock(). Call resolveComboSwing(state, combo, now, 0).
  2. Accepted → set state = { index = stepIndex, lastHitTime = now }, then for that step (via resolveStep):
    • play swing sound (SoundManager.PlaySFXAt, replicated) and optional AnimId;
    • run the predicted hitbox (queryMeleeTargets with the step's range/hitbox) → fire Signals.WeaponLocalHit on a hit;
    • draw the step's box via WeaponDebug.DrawBox(meleeHitbox(...), didHit);
    • fire Signals.WeaponComboChanged(toolName, stepIndex, #steps);
    • send payload-less Packets.ReqMeleeSwing:Fire().
  3. Not accepted (busy) → store the click in the buffer slot and schedule a one-shot retry at the Recovery/ResetCooldown boundary (task.delay tracked by the Tool's Janitor). When it fires, re-run step 1 once; if still not accepted, drop it (no infinite re-buffer).

Reset the local ComboState to { index = 0, lastHitTime = -math.huge } on unequip (OnUnequip) and on a fresh character. The local cooldown clock is per-character/per-Tool, not module-global (fixes the Plan 1 module-level lastSwing).

7. Server flow (WeaponServer)​

On ReqMeleeSwing from a player:

  1. Resolve equipped Tool → MeleeWeaponConfig (existing getEquippedWeapon). Read combo = config.Combos.Primary.
  2. Load the player's authoritative ComboState for this weapon from WeaponState. now = os.clock().
  3. stepIndex, accepted = resolveComboSwing(state, combo, now, TOLERANCE). Rejected → return (drop).
  4. Accepted → persist { index = stepIndex, lastHitTime = now }. Resolve the step's effective Range/HitboxSize/Damage (resolveStep), re-run queryMeleeTargets from the server's character CFrame, route each hit through CombatService.ApplyToModel(..., melee.DamageType, player), and broadcast Packets.WeaponImpact:Fire(pos, toolName) per hit.

TOLERANCE is a small constant (≈ 0.05s) absorbing network jitter so a slightly-early packet isn't wrongly dropped. Security property preserved: DPS is capped by per-step Recovery; the finisher is unreachable without walking hits 1→N; client aim and client-claimed index are never trusted.

8. State (WeaponState)​

Extend the per-player record with a combo map keyed by weapon name:

type Record = {
    lastFire: { [string]: number },                 -- (retained; later gun plans use it)
    combo: { [string]: { index: number, lastHitTime: number } },
}

Accessors: GetCombo(player, weaponName) -> ComboState (defaults {0, -math.huge}), SetCombo(player, weaponName, index, time), ResetCombo(player, weaponName). Cleared on player leave via the existing Clear/Initialize. No explicit unequip packet — switching weapons uses a different key and idle combos lapse by timeout.

9. Signals / HUD contract​

Add one client signal (the user builds the HUD; we only emit):

WeaponComboChanged = Signal() :: Signal.Signal<string, number, number>, -- (weaponName, stepIndex, comboLength)

Fired by MeleeHandler on each accepted predicted hit. A combo counter HUD reads stepIndex/comboLength; it can infer reset when no event arrives within the window. WeaponEquipped/Unequipped/WeaponLocalHit are unchanged. No new packets.

10. Verification (Studio, manual)​

  • 4 quick LCs on the dummy apply 25/25/25/45 (=120) and the 4th visibly differs (longer reach box if you stand at ~9 studs).
  • Spamming LC faster than Recovery does not exceed the 4-hit cadence (buffering paces it); the burst-fire exploit check from Plan 1 still caps damage.
  • Pausing mid-combo > ChainWindow restarts at hit 1 (25 dmg).
  • Immediately after the finisher, the next hit is briefly gated (ResetCooldown) before hit 1 lands.
  • WeaponDebug (ENABLED) shows the per-step box; the finisher's is larger.

11. Open questions​

None blocking. Future: RC string (Combos.Secondary), per-step knockback/stun, animation-driven hit timing — all additive to this schema.
