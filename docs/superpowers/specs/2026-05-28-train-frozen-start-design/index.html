Train Frozen Start — Design

Date: 2026-05-28 Status: Approved (pending written-spec review)

Goal​

The game should begin in a frozen state: train fuel does not drain and no floating junk spawns. The first time a player un-brakes the train, everything starts — fuel begins draining at the running rate and junk spawns normally.

This is a one-time transition per server session. After the game has started, braking reverts to today's behavior (slow drain STOPPED_DRAIN_PER_SEC

  • slow junk via SetTrainState(false)); the frozen state never returns.

Current behavior (for contrast)​

  • Train starts braked (TrainConfig.INITIAL_BRAKED = true).
  • Braked → fuel drains at STOPPED_DRAIN_PER_SEC (1/30/sec, slow but nonzero).
  • Braked → Signals.SetTrainState:Fire(false) → junk spawns at STOPPED_SPAWN_RATE / STOPPED_JUNK_SPEED (slow but still spawning).

So today there is no true "off" state — only "running" (fast) and "stopped" (slow). This design adds a pre-game frozen phase that is fully off.

Design​

1. Signals — Signals/init.luau​

Add a dedicated boolean signal:

SetTrainStarted = Signal() :: Signal.Signal<boolean>,

This keeps the existing SetTrainState boolean untouched. SetTrainState continues to mean "is the train moving fast vs slow"; SetTrainStarted means "has the game started (does junk spawn at all)". The two concerns stay separate.

2. TrainFuelManager — TrainFuelManager.luau​

  • New state flag hasStarted = false.
  • rateForState(): return 0 first when not hasStarted (frozen), before the stalled/braked/running checks. With currentRate == 0, reschedule() schedules nothing, so fuel never drains and never stalls during the frozen phase.
  • Initialize(): set hasStarted = false; fire Signals.SetTrainStarted:Fire(false). INITIAL_BRAKED stays true (train starts braked + frozen, prompt reads "Resume Train").
  • handleToggleBrake(): on the first un-brake (not hasStarted and the toggle results in un-braked), set hasStarted = true and fire Signals.SetTrainStarted:Fire(true) before calling commitEvent(). commitEvent then flips SetTrainState to running (running-state flip from false→true) and schedules the stall under the now-running rate.

Because the train always starts braked, the only way to reach an un-braked state while not hasStarted is this first "Resume Train", so the first toggle is unambiguously the start trigger.

3. JunkService — JunkService.server.luau​

  • Initialize the already-present-but-unused CurrentState.IsSpawning to false.
  • Gate the spawn loop: continue when not CurrentState.IsSpawning (after the task.wait(rate)).
  • Connect Signals.SetTrainStarted → set CurrentState.IsSpawning = started.

Default-false plus the handler means no startup race regardless of server script load order: if SetTrainStarted(false) fires before JunkService connects its handler, the default already gates spawning; SetTrainStarted(true) only fires later (on un-brake), by which point the handler is connected.

4. Client — no changes​

  • Fuel rate 0 → the client's predicted bar sits static at INITIAL_FUEL (extrapolation fuel - rate * dt with rate == 0).
  • The brake lever prompt already shows "Resume Train" while braked (TrainClient.client.luau leverActionText), so the first un-brake naturally doubles as the start action.
  • distanceTravelled / EXP tracking already only advances while isTrainMoving (false during the frozen phase), so it stays frozen with no change.

5. Docs — Project-Maintenance-Guide.md​

Add SetTrainStarted to the signals / networking map (producer: TrainFuelManager on first un-brake / at init; consumer: JunkService — gates whether junk spawns at all).

Out of scope​

  • No separate "press to start" UI; the existing "Resume Train" prompt suffices.
  • No change to the "stopped/slow" behavior after the game has started.
  • No persistence of hasStarted across server restarts (per-session only).
