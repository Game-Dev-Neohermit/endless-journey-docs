Train Fuel System — Design

Date: 2026-05-28 Status: Approved design, pending implementation plan

Summary​

A server-authoritative fuel system for the train. Fuel is a single global, server-wide resource (0–100). The train consumes fuel while running; players refuel by feeding collected Energy junk (Tiers 1–5, already collectable via the GrabHook) into the engine through a ProximityPrompt. A separate brake lever world object lets players stop/resume the train: while braked the floating junk slows significantly and fuel drains at a much lower rate. When fuel reaches 0 the train stalls (junk slows as if braked) and a 3-minute countdown begins; on expiry the game prints a placeholder "GAME OVER" message (real game-over is a future TODO). Refueling above 0 cancels the countdown and resumes running.

Architecture follows the existing Approach A pattern: a dedicated TrainFuelManager module + a thin loader, mirroring StaminaManager / StaminaSystemLoader.

Goals​

  • Global shared fuel (one train, one 0–100 value, everyone sees the same level).
  • Refuel by feeding Energy junk via an engine ProximityPrompt.
  • Brake lever (separate tagged world object) to stop/resume the train.
  • Visible fuel level on every client's HUD.
  • Server-authoritative with anti-exploit validation, consistent with the codebase's predict/authoritative pattern.
  • Engine and lever models are not built yet — code must wait on CollectionService tags so absent models cause no errors.

Non-goals​

  • Real game-over handling (only a print + TODO for now).
  • Per-player fuel.
  • EXP/progression tie-ins.
  • Building the engine/lever models themselves (authored later in Studio).

Architecture​

Dedicated server module + loader, mirroring Stamina/Health:

  • ServerStorage/SharedModules/TrainFuelManager.luau — authoritative state + logic.
  • ServerScriptService/TrainFuelSystemLoader.server.luau — requires the manager, calls .Initialize().

The manager fires the existing Signals.SetTrainState(boolean), which JunkService already consumes to slow junk spawn rate / speed. The brake and the stall both reuse this wiring — no changes to JunkService's junk logic are required.

Drain model — event-driven + prediction (no loop)​

Fuel drains at a known constant rate within any given state, so it is computed algebraically rather than iterated per frame.

Server holds:

fuelAtLastEvent : number    -- fuel snapshot at the last state change
lastEventTime   : number    -- workspace:GetServerTimeNow() at that change
currentRate     : number    -- fuel/sec being drained in the current state
isBraked        : boolean    -- player lever state
isStalled       : boolean    -- true while fuel == 0
gameOverFired   : boolean    -- guard so the placeholder prints once
scheduleNonce   : number     -- bumped on every event to invalidate stale task.delay callbacks
  • getFuel() = clamp(fuelAtLastEvent - currentRate * (now - lastEventTime), 0, MAX_FUEL) — computed on demand.
  • Effective running state = not isBraked and not isStalled.
  • currentRate = RUNNING_DRAIN_PER_SEC when running, STOPPED_DRAIN_PER_SEC when braked, 0 when stalled.

Events (refuel, brake toggle, stall, resume, init): snapshot current fuel into fuelAtLastEvent, set lastEventTime = now, update currentRate, bump scheduleNonce, (re)schedule future transitions, broadcast TrainStateSync, and fire SetTrainState if the effective running state changed.

Scheduled future transitions (via task.delay, guarded by scheduleNonce):

  • Entering a draining state → task.delay(getFuel() / currentRate, onStall) (fires exactly when fuel hits 0).
  • On stall → task.delay(GAME_OVER_DELAY, onGameOver).
  • Any new event bumps scheduleNonce; a fired callback whose captured nonce != current nonce is a no-op.

onStall: set isStalled = true, currentRate = 0, snapshot (fuel = 0), fire SetTrainState(false), broadcast, schedule game-over.

onGameOver: if not gameOverFired → print("[TrainFuel] GAME OVER — train out of fuel"), set guard. -- TODO: real game-over mechanic.

Resume from stall happens only via refuel (see below).

Initial state / join​

  • Initialize(): fuel = MAX_FUEL, isBraked = false, isStalled = false, currentRate = RUNNING_DRAIN_PER_SEC, lastEventTime = now. Fire SetTrainState(true), schedule stall, broadcast.
  • Players.PlayerAdded → send TrainStateSync to that player with the current snapshot so their HUD initializes correctly.

Config — ReplicatedStorage/SharedModules/Configs/TrainConfig.luau​

MAX_FUEL              = 100
RUNNING_DRAIN_PER_SEC = 1/6      -- full tank = 600s = 10 min
STOPPED_DRAIN_PER_SEC = 1/30     -- braked: 5x slower
GAME_OVER_DELAY       = 180      -- 3 min stalled -> game over (print + TODO)
PROXIMITY_TOLERANCE   = 4        -- server-only slack added during anti-exploit distance checks
ENGINE_TAG            = "TrainEngine"
BRAKE_LEVER_TAG       = "TrainBrakeLever"
REFUEL_PROMPT_PART    = "RefuelPromptPart"
BRAKE_PROMPT_PART     = "BrakePromptPart"
BRAKE_ACTION_STOP     = "Stop Train"
BRAKE_ACTION_RESUME   = "Resume Train"
TierRecharge          = { [1] = 5, [2] = 10, [3] = 20, [4] = 30, [5] = 50 }

No INTERACT_DISTANCE: the ProximityPrompt's MaxActivationDistance (and ActionText/ObjectText for the refuel prompt) are authored in Studio, not pushed by script.

Networking — add to Packets/init.luau​

  • TrainStateSync (Server → all Clients; fired only on events, plus to a single player on join):
    • fuel NumberF32, rate NumberF32, isBraked Boolean8, isStalled Boolean8, serverTime NumberF32
  • ReqRefuelTrain (Client → Server, Response): arg engine Instance (Model)
    • Response: success Boolean8, fuelAdded NumberF32, reasonCode NumberU8
  • ReqToggleBrake (Client → Server, Response): arg lever Instance (Model)
    • Response: success Boolean8, isBraked Boolean8, reasonCode NumberU8

Result codes — ReplicatedStorage/SharedModules/TrainResultCodes.luau​

Mirrors ShredderResultCodes: NONE, INVALID_ENGINE, INVALID_LEVER, TOO_FAR, NO_ENERGY, FUEL_FULL, STALLED.

Signals — add to Signals/init.luau​

  • OnTrainStateChanged (client-side): fired by TrainClient on each TrainStateSync to drive the HUD. Signature (fuel, rate, isBraked, isStalled, serverTime).
  • Server reuses the existing SetTrainState.

Server interaction handlers (in TrainFuelManager)​

ReqRefuelTrain.OnServerInvoke(player, engine)​

  1. Validate engine is a Model with the ENGINE_TAG (CollectionService) → else INVALID_ENGINE.
  2. Proximity check: player HumanoidRootPart → engine PrimaryPart, within the refuel prompt's own MaxActivationDistance + PROXIMITY_TOLERANCE → else TOO_FAR.
  3. If getFuel() >= MAX_FUEL → FUEL_FULL.
  4. Gather the player's Energy tools (Backpack + currently-equipped) by reading the Tool's PrimaryPart attributes Type == "Energy" and Tier (reuses the Shredder's getJunkAttributes approach). None → NO_ENERGY.
  5. Sort ascending by TierRecharge value; consume smallest-first, one at a time, while fuel < MAX_FUEL. Each fed tool: add its recharge (cap at MAX), destroy the tool, accumulate fuelAdded. Stop the moment fuel reaches MAX. The bulk stockpile is preserved; only the last tool fed may overshoot the cap slightly (acceptable).
  6. Apply as an event: snapshot fuel. If isStalled and fuel now > 0 → clear stall (isStalled = false), reset gameOverFired. Recompute currentRate for the current running/braked state, bump nonce, reschedule, fire SetTrainState(not isBraked) if the running state changed, broadcast TrainStateSync.
  7. Return success = fuelAdded > 0, fuelAdded, NONE.

Consuming equipped tools: unequip via Humanoid:UnequipTools() before destroying, matching the Shredder.

ReqToggleBrake.OnServerInvoke(player, lever)​

  1. Validate lever is a Model with the BRAKE_LEVER_TAG → else INVALID_LEVER.
  2. Proximity check (brake prompt's MaxActivationDistance + PROXIMITY_TOLERANCE) → else TOO_FAR.
  3. If isStalled → STALLED (lever is locked out until refueled). Return false, isBraked, STALLED.
  4. Toggle isBraked. Apply as an event: snapshot fuel, swap currentRate (running ↔ stopped), bump nonce, reschedule stall, fire SetTrainState(not isBraked), broadcast.
  5. Return true, isBraked, NONE.

Client​

Two files mirroring the Shredder split (ShredderClient interaction + a GUI controller):

StarterPlayer/StarterPlayerScripts/TrainClient.client.luau​

  • Receives Packets.TrainStateSync.OnClientEvent → stores the latest snapshot and fires Signals.OnTrainStateChanged.
  • Registers engine and lever models via CollectionService tags (GetInstanceAddedSignal / GetInstanceRemovedSignal + a pre-tagged scan), exactly like ShredderClient. Absent models → nothing registers, no errors.
  • Refuel prompt: find RefuelPromptPart's ProximityPrompt; connect .Triggered → ReqRefuelTrain:Fire(engine); show a toast with the result (fuelAdded on success, mapped reason on failure). Does not set MaxActivationDistance, ActionText, etc.
  • Brake prompt: find BrakePromptPart's ProximityPrompt; connect .Triggered → ReqToggleBrake:Fire(lever); the only script-controlled property is ActionText, set to BRAKE_ACTION_STOP / BRAKE_ACTION_RESUME based on the synced isBraked (updated on each TrainStateSync). Stalled responses show a toast ("Out of fuel").
  • Reuses the Shredder toast pattern for feedback.

StarterPlayer/StarterPlayerScripts/TrainFuelGuiController.client.luau​

  • Builds a fuel bar + status label programmatically (self-contained, like the Shredder toast UI). Position/colors are local constants; can be restyled later.
  • Per-frame prediction drives smooth drain with zero extra packets: predicted = clamp(snapshot.fuel - snapshot.rate * (GetServerTimeNow() - snapshot.serverTime), 0, MAX_FUEL), read each frame from the latest snapshot.
  • Smooth drain comes from prediction itself (continuous). Refuel jumps are eased with MotionMaster (per the CLAUDE.md client-animation rule).
  • Status label reflects state: normal, BRAKED, OUT OF FUEL.

Model expectations (authored later in Studio)​

Code waits on tags, so these can be built after the code lands.

  • Engine: a Model tagged TrainEngine, with a PrimaryPart, containing a child BasePart named RefuelPromptPart that holds a ProximityPrompt (its MaxActivationDistance, ActionText, ObjectText all set in Studio).
  • Brake lever: a Model tagged TrainBrakeLever, with a PrimaryPart, containing a child BasePart named BrakePromptPart that holds a ProximityPrompt (distance set in Studio; ActionText is overwritten by script).

Part and tag names live in TrainConfig for easy changes.

Verification​

No automated tests; verification happens in Studio via live Rojo sync (no rojo build, no selene step). Manual checks:

  • Fuel drains from 100 over ~10 min running; HUD bar predicts smoothly.
  • Refuel prompt feeds smallest-tier Energy first, only up to the cap; stockpile preserved.
  • Brake lever toggles Stop/Resume; junk visibly slows when braked; fuel drains slower.
  • At 0 fuel: train stalls (junk slows), lever locks out, HUD shows OUT OF FUEL.
  • 3 min after reaching 0 (and not refueled): the placeholder GAME OVER message prints once.
  • Refueling above 0 cancels the countdown and resumes running.
  • Late-joining player's HUD initializes to the current global fuel.
