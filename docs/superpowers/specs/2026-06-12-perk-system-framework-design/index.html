Perk System — Framework (Spec 1 of 5)

Date: 2026-06-12 Status: Approved for planning Game: Endless Journey (Roblox / Rojo / Luau) Series: Spec 1 of 5 — the foundation every other perk spec depends on.

Summary​

A level-driven perk system. Leveling up grants perk points that players spend to raise perks through 10 levels each. Perks come in two categories:

  • Personal perks buff only the owning player (HP, regen, reel speed, …).
  • Party perks buff the whole server, but to keep multiplayer balanced only the highest level held by any player in the server is active, resolved per perk (player A's Train Shield L9 wins independently of who holds the best Fuel perk).

The architecture mirrors the existing Tech Tree: a config defines perks and per-level values, a server authority owns allocation and persistence, and a dispatcher publishes the resolved buff values into replicated folders (ReplicatedStorage/PerkBuffs/<UserId> for personal, ReplicatedStorage/PartyPerkBuffs for party). Consumer systems read one attribute and apply a multiplier — exactly as they would read TechTreeBuffs today.

This spec builds the framework end-to-end and wires the four perks whose underlying mechanic already exists as a working vertical slice. The remaining seven perks are declared in PerkConfig now and wired in Specs 2–5.

Architecture​

Follows the project's client-predicts / server-authoritative pattern, and reuses the Tech Tree shape (pure shared rules + server authority + client controller + effect dispatcher).

ReplicatedStorage/SharedModules/
  Configs/PerkConfig.luau          -- every perk: Category, DisplayName, Description,
                                      MaxLevel, BuffKey, per-level value, display order
  PerkResultCodes.luau             -- numeric reason codes (mirror ShredderResultCodes)
  PerkState.luau                   -- PURE shared logic: canAllocate / spent / available
                                      (no side effects); used by client (button enable)
                                      AND server (authorize). Single rule source.

ServerStorage/SharedModules/
  PerkManager.luau                 -- authority: PlayerPerks ProfileStore, allocate/respec,
                                      derives points from XP level, replicates PerkStateSync

ServerScriptService/
  PerkSystemLoader.server.luau     -- calls PerkManager.Initialize() once (gameplay place)
  PerkEffectsDispatcher.server.luau-- recomputes & publishes resolved buffs to the folders;
                                      fires Signals.ApplyTierMultiplier for Junk Rarity

StarterPlayer/StarterPlayerScripts/
  PerkController.client.luau       -- drives authored StarterGui.PerkGui; predicts spend,
                                      sends ReqAllocatePerk / ReqRespecPerks, repaints on sync

Packets/init.luau   -- ReqAllocatePerk, ReqRespecPerks, PerkStateSync (below)
Signals/init.luau   -- OnPlayerLevelUp (server), OnPerkStateChanged (client)

Persisted state (server, ProfileStore "PlayerPerks")​

PROFILE_TEMPLATE = {
    PerkLevels = {},   -- { [perkId: string]: number }  (1..MaxLevel; absent = level 0)
}

No point counters stored — points are derived (see Decisions). Respec = PerkLevels = {}.

Config & perk model​

PerkConfig is the single tuning surface (per project convention). Each perk declares its category, cap, the buff key it publishes, and a per-level value (linear: published value = PerLevel * level). Starter values below are tunable.

export type PerkCategory = "Personal" | "Party"

export type Perk = {
    Category: PerkCategory,
    DisplayName: string,
    Description: string,   -- "%d" formats the current bonus for the GUI
    MaxLevel: number,      -- 10 for all v1 perks
    BuffKey: string,       -- attribute name written to the buff folder
    PerLevel: number,      -- value added to the buff per level (fraction unless noted)
    Order: number,         -- display order within its tab
}

PerkConfig.MaxPerkLevel = 10

PerkConfig.Perks = {

Consumers read the attribute on the relevant lifecycle event and subscribe to GetAttributeChangedSignal so a mid-session allocate/respec updates live.

Components & responsibilities​

  • PerkState (pure, shared). spent(perkLevels, category), available(perkLevels, category, playerLevel), canAllocate(perkLevels, perkId, playerLevel) -> (ok, reasonCode) (perk exists, level < MaxLevel, available(pool) >= 1). The client greys/enables the + button with it; the server authorizes with the same function.
  • PerkManager (server authority). Owns the PlayerPerks ProfileStore lifecycle (one session per player, key = UserId, identical pattern to XPManager). API: AllocatePoint(player, perkId), Respec(player, pool?), GetPerkLevels(player). Validates with PerkState (reading the player's level via XPManager.GetLevel), mutates PerkLevels, fires a recompute (Signals.OnPerkStateChanged server-side hook for the dispatcher), and sends PerkStateSync to the owner. Resends PerkStateSync on OnPlayerLevelUp (available points grew).
  • PerkEffectsDispatcher (server). The single writer of both buff folders.
    • Personal: for each player, writes every personal BuffKey = PerLevel * level into PerkBuffs/<UserId> (creates the per-player Folder on join, destroys on leave).
    • Party: for each party perk, computes maxLevel across all players' PerkLevels, writes BuffKey = PerLevel * maxLevel into PartyPerkBuffs.
    • Junk Rarity bridge: after recompute, fires Signals.ApplyTierMultiplier(tier, mult) for the rare tiers (3–5) using the resolved bonus — JunkService already listens (no producer existed before this spec).
    • Recomputes on OnPerkStateChanged, PlayerAdded, and PlayerRemoving (party max can drop when the holder leaves).
  • PerkController (client). Opens PerkGui from a HUD button / hotkey. Two tabs render perks from PerkConfig ordered by Order, each a level bar + + button + remaining-points counter; a Respec button per tab. Predicts the spend (optimistic bar fill), fires ReqAllocatePerk / ReqRespecPerks, and reconciles on PerkStateSync. For party perks it also shows the active resolved level read from the PartyPerkBuffs folder so a player sees when their level isn't the active one. No authoritative client state.

Consumer wiring (this spec's 4 perks)​

  • HealthManager (already owns player MaxHealth/regen): on spawn and on HPBonus/RegenBonus change for that UserId, set MaxHealth = HealthConfig.MaxHealth * (1 + HPBonus) (preserve current health, clamp) and scale the regen rate by (1 + RegenBonus).
  • Grabhook (client tool): read PerkBuffs/<UserId>.ReelSpeedBonus and scale the reel speed from GrabHookConfig. Server award/validation is unchanged (reel speed is visual; distance/cooldown thresholds stay authoritative).
  • Junk Rarity: handled entirely by the dispatcher's ApplyTierMultiplier bridge above; no change to JunkService (the listener already exists).

Network protocol (new Packets)​

-- Client → Server: spend one point on a perk (pool inferred from the perk's Category).
ReqAllocatePerk = Packet("ReqAllocatePerk",
    Packet.String      -- perkId
):Response(
    Packet.Boolean8,   -- success
    Packet.NumberU8     -- reason code (PerkResultCodes)
)

-- Client → Server: respec. pool: 0 = both, 1 = Personal, 2 = Party.
ReqRespecPerks = Packet("ReqRespecPerks",
    Packet.NumberU8    -- pool selector
):Response(
    Packet.Boolean8     -- success
)

-- Server → owning Client: authoritative perk snapshot. Sent on load, allocate,
-- respec, and level-up. perkLevels serialized as a { [perkId]=level } map.
PerkStateSync = Packet("PerkStateSync",
    Packet.Any,        -- perkLevels: { [string]: number }
    Packet.NumberU8,   -- personalAvailable
    Packet.NumberU8     -- partyAvailable
)

Party buffs are not packeted — the PartyPerkBuffs folder replicates its attributes to all clients for free, which the UI reads directly.

Two new Signals: OnPlayerLevelUp (server; fired by XPManager on level increase so PerkManager resends available points and the dispatcher needn't change) and OnPerkStateChanged (server; fired by PerkManager after a mutation so the dispatcher recomputes). XPManager gains a GetLevel(player): number getter (derives from TotalXP via XPCurve; returns 1 if no profile) and fires OnPlayerLevelUp where it already detects newLevel > oldLevel.

Data flow​

Allocate: + button → PerkState.canAllocate passes locally → optimistic bar fill → ReqAllocatePerk(perkId) → server re-validates with PerkState + XPManager.GetLevel → PerkLevels[perkId] += 1 → fire OnPerkStateChanged → dispatcher republishes buffs → respond success + PerkStateSync. On reject, client rolls the bar back from the sync.

Respec: Respec button → ReqRespecPerks(pool) → server clears the selected pool's perk levels → OnPerkStateChanged → dispatcher republishes (personal drops to 0 for this player; party perks recompute, possibly still held by someone else) → PerkStateSync.

Level-up: XPManager fires OnPlayerLevelUp(player, newLevel) → PerkManager resends PerkStateSync (available +1/+1) → client toast "Perk point earned".

Join / leave: dispatcher creates/destroys PerkBuffs/<UserId> and recomputes PartyPerkBuffs (a leaving player can lower a party-perk max; a joiner can raise it).

Edge cases & anti-exploit​

  • Authoritative re-validation on every allocate (PerkState + live level) — the client prediction is never trusted; a forged ReqAllocatePerk past cap or with no points is rejected with a distinct reason code and mutates nothing.
  • Derived points can't desync: because available = level − spent, there is no stored counter to corrupt; a profile that somehow holds more spent than the level allows (e.g. a future level-cap reduction) is clamped — available floors at 0 and allocation is blocked.
  • Respec mid-combat: allowed by default (perks are meta-progression); a buff drop simply recomputes Max HP downward with health clamped. (A "safe state only" gate is a one-line config flag if desired later — out of scope here.)
  • Party max recompute on leave: when the highest-level holder leaves, the dispatcher lowers the resolved party buff; consumers update live via attribute-changed signals.
  • Profile not loaded (request before load / after session end): all PerkManager APIs no-op, exactly like XPManager.
  • Unknown perkId: rejected with UNKNOWN_PERK.
  • HP buff & current health: raising Max HP keeps current HP (player must heal up); lowering Max HP clamps current HP to the new max. No free heal on allocate.

Out of scope (this spec)​

  • The 7 perks needing new/hook work: Player Damage, Coin Gain, Fuel Efficiency, Weapon Cost (Spec 2); Player Armor (Spec 3); Train Shield (Spec 4); Cannon Damage (Spec 5). They are declared in PerkConfig and publish buffs, but no consumer reads them yet.
  • Cosmetic perks, prestige beyond level 100, per-perk unlock prerequisites (all perks are available from level 1; the only gate is points).
  • Coin-cost respec (free respec was chosen).
