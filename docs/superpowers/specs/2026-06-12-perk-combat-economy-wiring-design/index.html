Perk System — Combat & Economy Wiring (Spec 2 of 5)

Date: 2026-06-12 Status: Approved for planning Game: Endless Journey (Roblox / Rojo / Luau) Series: Spec 2 of 5 — depends on Spec 1 (Perk Framework). Prerequisite: Spec 1 implemented (the buff folders, PerkConfig declarations, and the buff contract table already exist; these perks are declared but unwired).

Summary​

Wire the three perks whose underlying mechanic already exists and only needs a multiplier hook in an existing path:

  • Player Damage efficiency (Personal, DamageBonus) — outgoing weapon damage.
  • Coin gain multiplier (Personal, CoinGainBonus) — coin rewards.
  • Fuel efficiency (Party, FuelEfficiencyBonus) — train fuel drain, stacking with the Tech Tree's existing FuelEfficiency effect.

Each is a small, surgical change at a single chokepoint already present in the codebase. No new systems, packets, or GUI — Spec 1's framework and folders carry everything.

Deferred (declared, not wired here): Weapon material cost reduction (WeaponCostReduction). Weapons are plain Tools defined in WeaponConfig with no crafting/purchase cost system — there is nothing to reduce. The perk stays declared in PerkConfig and publishes its buff (like Spec 1 leaves all future perks declared); it gets a consumer only if/when a weapon-crafting-cost system is built. See "Deferred" below.

Architecture​

No new modules. Edits to three existing files plus the Tech Tree's fuel hook (wiring the already-declared FuelEfficiency effect that currently no-ops). All read from the Spec 1 buff folders; consumers subscribe to attribute-changed signals for live mid-session updates.

ServerScriptService/WeaponServer.server.luau     -- + scaledDamage(player, base) helper at
                                                    every damage call site (DamageBonus)
ServerStorage/SharedModules/CoinManager.luau      -- AddCoins scales amount (CoinGainBonus)
ServerStorage/SharedModules/TrainFuelManager.luau -- effective drain mult (FuelEfficiencyBonus
                                                    × TechTreeBuffs.FuelEfficiency)

Components & responsibilities​

Player Damage efficiency (DamageBonus)​

WeaponServer already computes a base amount/resolved.Damage per weapon and routes it through CombatService.ApplyToModel / ApplyAOE (melee, gun, throwable/C4 AOE). Add:

-- WeaponServer (server): scale a base damage by the attacker's perk bonus.
local function scaledDamage(player: Player, base: number): number
    local buffs = ReplicatedStorage.PerkBuffs:FindFirstChild(tostring(player.UserId))
    local bonus = buffs and (buffs:GetAttribute("DamageBonus") :: number?) or 0
    return base * (1 + bonus)
end

Apply at each call site: CombatService.ApplyToModel(model, humanoid, scaledDamage(player, resolved.Damage), ...), the gun amount (after the headshot multiplier so the bonus is multiplicative on the final figure), and the AOE damages. Server-authoritative throughout — the client never sends damage. NPC→player and environment damage paths are untouched (no attacking player perk applies).

Coin gain multiplier (CoinGainBonus)​

CoinManager.AddCoins(player, amount, reason?) is the single award API (earners call it). Scale at the top:

function CoinManager.AddCoins(player, amount, reason)
    if amount <= 0 then return end
    local buffs = ReplicatedStorage.PerkBuffs:FindFirstChild(tostring(player.UserId))
    local bonus = buffs and (buffs:GetAttribute("CoinGainBonus") :: number?) or 0
    amount = math.max(1, math.floor(amount * (1 + bonus)))  -- never round a real reward to 0
    -- …existing clamp to MAX_BALANCE + replicate…
end

Every present and future earner benefits with zero per-earner change. No client trust — earners are server-side.

Fuel efficiency (FuelEfficiencyBonus) + Tech Tree stacking​

TrainFuelManager computes fuel algebraically from the last event (no per-frame loop): each state change snapshots fuel and sets currentRate. To apply the buff:

  1. Add effectiveDrain(baseRate) that reads the party buff and the Tech Tree's fuel multiplier: effectiveRate = baseRate * techMult * (1 − FuelEfficiencyBonus) (clamp (1 − bonus) ≥ a small floor, e.g. 0.1, so fuel can't become free). techMult is derived from TechTreeBuffs.FuelEfficiency (see below).
  2. Use effectiveDrain wherever currentRate is set (running/braked).
  3. Mid-run buff change: subscribe to PartyPerkBuffs:GetAttributeChangedSignal("FuelEfficiencyBonus") and TechTreeBuffs:GetAttributeChangedSignal("FuelEfficiency"); on change, perform a state re-snapshot (same path as a brake toggle: snapshot current fuel at old rate, set new rate, broadcast TrainStateSync) so clients re-extrapolate from the new rate.

Tech Tree wiring (resolving the existing no-op): TechTreeConfig.Fuel_T1 already declares Effect = { Type = "FuelEfficiency", Multiplier = 2 }, but TechEffectsDispatcher has no handler (warns + no-ops). Implement the handler so it writes a drain multiplier into TechTreeBuffs.FuelEfficiency (e.g. Multiplier = 2 means "twice as efficient" → drain × 0.5; the handler stores 0.5, or stores the raw multiplier and TrainFuelManager inverts — pick one and document). The perk's party FuelEfficiencyBonus and the Tech Tree's FuelEfficiency then stack multiplicatively, never silently overriding each other.

Data flow​

  • Damage: player attacks → WeaponServer computes base → scaledDamage(player, base) reads PerkBuffs/<UserId>.DamageBonus → CombatService applies the scaled figure. Mid-combat allocate/respec changes the attribute; the next swing/shot reads the new value (no caching).
  • Coins: any earner → CoinManager.AddCoins scales by CoinGainBonus → clamp + replicate.
  • Fuel: dispatcher republishes PartyPerkBuffs.FuelEfficiencyBonus (party max) and/or a Tech node sets TechTreeBuffs.FuelEfficiency → TrainFuelManager re-snapshots → TrainStateSync broadcasts the new rate → clients re-extrapolate the bar.

Edge cases & anti-exploit​

  • All hooks are server-side reads of replicated buff attributes the server itself wrote; clients cannot forge them.
  • Coin rounding: scaling uses math.max(1, math.floor(...)) so a legitimate ≥1 reward never rounds to 0, and fractional coins never accrue.
  • Damage stacking with headshots: DamageBonus multiplies the post-headshot figure so the two multipliers compose predictably; document the order in the helper.
  • Fuel can't reach zero drain: (1 − FuelEfficiencyBonus) is floored (≥0.1) so max perk + max Tech node still drains slowly — no infinite runs.
  • Fuel mid-run correctness: because fuel is algebraic, the buff change must re-snapshot or clients would extrapolate the old rate indefinitely; the attribute-changed subscription is load-bearing, not cosmetic.
  • Party fuel resolution on leave: the highest-level holder leaving lowers FuelEfficiencyBonus (Spec 1 dispatcher recomputes); TrainFuelManager's subscription re-snapshots upward (faster drain) automatically.
  • No attacking player (NPC/environment damage): scaledDamage is only applied on the player-attack paths; NPC and hazard damage is unaffected.

Deferred — Weapon material cost reduction​

WeaponConfig defines weapons as Tools with combat stats only; there is no weapon crafting/purchase/material-cost path anywhere in the codebase. The WeaponCost perk (WeaponCostReduction, Party) therefore has no consumer and is intentionally left declared-but-unwired in PerkConfig — identical to how Spec 1 declares all not-yet-wired perks and how the Tech Tree declared FuelEfficiency ahead of its mechanic. When a weapon-crafting-cost system is designed, its cost calculation reads PartyPerkBuffs.WeaponCostReduction and applies cost * (1 − bonus) (rounded up, floored at 1). That is a single line in the future system; no perk-side work remains.

Out of scope (this spec)​

  • Building a weapon crafting/cost system (the host for WeaponCostReduction).
  • Any new perks, packets, GUI, or persistence (all in Spec 1).
  • Coin earner modules themselves (challenges, session rewards) — only the central multiplier in AddCoins; earners are wired independently and inherit the bonus for free.
