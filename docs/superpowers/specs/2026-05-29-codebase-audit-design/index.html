Codebase Audit — Design / Charter

Date: 2026-05-29 Status: Approved (design) Type: Audit charter (not a feature spec)

Purpose​

Audit the first-party gameplay code of Endless Journey for correctness/hallucinations (top priority), dangerous exploits, performance/algorithm issues, and design-consistency drift. Produce a prioritized findings report; afterward, turn the high-priority findings into an implementation plan to fix.

This document is the audit charter: it fixes scope, methodology, severity rubric, and the report format before the investigation begins, so coverage is agreed and the report has a predictable shape. It does not itself contain findings.

Deliverable & two-phase flow​

  • Phase 1 — Audit → report. Run the audit per the methodology below and write a findings report to docs/audits/2026-05-29-codebase-audit-findings.md. No code is changed in this phase. The report is grouped by system; each finding carries ID, severity, category, file:line, what/why, suggested fix, and a confidence tag.
  • Phase 2 — Fix plan. Select the findings worth fixing and invoke the writing-plans skill to produce the implementation plan for those fixes. The writing-plans cycle is reserved for the fixes themselves, because they cannot be planned until findings exist.

Methodology (correctness-first)​

For each system, hold both ends of every value in view and trace producer → consumer, targeting the seams where hallucinations live:

  • Attribute set/read pairs — every attribute a reader expects is actually written somewhere, with a matching name and type.
  • Packet field shape — field names, order, and types match on the send and receive sides of each Packet.
  • Signal producer/consumer — every :Connect has a corresponding :Fire, and argument shapes match.
  • Config keys — every Config.X.Y reference resolves to a key that exists in the config module.
  • Instance / tag references — WaitForChild / FindFirstChild / CollectionService tag lookups resolve to things the game actually contains.

Verification aids:

  • Studio MCP (read-only): verify instance / tag / attribute references against the live game tree. Tree-structure inspection only — no object modification, no playtesting.
  • Context7: verify suspicious or possibly-deprecated Roblox engine API calls against current documentation.

On the same read, note exploits, performance, and consistency issues.

Categories​

  1. Correctness / Hallucination (top priority) — references to APIs/instances/attributes/ config keys that don't exist, deprecated engine calls, logic that can't work as written, dead or contradictory paths.
  2. Exploit — client-authority gaps, missing/weak server validation, spoofable requests, race conditions, trust of client-supplied instances/attributes, remote spam.
  3. Performance — per-frame allocations, O(n²) loops, redundant raycasts/queries, unbounded growth, pooling misuse, work that could be cached or batched.
  4. Consistency — patterns applied unevenly across systems (Packets vs raw remotes, Signals usage, config vs hardcoded values, error handling, naming), drift from the documented architecture.

Severity rubric​

  • Critical — exploitable for unfair advantage / economy break, or breaks a core loop for all players.
  • High — feature-breaking bug under normal play, or a hallucination that throws at runtime.
  • Medium — degraded behavior, performance issue under load, or an inconsistency that invites future bugs.
  • Low — dead code, micro-optimization, cosmetic inconsistency.

Confidence tagging​

Because this is static analysis, each finding is tagged:

  • Confirmed — substantiated from the code alone.
  • Suspected (needs Studio/runtime check) — plausible from the code but depends on the live game tree or runtime behavior to confirm.

A finding is never asserted as a real bug without substantiation; uncertainty is surfaced explicitly.

Report format (Phase 1 output)​

docs/audits/2026-05-29-codebase-audit-findings.md, structured as:

  1. Summary — counts by severity and category; the headline issues.

  2. Findings by system — one section per in-scope system, each finding as:

    ### [ID] Title
    - Severity: Critical | High | Medium | Low
    - Category: Correctness | Exploit | Performance | Consistency
    - Location: file:line (clickable)
    - Confidence: Confirmed | Suspected (needs check)
    - What: ...
    - Why it matters: ...
    - Suggested fix: ...

  3. Cross-cutting observations — patterns spanning multiple systems.

  4. Suggested fix priority — the shortlist proposed for the Phase 2 writing-plans cycle.

Out of scope for this charter​

  • Actual code changes (Phase 2 / writing-plans).
  • Auditing vendored library internals.
  • Runtime playtesting and Studio object modification.
