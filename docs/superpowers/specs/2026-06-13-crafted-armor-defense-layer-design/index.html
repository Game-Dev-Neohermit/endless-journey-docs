Crafted Armor — Defense Layer & Perk Rework

Date: 2026-06-13 Status: Approved for planning Game: Endless Journey (Roblox / Rojo / Luau) Relationship: Realizes the "Future extension" note in 2026-06-12-perk-player-armor-design.md (Spec 3). Re-points the Armor perk from a standalone reduction to an armor-efficiency multiplier.

Summary​

Introduce a server-authoritative armor tier per player. Each tier provides a base % incoming-damage reduction, defined in config. The existing Armor perk is repurposed from a standalone reduction into an efficiency multiplier on that base. Final mitigation at the single server-side damage chokepoint becomes:

effectiveReduction = clamp(armorBaseReduction * (1 + armorEfficiency), 0, 0.75)
amount = amount * (1 - effectiveReduction)

With no armor (tier 0 -> base 0), the perk contributes nothing — this is the locked, intended behavior: the perk amplifies crafted armor rather than standing alone.

This spec is the defense layer only. The workbench crafting interaction (UI, recipes, material costs) is a separate follow-up spec; it will drive this layer via the ArmorManager.SetTier seam.

Decisions (locked)​

TopicDecision
Armor mechanicFlat % incoming-damage reduction, same mechanic as the existing perk.
Perk relationshipPerk amplifies armor: effectiveReduction = armorBase * (1 + perkEfficiency). Perk does nothing with no armor equipped.
Armor item modelSingle, durable, tiered piece. Tier is the persisted unit; base reduction derives from config. No durability decay.
IntegrationAttribute-published (Approach A). ArmorManager publishes a server-written attribute; HealthManager reads armor + perk per hit, multiplies, clamps at the sink.
Safety capHard-clamp total reduction to 0.75 (same cap as Spec 3) so stacking can never reach immunity.
Live updatesRead per damage event (no caching); crafting a tier / respeccing the perk applies on the next hit.

Architecture​

ReplicatedStorage/SharedModules/Configs/ArmorConfig.luau   (new) -- tier table + cap
ServerStorage/SharedModules/ArmorManager.luau              (new) -- tier state, persistence, publish, SetTier seam
ServerStorage/SharedModules/HealthManager.luau             (edit) -- armor * perk at the damage sink
ReplicatedStorage/SharedModules/Configs/PerkConfig.luau    (edit) -- Armor perk -> efficiency multiplier
ServerStorage/SharedModules/ProfileStore.luau (profile template) (edit) -- add ArmorTier field
ReplicatedStorage/ArmorState/<UserId>.ArmorBaseReduction   (new runtime folder, parallel to PerkBuffs)

ArmorState is a new ReplicatedStorage folder created at boot, parallel to PerkBuffs. Armor is not a perk, so it gets its own folder rather than being mixed into PerkBuffs.

Components & responsibilities​

ArmorConfig.luau (new)​

Single tuning surface for armor (project tune-here convention). Declares the tier table and the cap. Tier names and values below are placeholders to tune:

ArmorConfig.MaxReductionCap = 0.75          -- same hard cap as Spec 3
ArmorConfig.Tiers = {
    [0] = { BaseReduction = 0.00, DisplayName = "Unarmored" },
    [1] = { BaseReduction = 0.10, DisplayName = "Scrap Plate" },
    [2] = { BaseReduction = 0.18, DisplayName = "Riveted Mail" },
    [3] = { BaseReduction = 0.25, DisplayName = "Reinforced Rig" },
}

Tier is the persisted unit; base reduction is always derived from config, so retuning a tier retroactively updates every player holding it.

ArmorManager.luau (new, ServerStorage/SharedModules)​

Mirrors PerkManager's shape and lifecycle. Responsibilities:

  • On player load: read ArmorTier from the player's ProfileStore profile (default 0), publish ArmorState/<UserId>.ArmorBaseReduction = ArmorConfig.Tiers[tier].BaseReduction.
  • ArmorManager.SetTier(player, tier) — validates the tier exists in config, writes it to the profile, republishes the attribute. This is the public seam the future workbench-crafting spec calls.
  • ArmorManager.GetTier(player) / GetBaseReduction(player) — reads for HUD or other systems.
  • Cleanup on PlayerRemoving using a Janitor (project cleanup primitive); creates the ArmorState folder once at boot.

ProfileStore.luau profile template (edit)​

Add ArmorTier: number (default 0) to the player profile data template. Absent field reads as the default, so no migration is required for existing profiles.

PerkConfig.luau (edit) — Armor perk rework​

The Armor perk entry changes meaning:

  • BuffKey: "ArmorReduction" -> "ArmorEfficiency" (clarifies it is now a multiplier, not a direct fraction).
  • Description: "-%d%% incoming damage" -> "+%d%% armor effectiveness".
  • PerLevel: keep 0.025 or retune against the tier values (at L10 = +25% effectiveness; e.g. Tier 3's 0.25 base -> 0.3125 effective).

PerkEffectsDispatcher publishes whatever BuffKey is declared, so the rename auto-publishes PerkBuffs/<UserId>.ArmorEfficiency with no dispatcher edit.

HealthManager.luau (edit) — integration at the sink​

Replace the current Spec 3 block (HealthManager.luau:139-140):

-- Crafted armor (base) scaled by the Armor perk (efficiency), clamped at the sink.
local armorState = ReplicatedStorage:FindFirstChild("ArmorState")
local holder = armorState and armorState:FindFirstChild(tostring(player.UserId))
local armorBase = holder and (holder:GetAttribute("ArmorBaseReduction") :: number?) or 0
local efficiency = perkBonus(player, "ArmorEfficiency")
local reduction = math.clamp(armorBase * (1 + efficiency), 0, ArmorConfig.MaxReductionCap)
amount = amount * (1 - reduction)

Requires ArmorConfig at the top of HealthManager. Still a single multiply at the one damage sink that covers Melee / Bullet / AOE / environment.

Data flow​

  1. Player joins -> ArmorManager reads ArmorTier from profile -> publishes ArmorState/<UserId>.ArmorBaseReduction.
  2. (Future crafting spec) player crafts/upgrades at the workbench -> calls ArmorManager.SetTier(player, tier) -> profile updated, attribute republished.
  3. Perk allocation/respec -> PerkEffectsDispatcher updates PerkBuffs/<UserId>.ArmorEfficiency.
  4. Any damage -> HealthManager.ApplyDamage -> applyDamageInternal reads ArmorBaseReduction and ArmorEfficiency, multiplies, clamps to MaxReductionCap, scales amount -> health subtracted and synced.

Edge cases & anti-exploit​

  • Server-side reads of server-written attributes — both ArmorBaseReduction and ArmorEfficiency are unforgeable by clients.
  • No armor / tier 0: armorBase = 0 -> reduction is 0 regardless of perk level (locked behavior).
  • Cap: math.clamp(..., 0, MaxReductionCap) guards against config typos or future stacking reaching immunity.
  • Invalid tier in SetTier: rejected against ArmorConfig.Tiers; profile is never written with an unknown tier.
  • Missing ArmorState holder (race on join before publish): FindFirstChild returns nil -> armorBase = 0; the next hit after publish reflects the real value.
  • Order vs attacker bonus: armor applies to the final post-attacker-bonus amount, so attacker DamageBonus and defender reduction multiply independently — unchanged from Spec 3.
  • Death still fires: mitigation only scales amount; existing health/Humanoid mirror and death handling are untouched.

Out of scope (this spec)​

  • Workbench crafting interaction, recipes, material costs.
  • Equip/visual armor model on the avatar.
  • Durability / decay / repair.
  • HUD armor readout (a HUD spec can read ArmorState).
  • Per-damage-type resistances (all types share one reduction).
  • Any new packets (the crafting/HUD specs add networking as needed).

Testing​

No automated suite (project convention). Verify in Studio: call ArmorManager.SetTier(player, n) from the command bar (or a temporary dev command), confirm ArmorState/<UserId>.ArmorBaseReduction updates, allocate the Armor perk, and confirm applied damage reflects armorBase * (1 + efficiency) clamped at 0.75 across attack types. Confirm tier 0 with a leveled perk yields zero reduction.
