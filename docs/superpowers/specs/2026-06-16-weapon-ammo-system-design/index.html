Weapon Ammo & Consumable Throwables — Design

Date: 2026-06-16 Status: Approved (pending spec review) Scope: Add an inventory-backed ammo system for guns, make C4/grenades consumable (deleted from the backpack on use), and expose a clean ammo/throwable read API for the GUI.

Problem​

Today, ranged weapons have a per-gun magazine/reserve model (WeaponState tracks { mag, reserve }, server gates fire on mag > 0, reload pulls from reserve), but the reserve refills to ReserveMax on every equip and is never tied to anything the player earns or spends — so ammo is effectively infinite. Throwables are worse: Grenade.CarryCount and C4.CarryCount exist in WeaponConfig but are never enforced — onThrowProjectile only gates on a cooldown, so a player can throw unlimited grenades and C4.

We want ammo to be a real, consumable inventory resource that guns draw from, and we want throwables to be consumed from the backpack on use.

Decisions (locked during brainstorming)​

QuestionDecision
Ammo representationNumeric ammo pool per player, owned by a server AmmoManager (mirrors CoinManager). Not physical Tools.
Ammo granularityPer ammo-type (Light, Heavy, Rocket), each gun maps to a type.
Mag vs poolKeep the magazine (per-gun loaded rounds); the shared pool replaces per-gun ReserveMax. Reload pulls from the pool.
PersistenceSession-only / in-memory. No ProfileStore. Reseeded per life.
Throwable model1 Tool = 1 throw. Throwing destroys the Tool. (CarryCount removed; design must not preclude a future Tool-stacking inventory.)
AcquisitionCrafted at the workbench. Ammo + throwable recipes under the existing "ammo" category.
GUIExpose current/max ammo and throwable counts via a client AmmoApi + reactive signals.

Architecture​

A new AmmoManager (ServerStorage/SharedModules) owns per-player, per-ammo-type numeric counts in memory, mirroring the CoinManager pattern. Guns keep their magazine (loaded rounds) in WeaponState; the shared pool is keyed by ammo type and lives entirely in AmmoManager. Reload moves rounds pool → mag. Throwables remain physical Tool instances, consumed (destroyed) server-side on throw. Ammo and throwables are granted by crafting via CraftOutputDispatcher. A client AmmoApi is the single read surface for the HUD, kept current by sync packets and backpack changes.

Alternative considered and rejected: folding the pool into WeaponState (reserve becomes a type-keyed pool). WeaponState is per-weapon and per-life; a shared, crafted resource belongs in its own manager that mirrors CoinManager and that CraftOutputDispatcher can grant into cleanly.

Components​

1. Data model & config​

New Configs/AmmoConfig.luau:

  • AmmoTypes: id -> { DisplayName: string, Capacity: number, Starting: number }. Initial set:
    • Light — Pistol, SMG, AR
    • Heavy — SR
    • Rocket — RocketLauncher Capacity is the pool cap (the GUI's "max" for the pool); Starting is the per-life seed.
  • WeaponAmmo: gunToolName -> ammoTypeId (or, equivalently, an AmmoType field added to each gun entry in WeaponConfig). One source of truth; do not duplicate.

WeaponConfig gun entries: add AmmoType: string. Remove ReserveMax (pool capacity now lives in AmmoConfig). MagazineSize and ReloadTime stay. WeaponTypes.GunWeaponConfig updated to match (AmmoType: string, drop ReserveMax).

AmmoManager (ServerStorage/SharedModules), mirrors CoinManager:

  • GetAmmo(player, ammoType): number — 0 if unknown.
  • AddAmmo(player, ammoType, amount) — no-op on amount <= 0; clamps to Capacity; fires sync.
  • ConsumeAmmo(player, ammoType, amount): boolean — atomic spend; false with no mutation on amount <= 0 or insufficient.
  • EnsureStarting(player) — seed each type's Starting once per life (called on CharacterAdded).
  • Initialize() — wires per-player lifecycle; clears state on PlayerRemoving; every successful mutation fires AmmoPoolSync(ammoTypeId, amount) to the owning client.

2. Gun firing & reload flow​

  • Fire (WeaponServer.onFireWeapon): unchanged ammo behavior except the source. Firing drains the per-gun magazine in WeaponState; mag <= 0 rejects the shot (dry). The pool is not touched on fire.
  • Reload (WeaponServer.onReloadWeapon): on reload completion compute take = min(MagazineSize - mag, AmmoManager.GetAmmo(player, ammoType)), then AmmoManager.ConsumeAmmo(player, ammoType, take) and mag += take. If the pool is empty (take == 0), reload is a no-op (returns false). WeaponValidation.ammoAfterReload is reworked to (mag, poolAvailable, magSize) -> (newMag, taken).
  • WeaponState: AmmoEntry drops reserve, becoming { mag, reloadEndsAt }. EnsureAmmo seeds only mag = MagazineSize. GetAmmo/SetAmmo reduce to mag-only (rename to GetMag/SetMag for clarity).
  • Sync packets: replace WeaponAmmoSync(weaponName, mag, reserve) with:
    • WeaponMagSync(weaponName, mag) — per-gun loaded rounds.
    • AmmoPoolSync(ammoTypeId, amount) — per-type pool (capacity is static config, not sent).
  • Client (GunHandler): local prediction keeps mag per gun; pool is read from the AmmoApi cache. Reload predicts the same take math and is reconciled by the two sync packets. Dry-fire SFX behavior unchanged.

3. Throwables (Grenade & C4)​

  • Consumption (WeaponServer.onThrowProjectile): after a validated throw, destroy the equipped throwable Tool (1 Tool = 1 throw). Keep the cooldown gate (relevant when the player holds several). Spawn / fuse / stick logic unchanged. CarryCount removed from config.
  • C4 detonation decoupling: detonation moves off the per-Tool G binding (in WeaponController) into an always-listening client path that fires ReqDetonate on G regardless of the equipped Tool. The server already no-ops onDetonate when the player has no active charges. This lets a player throw their last C4 (Tool destroyed) and still detonate. MaxActive still caps simultaneously-stuck charges.
  • Throwable counts for GUI: derived from Tool instances in Backpack + Character by ToolName (same pattern as WorkbenchService.countMaterial). Exposed via AmmoApi.GetThrowableCount(toolName) and a Signals.ThrowableCountChanged(toolName, count) fired on backpack add/remove.

4. GUI API​

Client module AmmoApi (ReplicatedStorage/SharedModules) is the single read surface for the HUD; the GUI never talks to the server directly.

  • GetMag(weaponName): (mag, magSize)
  • GetPool(ammoType): (amount, capacity)
  • GetEquippedAmmo(): (mag, magSize, poolAmount, poolCapacity)? — convenience for the active gun
  • GetThrowableCount(toolName): (count)

Reactive signals (no polling):

  • Signals.WeaponMagChanged(weaponName, mag)
  • Signals.AmmoPoolChanged(ammoType, amount)
  • Signals.ThrowableCountChanged(toolName, count)

AmmoApi maintains its client cache by listening to WeaponMagSync / AmmoPoolSync and to backpack ChildAdded/ChildRemoved.

5. Crafting integration​

  • New Output kind in WorkbenchConfig: { Kind = "Ammo", AmmoType: string, Amount: number }. CraftOutputDispatcher.isFeasible validates the ammo type exists in AmmoConfig; grant calls AmmoManager.AddAmmo.
  • Throwables crafted via the existing Weapon output ({ Kind = "Weapon", ToolName = "Grenade" }), cloning the Tool from WeaponTemplates. Optional Count field on the Weapon output to grant a batch (e.g. 3 grenades per craft); default 1.
  • Add real recipes under the existing "ammo" category: Light/Heavy/Rocket ammo bundles, plus Grenade and C4. (Grenade/C4 Tool templates must exist in ServerStorage/WeaponTemplates.)

Data flow​

Craft ammo:   ReqCraft → WorkbenchService → CraftOutputDispatcher.grant
                       → AmmoManager.AddAmmo → AmmoPoolSync → AmmoApi → Signals.AmmoPoolChanged → HUD

Fire gun:     ReqFireWeapon → WeaponServer (drains WeaponState mag) → WeaponMagSync
                            → AmmoApi → Signals.WeaponMagChanged → HUD

Reload gun:   ReqReloadWeapon → WeaponServer (pool→mag via AmmoManager.ConsumeAmmo)
                              → WeaponMagSync + AmmoPoolSync → HUD

Throw:        ReqThrowProjectile → WeaponServer (spawn + destroy equipped Tool)
                                 → backpack ChildRemoved → AmmoApi → Signals.ThrowableCountChanged → HUD

Detonate C4:  G (always-on client) → ReqDetonate → WeaponServer.onDetonate (no-op if no actives)

Edge cases​

  • Empty pool + empty mag: fire rejected with dry SFX (existing); reload no-ops.
  • Death/respawn: pool reset and reseeded via AmmoManager.EnsureStarting; mag reseeded by EnsureAmmo; thrown Tools gone with the old backpack.
  • Player leaving mid-reload: retain the existing player.Parent == nil guard in the reload task.delay; AmmoManager clears on PlayerRemoving.
  • Throwing the last Tool: equipped Tool destroyed → character has no equipped Tool; player re-selects from the hotbar (acceptable; auto-equip-next is a possible later enhancement).

Testing (Studio, manual — no automated suite)​

  • Fire until mag empty → dry SFX; reload with pool > 0 refills mag and decrements pool; reload with empty pool no-ops.
  • Pool reads correct per ammo type; AR/SMG/Pistol share Light; SR uses Heavy; rocket uses Rocket.
  • Craft ammo at the workbench → pool increases (clamped at Capacity), HUD updates.
  • Throw a grenade → Tool removed from backpack; throwing the last grenade leaves no equipped Tool.
  • Throw C4, switch away / throw last C4, press G → charges detonate.
  • AmmoApi getters and signals return correct values for HUD wiring.

Out of scope​

  • ProfileStore persistence of the ammo pool (session-only by decision).
  • World / pickup ammo sources (crafting only this iteration).
  • The future Tool-stacking inventory (design avoids blocking it; throwables stay 1 Tool = 1 throw).
  • The actual HUD visuals — only the AmmoApi + signals are in scope.
