Prompt-Part Resolver — Depth-Agnostic Prompt Lookup

Date: 2026-06-18 Status: Approved for planning Game: Endless Journey (Roblox / Rojo / Luau) Trigger: Restructuring train props into Models with a PrimaryPart broke client-side prompt wiring; investigation surfaced a client/server divergence affecting five controllers.

Summary​

Client controllers and the server locate interaction prompts (a named BasePart hosting a ProximityPrompt, e.g. ProxPromptPart) differently. The server searches the tagged object recursively; the client requires the part as a direct child. When the props were wrapped into Models with a PrimaryPart, the part became a deeper descendant — the server still found it, the client did not. The client WaitForChild then timed out 10s per object, never wired the prompt's Triggered handler, and refuel / brake / shield interactions silently stopped working. This is the cause of the Studio warnings:

[TrainClient] Engine 'TrainEnginePlaceholder' missing ProxPromptPart/ProximityPrompt — skipping.
[TrainShieldController] Console 'TrainShieldGeneratorPlaceholder' missing ProxPromptPart/ProximityPrompt — skipping.
[TrainClient] Lever 'Brake' missing ProxPromptPart/ProximityPrompt — skipping.
[TrainClient] Lever 'CollisionBox' missing ProxPromptPart/ProximityPrompt — skipping.

The fix introduces one shared resolver — PromptResolver in ReplicatedStorage/SharedModules — that finds the prompt part recursively (depth-agnostic) and, on the client, waits for replication. Both the client controllers and the server's ProximityValidation route through it, so the two sides can never disagree about where a prompt lives again. The same direct-child trap exists in three further controllers (Tech Tree, Workbench, Cannon); all five are converged onto the resolver in this change.

Component: PromptResolver (the single unit of behavior)​

A --!strict module with a moonwave --[=[ @class PromptResolver ]=] doc-comment. Two pure functions, depending only on the passed root + name (no globals, no side effects):

  • FindPart(root, partName, timeout?) -> BasePart? — recursive root:FindFirstChild(partName, true), validated IsA("BasePart"). timeout nil/0 → one synchronous check, no yield. timeout > 0 → poll via task.wait() until found or os.clock() deadline. This reproduces WaitForChild's replication-wait, which has no recursive built-in equivalent.
  • Find(root, partName, timeout?) -> (BasePart?, ProximityPrompt?) — builds on the same recursive search, then part:FindFirstChildWhichIsA("ProximityPrompt"). Returns (nil, nil) if either is missing within the timeout.

Why it can be understood in isolation: input is an instance + a name + an optional wait budget; output is the part (and prompt). Server calls it with no timeout (synchronous, exactly today's behavior); client calls it with a 10s timeout (exactly today's behavior). Neither caller needs to know the other exists.

Call-site integration​

  • Train engine / lever, shield console, tech bench, workbench station — these consume an authored prompt: call Find(root, name, 10), keep each controller's existing warn + early-return on nil.
  • Cannon — attachPrompt creates the prompt at runtime, so it calls FindPart(model, name) for the host part only and keeps its duplicate-guard (FindFirstChildOfClass) and Instance.new("ProximityPrompt") logic.

Error handling​

  • Missing part/prompt within the timeout → resolver returns nil (or nil, nil); callers keep their current warning and skip wiring (no crash, no half-wired prompt).
  • A tagged object with no prompt (e.g. CollisionBox until the tag is removed) still warns once after the timeout — acceptable and self-correcting once the stray tag is gone.

Testing / verification​

No automated suite (per project convention); verification is in Studio after a Rojo sync:

  1. With the stray CollisionBox tag removed, the four load warnings disappear.
  2. Engine refuel adds fuel; brake lever toggles and its ActionText flips Stop/Resume; shield console recharges with SFX.
  3. Tech bench and workbench prompts still open their GUIs; placed cannons still receive a mount prompt and mount.
  4. No new warnings from any of the five controllers.

Out of scope​

  • The CollisionBox stray TrainBrakeLever tag (authoring fix in Studio).
  • Cannon's server-side validation (unchanged; only the client part lookup is made recursive).
  • Any change to prompt visuals, ranges, or interaction behavior.
