Janitor Cleanup Adoption — Design

Date: 2026-06-01 Status: Approved (design); plan pending

Problem​

The codebase has no shared cleanup primitive. Lifecycle teardown is hand-rolled with { RBXScriptConnection } arrays plus manual disconnect/clear loops, and the same pattern is duplicated across at least four files:

local characterConnections: { RBXScriptConnection } = {}
local function cleanup()
    for _, conn in characterConnections do conn:Disconnect() end
    table.clear(characterConnections)
end

This duplication is error-prone, and two latent bugs already exist because of it:

  • ProximityPickupController per-item leak — a per-item AncestryChanged connection (ProximityPickupController.client.luau:62) is never explicitly disconnected, and two parallel tables (trackedItems, hoverHandles) must be kept in sync by hand.
  • ShredderClient Backpack-rebind leak — bindBackpack (ShredderClient.client.luau:245) connects ChildAdded/ChildRemoved on every Backpack that appears but never disconnects the connections bound to the previous (destroyed) Backpack. The Backpack is replaced on every character load, so connections accumulate.

Janitor (the Validark/howmanysmall library) is already present in the tree transitively — vendored as Zone/Janitor.lua — but it is not used as a first-class project pattern. (A Maid previously lived in SmoothShiftLock/Dependencies/, but that whole module was removed by the 2026-06-01 camera consolidation, so Zone/Janitor.lua is now the only transitive copy.)

Goals​

  • Adopt one cleanup primitive as the standard project pattern.
  • Migrate the existing hand-rolled connection-tracking sites to it.
  • Fix the two latent leaks as part of the migration.
  • Document the pattern so new/touched code uses it.

Non-goals (YAGNI)​

  • No project convenience wrapper around Janitor — use it directly.
  • No migration of singleton top-level controller connections that live for the whole session (e.g. SprintController's permanent :Connects) — they never churn, so a Janitor adds nothing.
  • No changes to vendored packages (Zone, PartySystem, Satchel).
  • No LinkToInstance usage unless a specific site clearly benefits.
  • Do not consolidate Zone's private Zone/Janitor.lua — it stays as Zone's internal dependency.
  • CameraController is not a target. The 2026-06-01 camera consolidation unified the third-person and aim cameras into CameraController.client.luau. It was evaluated and deliberately excluded: every connection in it is a singleton session-lifetime wiring (CharacterAdded/CharacterRemoving, the Signals connections, the ContextActionService bind, the render-step binding), and its one per-character resource — the MotionMaster offsetSpring — is already explicitly :Destroy()-ed on CharacterRemoving. A Janitor would add nothing.

Dependency & wiring​

Add to [dependencies] in wally.toml (shared realm, alongside TweenPlus):

Janitor = "howmanysmall/janitor@1.18.3"

Then:

wally install
wally-package-types --sourcemap sourcemap.json Packages/

wally-package-types is required so the --!strict files type-check against Janitor's exported types. Janitor resolves to ReplicatedStorage.Packages.Janitor, reachable from both client and server.

The standard pattern​

Use raw Janitor directly. One Janitor owns one lifecycle scope.

local Janitor = require(ReplicatedStorage.Packages.Janitor)

local janitor = Janitor.new()
janitor:Add(someInstance.Event:Connect(fn), "Disconnect")  -- connection
janitor:Add(hoverHandle, "Stop")                            -- arbitrary method
janitor:Add(somePart, "Destroy")                            -- instance
janitor:Cleanup()  -- tear everything down, Janitor reusable afterwards
janitor:Destroy()  -- tear down and discard the Janitor

For keyed collections, each entry owns its own Janitor.new(). The map shape changes from { [key]: { Connections = { RBXScriptConnection } } } to { [key]: Janitor }. Unregistering an entry calls that entry's janitor:Destroy() and removes the key.

Migration targets​

Each target is mechanical and independently verifiable in Studio.

1. PlaceableActions (PlaceableActions.luau:90-152) — cleanest first​

  • Replace per-binding buttonConnections array + ancestryConnection with one Janitor owned by the binding.
  • disconnectButtons() semantics: button listeners and the ancestry listener go into the binding's Janitor; Unbind() becomes janitor:Destroy().
  • Preserve the existing subtlety: on model destruction the button listeners are disconnected but explicitUnbind is NOT set, so an in-flight handler can still fire its success signal. Keep inFlight/explicitUnbind/buttonsDisabled flags as they are; only the connection storage moves to the Janitor.

2. ProximityPickupController (ProximityPickupController.client.luau:19-106)​

  • Per-item Janitor holding the AncestryChanged connection (fixes the leak) and the hover handle (janitor:Add(hoverHandle, "Stop")).
  • Collapse the two parallel tables (trackedItems, hoverHandles) — the item's state lives in a single map of { [itemId]: { handle, janitor } } (or equivalent). On claim/destroy, janitor:Destroy() replaces the manual stopHoverEffect + table-nil dance.

3. ShredderClient (ShredderClient.client.luau:227-404)​

  • WorkbenchEntry.Connections array → per-workbench Janitor; unregisterWorkbench calls janitor:Destroy().
  • characterConnections array → a character-scope Janitor; bindCharacter cleans the previous one before rebinding.
  • Fix the bindBackpack leak: hold each Backpack's ChildAdded/ChildRemoved connections in a per-Backpack Janitor and clean the previous Backpack's Janitor when a new Backpack appears.

4. PlacementClient (PlacementClient.client.luau:65-68, 312-360)​

  • characterConnections + heartbeatConnection + clickConnection → one Janitor.
  • cleanupConnections() → janitor:Cleanup() (Janitor reused across character spawns).

5. TrainClient (TrainClient.client.luau:137-200)​

  • LeverEntry/EngineEntry connection fields → a per-entry Janitor.
  • Unregister loops → janitor:Destroy() per entry.

Documentation​

  • CLAUDE.md — add a "Cleanup / lifecycle" bullet to the cross-cutting modules section: any scope that owns connections or instances must use Janitor (ReplicatedStorage.Packages.Janitor); never hand-roll { RBXScriptConnection } arrays or manual disconnect loops.
  • Project-Maintenance-Guide.md — add a short Janitor pattern note (the standard pattern above and the keyed-collection shape).

Verification​

Verification is in Studio per project convention (no rojo build or selene as explicit steps; user syncs live with Studio). Each migrated file is checked in isolation by exercising its feature:

  • PlaceableActions / PlacementClient: place, move, and stash a placeable; respawn.
  • ProximityPickup: spawn pickups, collect some, let others be destroyed; confirm hover stops and no orphaned effects after many cycles.
  • ShredderClient: register/unregister workbenches, respawn repeatedly, confirm prompt durations stay correct (Backpack rebind path).
  • TrainClient: register/unregister engines and levers; refuel; brake toggle.

Risks​

  • Behavioral subtlety in PlaceableActions — the in-flight success-signal path must survive the migration. Covered explicitly in target #1.
  • Type-checking — if wally-package-types is skipped, --!strict files will not see Janitor's types. Step is mandatory in the wiring section.
  • Migration churn — five files touched. Mitigated by migrating one file at a time, each independently verifiable.
