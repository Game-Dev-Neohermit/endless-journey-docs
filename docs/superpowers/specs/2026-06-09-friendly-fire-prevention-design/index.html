Friendly Fire Prevention — Design

Date: 2026-06-09 Status: Approved (design); implementation plan pending

Goal​

Eliminate friendly fire from combat damage:

  • Players cannot damage other players.
  • Players cannot damage friendly NPCs (e.g. the trader).
  • Enemy NPCs cannot damage other enemy NPCs.
  • Enemy NPCs cannot damage friendly NPCs.

Normal combat is preserved: players damage enemy NPCs, and enemy NPCs damage players.

Background / current state​

All weapon damage already funnels through a single server-side choke point, CombatService.ApplyToModel — melee, guns, and AOE all call it (directly, or via ApplyToPart / ApplyAOE). It carries source: Player? and resolves targets two ways:

  • a Player's character (via Players:GetPlayerFromCharacter) → routed to HealthManager.ApplyDamage (keeps the HUD-tracked record correct);
  • a Model tagged with the CollectionService tag "NPC" and owning a Humanoid → direct Humanoid:TakeDamage.

The "NPC" tag currently does double duty: it gates damageability in CombatService and places the model's parts in the Character collision group via NpcCollisionService so thrown charges pass through NPCs.

There is no faction / team concept anywhere yet, and NPCs do not deal damage yet (enemy AI is supplied elsewhere). Today the only source is a player.

Decisions​

These were settled during brainstorming:

  1. Faction tags replace the "NPC" tag. "EnemyNPC" and "FriendlyNPC" become the only NPC markers. Being either tag means "combatant" — i.e. collision pass-through (NpcCollisionService) and damageable (CombatService). No bare-"NPC" case needs to be supported.
  2. Friendly NPCs are invulnerable to all combat damage. Since players cannot hurt them and enemies cannot hurt them, nobody can — the natural reading of the requirements and the desired behavior for a shopkeeper.
  3. Self-damage is preserved. A player can still be hurt by their own explosives (governed by the existing per-weapon ignore list); they simply cannot hurt other players or friendly NPCs.

Approach (chosen: A)​

A shared Factions policy module plus a single allow/deny check at the existing CombatService choke point. One check covers melee, guns, and AOE because they all route through ApplyToModel. Rejected alternatives: inlining the policy in CombatService (no reuse, policy welded to plumbing), and filtering friendlies at query/raycast time per weapon (touches many paths, easy to reopen friendly fire).

Design​

1. Factions shared module​

New module at src/ReplicatedStorage/SharedModules/Factions.luau. Shared so the client can reuse resolve later (e.g. suppress hit-markers / aim-assist on friendlies); the server remains authoritative because the actual block lives in CombatService.

  • Faction type: export type Faction = "Player" | "Friendly" | "Enemy".

  • Tag-name constants (single source of truth, imported by NpcCollisionService and CombatService — no hardcoded tag strings elsewhere):

    • Factions.EnemyTag = "EnemyNPC"
    • Factions.FriendlyTag = "FriendlyNPC"
    • Factions.NpcTags = { Factions.EnemyTag, Factions.FriendlyTag } (for the collision watcher to iterate).

  • Factions.resolve(actor: (Player | Model)?): Faction?

    • nil → nil (environment / unknown).
    • a Player instance, or a Model that Players:GetPlayerFromCharacter resolves to a player → "Player".
    • a Model tagged EnemyTag → "Enemy".
    • a Model tagged FriendlyTag → "Friendly".
    • anything else → nil (not a combatant).

  • Factions.canDamage(attacker: Faction, target: Faction): boolean — a default-deny hostility table allowing only:

    • Player → Enemy
    • Enemy → Player

    Every other ordered pair is false. This single table yields all four rules: no player-vs-player, no enemy-vs-enemy, no enemy-vs-friendly, no player-vs-friendly (friendly NPCs undamageable). Extensible: adding a faction is one row/column.

2. CombatService check + signature change​

ApplyToModel's source: Player? parameter becomes attacker: (Player | Model)?. All current call sites pass a Player, so they are unchanged in behavior; the wider type lets a future NPC attacker pass its own model. Internally CombatService still derives the Player (when attacker is a player) to pass to HealthManager.ApplyDamage for HUD/kill-credit.

Check order inside ApplyToModel, before any damage is applied:

targetFaction = Factions.resolve(targetModel)
if not targetFaction then return false end          -- not a combatant

attackerFaction = Factions.resolve(attacker)
if attackerFaction
   and not isSelf(attacker, targetModel)
   and not Factions.canDamage(attackerFaction, targetFaction) then
       return false
end
-- ...existing routing: Player character → HealthManager, else Humanoid:TakeDamage
  • Self-exemption: isSelf is true when the target is the attacker's own character (attacker is a Player and targetModel == attacker.Character) or the attacker's own model (attacker is a Model and targetModel == attacker). When self, the faction check is skipped and the existing per-weapon ignore list governs whether self-damage lands — preserving self-damage from one's own AOE.
  • Environmental (attacker == nil → attackerFaction == nil): the check is bypassed and damage applies, preserving today's nil = environment semantics.
  • The damageable gate changes from CollectionService:HasTag(model, "NPC") to "Factions.resolve(targetModel) returned a non-nil faction".

3. Tag migration (replacing "NPC")​

  • NpcCollisionService watches both faction tags instead of "NPC", refactored to loop over Factions.NpcTags for the GetInstanceAddedSignal / GetInstanceRemovedSignal / GetTagged wiring. The per-model Janitor + DescendantAdded collision-group assignment is otherwise unchanged. (A model carries exactly one faction tag, so there is no double-watch concern.)
  • CombatService imports Factions and uses resolve for the damageable gate (see §2).
  • Existing "NPC"-tagged instances in the place file must be re-tagged EnemyNPC / FriendlyNPC (done in Studio; no bare-"NPC" support).

4. AOE​

No special-casing. ApplyAOE already calls ApplyToModel per target, so the faction check applies to every target in the blast radius automatically. A player's grenade in a mixed crowd damages enemies, skips other players and traders, and still self-damages the thrower when they are in range and not in the weapon's ignore list.

Non-goals​

  • NPC AI / how enemy NPCs decide to attack (supplied elsewhere). This design only ensures that when an NPC attacker routes through ApplyToModel, faction is enforced.
  • Environmental-hazard faction rules (fall damage, hazards) — nil attacker bypasses the check, as today.
  • PvP-enabled zones or team-based modes.
  • More than the three factions above (the table is extensible if needed later).

Testing​

Manual verification in Studio (no automated test suite in this project):

  1. Tag one dummy model EnemyNPC and one FriendlyNPC, each with a Humanoid.
  2. As a player, confirm melee / gun / grenade damages the enemy.
  3. Confirm the friendly NPC takes no damage from melee, gun, or grenade.
  4. With two players, confirm neither can damage the other (melee, gun, AOE).
  5. Confirm a player's own grenade still self-damages (weapon ignore empty).
  6. Confirm thrown charges still pass through both faction-tagged NPCs (collision migration intact).

Factions.canDamage is a pure table lookup, verifiable by inspection.
