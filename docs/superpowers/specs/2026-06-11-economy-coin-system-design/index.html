Economy / Coin System — Design

Date: 2026-06-11 Status: Approved (design) Scope: The coin wallet module only. Earning sources (gameplay-session completion, daily/weekly challenges) and any spend UI/shop are separate future systems that call this module's API.

Summary​

A server-authoritative coin wallet for "Endless Journey", persisted via ProfileStore so the balance is shared across the lobby and gameplay places. The module exposes a small earn/spend/read API; future earner systems (session-complete reward, daily/weekly challenges) and future sinks (shop) call into it. The design is a deliberate, file-for-file mirror of the shipped-and-verified XP/Level system, so it reads as a sibling to XPManager.

Decisions (from brainstorming)​

  • Storage: a separate PlayerCoins ProfileStore profile, isolated from the existing PlayerXP profile. Accepts a second session lock per player in exchange for a fully self-contained module matching the one-module-per-system pattern.
  • Module scope: wallet + reward API only. The economy module owns the balance, persistence, replication, and the AddCoins/DeductCoins/GetCoins API. Challenge tracking and session-completion logic are out of scope.
  • Spending: include a guarded, atomic DeductCoins now (insufficient-funds returns false), so the future shop inherits correct authority semantics.
  • Structure: Approach A — mirror XPManager exactly (single dedicated manager), with an optional reason/source string on AddCoins for server-side award logging.

Architecture & components​

Four new files mirror the XP system's layout:

FileRole
src/ServerStorage/SharedModules/CoinManager.luauServer authority. Owns the PlayerCoins ProfileStore lifecycle (one session/player, key = UserId), the wallet API, and per-player replication. Runs in both places.
src/ServerScriptService/CoinSystemLoader.server.luauEntry point. Calls CoinManager.Initialize() once. Place-agnostic (lobby + gameplay). No earners in scope.
src/ReplicatedStorage/SharedModules/Configs/CoinConfig.luauTuning: STORE_NAME, STARTING_BALANCE, MAX_BALANCE.
src/StarterPlayer/StarterPlayerScripts/CoinController.client.luauClient bridge. On CoinStateSync, re-fires Signals.OnCoinsChanged(balance) for a future HUD.

Data model & persistence​

Single-field ProfileStore template:

local PROFILE_TEMPLATE = { Coins = CoinConfig.STARTING_BALANCE }
  • STORE_NAME = "PlayerCoins", identical in every place of the universe, so the lobby and gameplay share one DataStore record.
  • ProfileStore session-locking serializes the lobby↔gameplay teleport handoff automatically.
  • Lifecycle is copied from XPManager verbatim (the verified idiom): StartSessionAsync with a Cancel guard (player.Parent ~= Players), AddUserId (GDPR), Reconcile (fill missing fields), OnSessionEnd → clear + kick, EndSession on PlayerRemoving, and the "player left before session started" branch that ends the session immediately.

Server API (server-authoritative)​

CoinManager.GetCoins(player): number              -- 0 if no profile loaded
CoinManager.AddCoins(player, amount, reason?)      -- reason: optional string, server log only
CoinManager.DeductCoins(player, amount): boolean   -- false if profile missing or insufficient funds
CoinManager.Initialize()                           -- wire profile lifecycle; call exactly once per server

Rules:

  • AddCoins / DeductCoins reject amount <= 0 (no-op / return false).
  • Balance is clamped to [0, CoinConfig.MAX_BALANCE].
  • DeductCoins is atomic: it checks Coins >= amount before subtracting and returns false with no mutation on insufficient funds — the contract a future shop relies on.
  • Every successful mutation calls replicate(player) to push the new balance to the owning client.
  • GetCoins with no loaded profile returns 0; AddCoins no-ops; DeductCoins returns false.
  • Future earners call AddCoins(player, amount, "DailyChallenge") etc. — those modules are out of scope.

Networking — Packets & Signals​

One new packet in src/ReplicatedStorage/SharedModules/Packets/init.luau, beside the XP packets:

-- Server → owning Client: authoritative coin balance. Sent on profile load and
-- on every balance change.
local CoinStateSync = Packet("CoinStateSync", Packet.NumberU32) -- balance
  • NumberU32 caps at ~4.29 B, above MAX_BALANCE.
  • No client→server packet — earning and spending are fully server-driven in this scope; a future shop adds its own purchase packet.
  • Add the entry to docs/reference/networking-map.md in the same commit (CLAUDE.md rule).

One new signal in src/ReplicatedStorage/SharedModules/Signals/init.luau:

OnCoinsChanged -- (balance: number) — client-side bus event for a future coin HUD

Config​

CoinConfig.STORE_NAME       = "PlayerCoins"   -- identical across places for cross-place sharing
CoinConfig.STARTING_BALANCE = 0
CoinConfig.MAX_BALANCE      = 1_000_000_000   -- clamp ceiling (< NumberU32 max)

No reward-amount constants here — those belong to the future earner modules (session/challenges), not the wallet.

Client feedback​

CoinController only re-fires Signals.OnCoinsChanged so a future HUD can bind to it — no toast in this scope. (XP earns silently and only toasts on level-up; a "+coins" toast belongs to whichever earner grants the coins, so it ships with the challenge/session systems.) This keeps the module a pure wallet.

Cross-place behavior​

CoinManager.Initialize() runs in lobby and gameplay. Same STORE_NAME + UserId key ⇒ shared record; session-locking serializes lobby↔gameplay teleports. A player sees the same balance in both places, and earns/spends persist regardless of where they occur.

Error handling​

  • Profile fails to load → kick: "Coin profile failed to load — please rejoin."
  • Session ends mid-play → clear from Profiles, kick.
  • API called with no loaded profile → GetCoins → 0, AddCoins → no-op, DeductCoins → false.

Verification (no automated test suite in this repo)​

In Studio:

  1. Fresh profile starts at STARTING_BALANCE.
  2. From the command bar, AddCoins / DeductCoins and confirm OnCoinsChanged fires with the correct balance.
  3. Insufficient DeductCoins returns false and does not mutate the balance.
  4. Balance clamps at 0 and MAX_BALANCE.
  5. Rejoin to confirm persistence.
  6. If feasible, teleport lobby↔gameplay to confirm the shared record and clean session handoff.

Out of scope (future work)​

  • Session-completion coin grant (separate earner module).
  • Daily / weekly challenge definitions, tracking, reset timers, claim/idempotency.
  • Shop / spend UI and its purchase packet.
  • Coin HUD that binds to OnCoinsChanged.
