Tech Tree & Weapons Documentation — Design Spec

Date: 2026-06-11 Status: Approved design, pending implementation plan Game: Endless Journey (Roblox / Rojo / Luau)

Summary​

Two shipped, Studio-verified systems — the Tech Tree and the Weapon System — have no page in the published Moonwave docs site. The site's "Systems" nav is auto-generated from docs/systems/ (.moonwave/sidebars.js), and neither system has a file there. This is a direct gap against the CLAUDE.md rule that a change touching a system must update its system page and the relevant reference map in the same commit.

This spec defines the two missing system pages plus the reference-map rows that were skipped for these systems, bringing the published docs in line with the current source.

The weapon packets/signals already in the maps reflect the post-redesign code (ReqThrowProjectile / ReqDetonate, ServerProjectile replicated physics, melee Combos, C4 as a Manual throwable). The new docs must describe that current shape, not the original 2026-06-06 spec.

Scope​

In scope:

  1. docs/systems/tech-tree.md — new system page.
  2. docs/systems/weapons.md — new system page (title "Weapons").
  3. docs/reference/networking-map.md — add the 4 Tech Tree packets.
  4. docs/reference/signals-map.md — add the 2 Tech Tree signals.
  5. docs/reference/config-map.md — add WeaponConfig and TechTreeConfig rows.

Out of scope:

  • A how-to playbook for either system (can follow later).
  • Re-auditing or editing the weapon networking-map / signals-map rows (already current).
  • Documenting the Economy (CoinConfig) / Progression (XPConfig) config-map gaps — separate systems, not this pass.
  • Any source-code change. This is documentation only; the docs describe code exactly as it currently exists. If a discrepancy between code and the original specs is found while writing, it is reported, not silently "fixed."

House style (both pages follow this)​

Derived from existing pages (train-fuel.md, shredder.md, health.md):

  • Frontmatter sidebar_position (next free integer in docs/systems/; today the detailed pages use 1–8 and Economy uses 99 — Tech Tree and Weapons take the next sequential positions among the gameplay systems, ahead of Economy's 99).
  • # Title + a 2–4 sentence intro describing the model in plain terms.
  • ## Data flow — an ASCII diagram with a Server column and a Client column, showing packet names on the arrows (matching train-fuel.md).
  • ## Client / Server / Shared — one bold-headed paragraph per module describing its responsibility.
  • ## Key files — bulleted list of src/... paths with one-line roles.
  • ## Config knobs — a | Field | Default | Effect | table sourced from the actual config module.
  • ## Gotchas — :::caution admonitions for sharp edges + prose notes for subtler ones.

All file references in the prose use the relative [text](../../src/...) form so they resolve both on the site and in-repo.

Page 1 — docs/systems/tech-tree.md​

Source of truth: TechTreeConfig.luau, TechTreeState.luau, TechTreeService.server.luau, TechEffectsDispatcher.server.luau, MaterialEjector.luau, TechTreeGuiController.client.luau, and the 2026-06-10 design spec.

Content to cover:

  • Intro: cooperative, server-wide, session-only (no DataStore) tech tree funded with crafted materials (Wood/Metal) pooled into nodes at one fixed bench. Always-open eligibility; auto-unlock when a node's full cost is met.
  • Data flow (ASCII, Server ↔ Client): Submit (ReqTechSubmit → validate proximity + TechTreeState.validateSubmit + held-tool count → consume Tools → pool delta or unlock → TechNodeUpdate broadcast), auto-unlock effect (OnNodeUnlocked → TechEffectsDispatcher), Cancel (ReqTechCancel → MaterialEjector.Eject ground-pile refund), Join snapshot (ReqTechSnapshot).
  • Client / Server / Shared: TechTreeState (pure shared validator — single rule source for client greying + server authorization), TechTreeService (owns unlocked / pools, packet handlers, Tool consumption), TechEffectsDispatcher (one wired StatBuff effect; unknown types warn + no-op so future nodes are declarable now), MaterialEjector (Shredder-style MotionMaster.SplineMove arc → ProximityPickupServer pile, pure mechanism), TechTreeGuiController (authored StarterGui.TechTreeGui, proximity-opens, repaints on OnTechTreeStateChanged).
  • Key files: the seven files above + Packets/Signals entries.
  • Config knobs table: BENCH_TAG, INTERACT_DISTANCE, INTERACT_DISTANCE_TOLERANCE, trajectory point names, PROMPT_PART_NAME, MATERIALS_FOLDER, DROPPED_FOLDER_NAME, refund-arc tuning (ARC_DURATION, ARC_HEIGHT_BOOST, LANDING_SCATTER_RADIUS, ITEM_EJECT_DELAY, MAX_ANIMATED_EJECT_ITEMS, DIRECT_GRANT_BATCH_SIZE, AUTO_COLLECT_DELAY), and the Nodes schema (Branch/Tier/Cost/Prereq/Effect).
  • Studio setup note: TechTreeBench-tagged Model w/ PrimaryPart, child TrajectoryPoints (SpawnPoint/LandingPoint), child TechPromptPart w/ a ProximityPrompt; ReplicatedStorage/CraftingMaterials holds Wood/Metal Tool templates (shared with the Shredder).
  • Gotchas: server-side proximity re-check (client GUI proximity never trusted); over-submission clamped server-side; validate-then-consume (count Tools first); concurrent last-unit submit → ALREADY_UNLOCKED, consumes nothing; effect idempotency (unlocked guard fires OnNodeUnlocked once); TechNodeUpdate is typed to Metal/Wood and widens to Any if a third material is added; bench-missing degrades gracefully (drop at origin, never errors).

Page 2 — docs/systems/weapons.md​

Source of truth: WeaponConfig.luau, WeaponTypes.luau, WeaponValidation.luau, WeaponServer.server.luau, CombatService.luau, WeaponState.luau, ServerProjectile.luau, the client WeaponController + WeaponHandlers/ (MeleeHandler, GunHandler, ThrowableHandler, TrajectoryPreview) + WeaponEffectsController, and the 2026-06-06 spec as amended by the replicated-projectile-redesign, melee-combo, friendly-fire-prevention, npc-collision-passthrough, and throwable-trajectory-preview specs. The page is written against current code; where it diverges from the original spec, current code wins.

Content to cover:

  • Intro: client-predicts / server-authoritative combat with a shared validator; all damage applied server-side, client hit claims never trusted.
  • Categories table: Melee (combo steps), Gun-Hitscan (pistol/SMG/AR/SR), Gun-Projectile (RocketLauncher) and Throwable (Grenade, C4) — note the current delivery: server-owned replicated ServerProjectile physics (not server-side FastCast2), grenade fused, C4 = Manual detonation. Map each to its damage type (Melee / Bullet / AOE/Explosion).
  • Data flow (ASCII): per-category fire flows — Melee (ReqMeleeSwing → server hitbox from server CFrame → CombatService → WeaponImpact); Hitscan (ReqFireWeapon → server raycast → WeaponFired + WeaponAmmoSync); Projectile/ Throwable (ReqThrowProjectile / rocket via ReqFireWeapon → ServerProjectile → AOE on impact/fuse → ExplosionAt); C4 detonate (ReqDetonate → all active charges).
  • Client / Server / Shared: WeaponController dispatch by Category; the four handlers; WeaponValidation (pure fire-rate / spread / hitbox / AOE falloff / ammo transitions); WeaponServer (per-category validation + damage); CombatService (damage router: Player→HealthManager, NPC-tagged→Humanoid); WeaponState (per-player authoritative ammo + cooldown + reload window); ServerProjectile; WeaponEffectsController (consumes broadcast FX packets).
  • HUD integration contract: the page documents that the system ships no UI and lists the consumable signals (WeaponEquipped, WeaponUnequipped, WeaponAmmoChanged, WeaponReloadStarted, WeaponReloadComplete, WeaponLocalHit, WeaponComboChanged) + WeaponAmmoSync packet.
  • Key files: all modules above.
  • Config knobs: a per-category field reference sourced from WeaponConfig (common fields + Melee / Gun-Hitscan / Gun-Projectile / Throwable field groups), noting tuning lives in config not code.
  • Gotchas / anti-exploit: server-enforced fire-rate (60/RPM or SwingCooldown), server-authoritative ammo + reload timing, origin tolerance check, range cap (MaxDistance), spread bound, server does its own cast (LOS implicit), friendly-fire prevention, NPC collision pass-through tied to the NPC tag, HealthManager mirrors record→Humanoid but not the reverse (route player damage through ApplyDamage).

Reference-map edits​

  • networking-map.md: add rows for ReqTechSubmit, ReqTechCancel, TechNodeUpdate, ReqTechSnapshot (direction, transport, payload, summary — matching the table's existing columns), verified against the registered packet definitions in Packets/init.luau.
  • signals-map.md: add rows for OnTechTreeStateChanged (client repaint) and OnNodeUnlocked (server effect dispatch), with emitter/consumer/payload columns.
  • config-map.md: add a WeaponConfig row (per-weapon registry: categories, damage, fire-rate, ammo, AOE, spread, sounds — link to the Weapons page) and a TechTreeConfig row (bench tag/interaction, refund-arc tuning, node/branch definitions — link to the Tech Tree page).

Accuracy method​

Every claim, default value, packet signature, signal name, and field is read from the actual source module before being written — not copied from the older specs, which predate the projectile redesign and combo changes. Packet payload shapes are confirmed against Packets/init.luau; signal payloads against Signals/init.luau; config defaults against the config modules.

Verification​

  • docs/systems/ contains tech-tree.md and weapons.md; both render with the standard section structure and valid frontmatter.
  • No remaining published-doc reference to a renamed/removed weapon packet (e.g. ReqThrowGrenade, ReqPlaceC4) — current names only.
  • networking-map lists all 4 tech packets; signals-map lists both tech signals; config-map lists WeaponConfig and TechTreeConfig.
  • (Optional, if the user runs it) moonwave dev builds without broken-link warnings for the new pages.

Documentation-of-record​

This is itself a docs task; the deliverables update the docs site directly. No separate "update the docs" step beyond the edits listed above.
