Moonwave Documentation Site — Design

Date: 2026-06-05 Status: Approved (design phase) Topic: Replace the monolithic maintenance guide with a Moonwave-powered documentation site published to GitHub Pages.

Problem​

The project's documentation is a single 542-line file, Documentations/Project-Maintenance-Guide.md. It is accurate but dense and hard to navigate. It does not serve the three jobs the owner needs:

  1. Self-serve simple edits without spending AI tokens on routine "how do I tune X" questions.
  2. Fast lookup of contracts (packets, signals, configs) and APIs.
  3. Re-onboarding after weeks/months away from the project.

Goals & success criteria​

The site succeeds when the owner can answer these from the site alone, no AI needed:

  • "How do I tune/change X?" → How-To Playbooks (numbered checklists).
  • "Where does Y live / what's its contract?" → Reference tables + API pages.
  • "How does Z actually work?" → Per-system narrative pages with diagrams.

Jobs (1) and (2) are served by the playbooks and reference/API material; job (3) by the architecture and per-system narrative.

Decisions (locked during brainstorming)​

DecisionChoice
Documentation depthHybrid — rich narrative for everything + moonwave doc-comments on the cross-cutting modules and the core module(s) of each major system
HostingSeparate public docs repo (code stays private; built site is public)
Old guideMigrate then replace — port content into the site, delete the monolith, leave a short pointer
PublishingCI from the start — GitHub Action builds on push to main and deploys to the public docs repo

Tooling​

  • Moonwave (Docusaurus under the hood). Installed via Node.js + npm i -g moonwave@latest. Moonwave is not a Rokit tool, so it stays out of rokit.toml; the install step is documented in a "Build the docs" page.
  • Local loop: moonwave dev (live preview at localhost:3000), moonwave build (static output to build/).
  • Mermaid diagrams enabled for data-flow / system diagrams.

Repo & hosting layout​

  • Source of truth = the private Endless-Journey repo: holds moonwave.toml, the docs/ narrative folder, the .moonwave/ overrides, and the doc-comments embedded in src/.
  • Build output → a new public repo, e.g. Game-Dev-Neohermit/endless-journey-docs, served at https://game-dev-neohermit.github.io/endless-journey-docs/. Therefore baseUrl = "/endless-journey-docs/" and url = "https://game-dev-neohermit.github.io".
  • One-time owner setup (prerequisite, manual): create the public repo and enable GitHub Pages on it (serve from the gh-pages branch).
  • Edit/source links: moonwave's "Edit this page" / "View source" links point at the private repo and would 404 for outside visitors → disable edit links in the Docusaurus theme config.

Publishing pipeline (CI from the start)​

  • A GitHub Action in the private repo triggers on push to main:
    1. Checkout, set up Node 22, npm i -g moonwave@latest.
    2. moonwave build.
    3. Deploy build/ to the public docs repo's gh-pages branch using peaceiris/actions-gh-pages with external_repository + a deploy key.
  • Auth (one-time): generate an SSH deploy key. Public half → the docs repo's Deploy Keys (write access). Private half → a secret (e.g. DOCS_DEPLOY_KEY) in the private repo.
  • Cost: the build runs in the private repo; the Free plan grants 2,000 Action-minutes/month. A docs build is ~2–4 min and runs only on pushes to main — comfortably within the free allotment.

The docs/ folder collision​

docs/ is moonwave's narrative root and requires a mandatory docs/intro.md. It already contains internal working files that must not be published: docs/superpowers/** (specs/plans/audits written there by the superpowers skills) and docs/audits/**.

Resolution (folders stay exactly where they are):

  • A curated .moonwave/sidebars.js lists only the intended narrative pages, so internal folders never appear in the nav.
  • Docusaurus exclude globs for superpowers/** and audits/** keep them out of the built output entirely.
  • Fallback if exclude-passthrough proves limited: add unlisted: true (or draft: true) frontmatter to the internal pages, or scope the docs plugin to the curated subtree.

Implementation note: verify moonwave's [docusaurus] passthrough supports the docs plugin exclude option during setup; if not, use the fallback.

Information architecture (narrative sidebar)​

  1. Introduction (intro.md) — what the game is (Void Train-inspired), the client-predicts / server-authoritative philosophy, how to read these docs.
  2. Getting Started / Toolchain — Rokit, Rojo (build/serve/sourcemap), Wally + wally-package-types, the TweenPlus TweenPreallocations gotcha, selene, "no test suite — verify in Studio."
  3. Architecture — runtime layers (client/shared/server), the system map, the authority pattern, and the cross-cutting backbone (Signals, Packets, Configs, SoundManager, NotificationManager, Janitor, MotionMaster), each with a "what / why / how to use" blurb.
  4. Systems — one page each, with a Mermaid data-flow diagram: Placement, Stamina/Sprint, Junk, Grabhook, Shredder, Health, Train Fuel, Proximity Pickup / Dropped Tools, Placeable Actions (Stash/Move), Camera, Sound, Notifications. Each page: overview, client/server/shared split, data flow, key files, config knobs, gotchas.
  5. How-To Playbooks — numbered checklists, migrated and expanded from today's "Safe Change Playbooks": Add a placeable · Tune stamina · Adjust junk flow · Change sprint · Tune shredder · Add a sound · Add a notification · Add a packet · Add a signal · Enable Stash/Move on a placeable · Update build UI.
  6. Reference — Networking map (packets), Signals map, Config map, Janitor patterns, MotionMaster cheat-sheet, and a Dependencies page (see "Third-party libraries" below). The pure lookup tables.
  7. API — auto-generated by moonwave from the annotated modules (next section).

Hybrid API-annotation set​

Add moonwave --[=[ ]=] doc-comments (@class, @within, @param, @return, @tag, and realm tags @server / @client) to the following. classOrder in moonwave.toml groups them into sidebar sections (e.g. Backbone, Audio, Placement, Systems, Utilities).

Cross-cutting / library modules (clean APIs):

  • SoundManager (+ submodules Groups, Pool, SFX, Music, Ambience) — richest API.
  • MotionMaster — rich API (Play/Create/Spring/Sequence/SplineMove/PivotMove/fromPreset).
  • PlacementSystem — shared validation API (client preview + server validation).
  • SprintValidation — shared sprint helpers.
  • ShredderMath, ShredderResultCodes — shared math + result-code enum.
  • GenericPoolInstance, GenericPoolObject — pooling utilities.
  • SpawnHelper, GrabHookVisuals, PlaceableActions, BindableCore — public helpers.

Major-system core modules (added per owner request): documented as @class tagged @client / @server. These are mostly top-level *.client.luau / *.server.luau scripts rather than require-able libraries, so their API pages are informational (describe notable functions, link to source) rather than call surfaces:

  • Grabhook → GrabHook.client (+ GrabHookVisuals, above).
  • Floating Junk → JunkController.client, JunkService.server (+ SpawnHelper/pooling, above).
  • Train Brake & Fuel → TrainFuelManager (server module), TrainClient.client, TrainFuelGuiController.client.
  • Camera → CameraController.client, CameraBoomController.client.
  • Shredding → ShredderServer.server, ShredderClient.client (+ ShredderMath/ShredderResultCodes, above).

Third-party / vendored libraries — NOT annotated, link out instead: We do not write or generate documentation for third-party code. Vendored trees (Zone/, SmoothShiftLock/, PartySystem/, Satchel/, Packets/Packet/, Signals/Signal.luau) and Wally deps (howmanysmall/janitor, alexanderlindholt/tweenplus) are covered by a single Dependencies reference page: a table of each dependency with a one-line "what we use it for" and a link to the author's own documentation (forum post / website / GitHub README). The only exceptions are:

  • Heavily modified deps — if we materially changed a vendored library, document the modifications (what diverged from upstream and why).
  • Project-specific integration gotchas — e.g. the TweenPlus TweenPreallocations attribute requirement stays in our Toolchain/gotchas docs because it is our integration knowledge, not upstream API. (How we use Janitor across the codebase also stays in our Reference → Janitor patterns page; the link to Janitor's own API goes on the Dependencies page.)

Documented in narrative reference, NOT as moonwave classes:

  • Signals and Packets — module-level overview annotation only; the per-channel detail lives in the Reference tables (an event bus / packet registry reads better as a table than as generated functions).
  • Configs — kept in the narrative Config reference; they change often, so annotating each field as a class invites churn.

Keeping the docs current​

  • Discipline (extends the existing "record any new signal/packet" rule): when a change touches a system, update that system page and any affected playbook in the same commit.
  • API pages auto-refresh from source comments on every build.
  • A short "Maintaining these docs" page documents the moonwave dev preview loop and how the CI publish works.

Migration of the old guide​

  • Port every section of Project-Maintenance-Guide.md into the appropriate new page (architecture, per-system, playbooks, reference). Preserve hard-won notes verbatim where they are gotchas — notably the TweenPlus TweenPreallocations attribute requirement and the anti-exploit threshold cautions.
  • The old guide's "Third-Party / Vendored Script Packages" section does not get ported as prose. It collapses into the Dependencies reference page (links to upstream docs), except: the TweenPlus TweenPreallocations gotcha moves to Toolchain/gotchas, and any genuinely modified-by-us behavior is documented.
  • Delete the monolith once migration is verified; replace it with a short pointer file (or update Documentations/README.md) directing readers to the site and to the narrative source under docs/.

Out of scope (YAGNI)​

  • Annotating all 75 modules.
  • Versioned docs, i18n, a blog.
  • Any second hosting mechanism beyond the public-repo Pages deploy.

Risks & open implementation questions​

  • Moonwave exclude passthrough for the docs plugin is unverified — confirm early; fallback documented above.
  • Cross-repo deploy key must have write access to the docs repo; the first CI run should be validated end-to-end (build → push → Pages live).
  • baseUrl must exactly match the docs repo name or assets 404; lock the repo name before configuring moonwave.toml.
  • Annotating top-level *.client / *.server scripts is slightly unconventional for moonwave; if the generated pages feel noisy, fall back to documenting those systems narratively and keep moonwave classes to the library modules.
