Placement Smart Cancel — Design

Date: 2026-06-17 Status: Approved (pending spec review)

Summary​

Add a cancel action to placement/build mode that behaves differently depending on how the build session began:

  1. Fresh placement — the player picked up a placeable Tool from the world and equipped it. Cancel unequips the tool back to the Backpack and exits build mode.
  2. Move session — the player started building by pressing a placed item's Move button (which destroyed the placed model, granted the matching Tool, and auto-equipped it). Cancel returns the item to its original spot if that spot is still free; if the spot is now occupied (or otherwise invalid), it falls back to a normal unequip.

The cancel action is triggered by a keyboard key (default X, configurable) and by the existing on-screen Cancel button — both are unified to the same behavior.

Background / current state​

  • PlacementClient enters build mode when a placeable Tool is equipped and drives a ghost preview. Its existing doCancel / unequipTool only exit build-mode visuals and clear the ghost — they do not actually unequip the Tool instance from the character.
  • The on-screen Cancel button (mobile / click) fires Signals.RequestPlacementCancel, wired to doCancel in BuildModeGuiController. Keyboard shortcuts R / F / L are handled in that controller's InputBegan.
  • "Moving" a placed item is the existing Stash/Move feature (PlaceableActionsServer): the Move branch destroys the placed model, clones the matching Tool into the player's Backpack, and Humanoid:EquipTools it — which re-enters build mode. The original model no longer exists, so a revert must recreate it server-side.

Platform constraint (resolved)​

Roblox reserves Escape to open the in-game menu; there is no supported way to suppress it. Binding cancel to Escape would pop the Roblox menu on every press. Decision: use a clean key (X) instead of Escape.

Design decision: server-owned revert state​

Because Move destroys the placed model, reverting must recreate the item server-side and confirm the spot is free. The chosen approach: the server remembers the original spot.

On Move, the server stores { cframe, placeableName, tool } keyed by player. On cancel the client always asks the server to revert; the server returns true only when it actually had a remembered spot and successfully re-placed the item. On false, the client unequips.

Key benefit: the client never tracks move-vs-fresh and never carries a CFrame — one uniform cancel path. Works at any distance (the server owns the authoritative CFrame, so no distance cap is needed for revert).

Components​

1. PlaceableRevertStore (new) — ServerStorage/SharedModules/PlaceableRevertStore.luau​

In-memory, server-only store mapping player → { cframe: CFrame, placeableName: string, tool: Tool }.

API:

  • Set(player, data) — record (or overwrite) the pending revert.
  • Get(player): data? — read current pending revert.
  • Clear(player) — drop the entry.

Shared because the write happens in PlaceableActionsServer (on Move) and the read/consume happens in PlacementServer (on revert).

2. PlaceableActionsServer (edit)​

In the Move branch of handleAction, after the tool is granted and equipped (and before/around the existing broadcast), call:

PlaceableRevertStore.Set(player, {
    cframe = cframe,            -- already captured before model:Destroy()
    placeableName = placeableName,
    tool = newTool,
})

Stash does not set the store. No other change to this file's validation.

3. RequestPlacementRevert packet (new)​

Registered in Packets:

local RequestPlacementRevert = Packet("RequestPlacementRevert"):Response(
    Packet.Boolean8 -- reverted
)

No payload (server owns all state). Returns true if the item was reverted, false otherwise. Added to the module's returned table and to the networking map.

4. PlacementServer (edit) — RequestPlacementRevert.OnServerInvoke​

handler(player):
  data = PlaceableRevertStore.Get(player)
  if not data: return false                       -- fresh session

  -- identity guard: equipped tool must be the exact granted instance
  tool = character:FindFirstChildOfClass("Tool")
  if tool ~= data.tool or data.tool.Parent ~= character:
      PlaceableRevertStore.Clear(player); return false

  template = PlaceableItems[data.placeableName]
  if not template: Clear; return false

  -- re-validate spot is free at the stored CFrame
  req = PlacementSystem.new("BuildArea", 2)
  req.IsBuildMode = true
  req:SetGhostModel(template, ServerStorage)
  boxCFrame, boxSize = req:GetCollisionBox(data.cframe)
  free = req:CheckValidity(boxCFrame, boxSize, req:BuildObstructionFilter(nil))
  if not free:
      req:Destroy(); PlaceableRevertStore.Clear(player); return false

  -- re-place exactly where it was
  placed = template:Clone()
  finalizeModel(placed)
  placed:PivotTo(data.cframe)
  placed:SetAttribute("PlaceableName", data.placeableName)
  placed.Parent = req.PlacedObjectsFolder
  data.tool:Destroy()
  req:Destroy()
  PlaceableRevertStore.Clear(player)
  return true

Notes:

  • No distance cap on revert (server owns the CFrame; that is the rationale for choosing server-owned state).
  • Reuses the existing private finalizeModel in PlacementServer.

Invalidation of the stored spot:

  • Revert success/failure → Clear (handler above).
  • PlaceItem success (item committed elsewhere) → add PlaceableRevertStore.Clear(player) in the existing PlaceItemPacket.OnServerEvent handler after a successful placement.
  • Player leaving → Clear in PlayerRemoving.
  • Drop / tool-swap → no explicit hook; the equipped-tool-identity check makes a stale entry return false safely, and it is cleared on player-leave.

5. PlacementClient (edit) — unified cancelPlacement()​

Merge doCancel and unequipTool into one function:

cancelPlacement():
  if not placement.IsBuildMode or not currentTool: return
  if cancelInFlight: return
  cancelInFlight = true

  -- snappy local exit (mirror existing doCancel visuals)
  currentTool = nil
  placement:SetBuildMode(false)
  isGhostLocked = false
  Signals.OnGhostLockChanged:Fire(false)
  ClientToggleGhost:Fire(false, nil)
  setShiftLockGate(false)
  Signals.OnBuildModeChanged:Fire(false)

  task.spawn(function()
    local reverted = RequestPlacementRevert:Fire()
    cancelInFlight = false
    if not reverted then
      local humanoid = character and character:FindFirstChildWhichIsA("Humanoid")
      if humanoid then humanoid:UnequipTools() end  -- tool → Backpack
    end
    -- if reverted, the server destroyed the tool; ChildRemoved runs the
    -- (idempotent) unequip path
  end)
  • Repoint Signals.RequestPlacementCancel:Connect(cancelPlacement) (replacing the doCancel connection) so the on-screen Cancel button shares the behavior.
  • ChildRemoved-driven unequipTool must remain safe to call when currentTool is already nil (it already early-returns).

6. BuildModeGuiController (edit)​

In the existing InputBegan block, add a branch alongside R / F / L:

elseif input.KeyCode == PlacementConfig.CancelKey then
    Signals.RequestPlacementCancel:Fire()

Both the key and the on-screen button funnel through RequestPlacementCancel. gameProcessed guard stays (X is not game-processed).

7. PlacementConfig (edit)​

Add a tunable keybind:

CancelKey = Enum.KeyCode.X,

Edge cases​

CaseOutcome
Fresh placement cancelGet → nil → false → unequip to Backpack
Move then cancel, spot freerevert: item re-placed at original CFrame, tool destroyed
Move then cancel, spot now occupiedCheckValidity fails → false → unequip
Cancel spam / double-invokeclient cancelInFlight guard + server Clear-on-consume
Move, place elsewhere, later cancel a different toolstale entry cleared on PlaceItem success; identity check is backstop
Move, drop tool, cancelequipped tool ≠ stored instance → false → unequip
Player leaves mid-sessionPlayerRemoving clears the store

Out of scope (YAGNI)​

  • No client-side move/fresh session tracking and no new Signal (server-owned state makes them unnecessary).
  • No migration of R / F / L into config — only CancelKey is added.
  • No attempt to suppress the Roblox Escape menu (clean key chosen instead).
