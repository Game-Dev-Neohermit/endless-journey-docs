Workbench Crafting — Design

Date: 2026-06-15 Status: Approved for planning Game: Endless Journey (Roblox / Rojo / Luau) Relationship: Realizes the "workbench crafting is a separate spec" follow-up promised in 2026-06-13-crafted-armor-defense-layer-design.md, which left the ArmorManager.SetTier seam ready. Drives that seam, plus weapon and placeable grants.

Summary​

A placed Workbench station that lets a player craft weapons, armor, and placeables from recipes by spending Wood/Metal crafting materials. A player places the Workbench (existing placeable system), walks up to it (ProximityPrompt) to open the already-built WorkbenchGui, picks a recipe from the grid, sees its cost/tier/requirements in the detail pane, and clicks Accept to craft. Crafting is instant and per-player (pay full cost once → receive the output) — distinct from the Tech Tree's shared-pool / auto-unlock model.

The interaction follows the project's client-predicts / server-authoritative pattern, mirroring the Tech Tree's shape (shared pure validator + frozen result codes + typed packets + an output dispatcher). The client greys recipes it can't afford or that are gated; the server re-validates everything and is the sole authority over material consumption and output grants.

Scope is framework-only. This spec builds the crafting system, config schema, networking, GUI wiring, and the Tech-Tree gate seam, seeded with a few clearly-marked placeholder recipes. The real recipe catalog and balancing are authored later against the shipped schema.

Components & responsibilities​

WorkbenchConfig.luau (new) — tune-here surface​

Recipe schema:

export type Output =
    | { Kind: "Weapon",    ToolName: string }       -- clone from weapon-templates folder
    | { Kind: "Armor",     Tier: number }           -- ArmorManager.SetTier(player, Tier)
    | { Kind: "Placeable", PlaceableName: string }  -- clone PlaceableTools/<PlaceableName>

export type Recipe = {
    Category: string,            -- "Weapon" | "Armor" | "Placeable" (drives future tabs)
    DisplayName: string,
    Description: string,
    Tier: number,                -- 1..5 flavor/quality badge only (no ladder)
    Icon: string,                -- grid + detail image asset
    Cost: { Wood: number?, Metal: number? },  -- GUI is fixed to these two materials
    RequiresNode: string?,       -- TechTree nodeId gate; nil = always available
    Output: Output,
}

Tuning constants (initial values to tune):

FieldDefaultEffect
STATION_TAG"WorkbenchStation"CollectionService tag on the placed Workbench Model
INTERACT_DISTANCE12Studs within which the GUI opens / crafts are accepted
INTERACT_DISTANCE_TOLERANCE5Server-side slack added to the distance check
PROMPT_PART_NAME"WorkbenchPromptPart"Child BasePart holding the open-GUI ProximityPrompt
CRAFT_COOLDOWN0.5Per-player seconds between accepted crafts
MATERIALS_FOLDER"CraftingMaterials"ReplicatedStorage folder of Wood/Metal Tool templates
WEAPON_TEMPLATES_FOLDER"WeaponTemplates"ServerStorage folder of craftable weapon Tools to clone
Sounds.CraftSuccess / Sounds.CraftFail""SoundManager keys; empty = silent (project convention)

Recipes is a { [string]: Recipe } table seeded with placeholder entries (one per Output kind), each commented -- PLACEHOLDER: replace with real content, e.g. a Weapon recipe outputting an existing weapon ToolName, an Armor recipe targeting an ArmorConfig tier, and a Placeable recipe outputting an existing PlaceableTools entry. At least one placeholder carries a RequiresNode to exercise the gate.

WorkbenchResultCodes.luau (new)​

Frozen enum, companion to the validator (mirrors TechTreeResultCodes). Codes: NONE, UNKNOWN_RECIPE, INVALID_TARGET, TOO_FAR, COOLDOWN, LOCKED, OUTPUT_FAILED, INSUFFICIENT_MATERIALS. Shared by both sides so string literals never appear in business logic; the client maps codes to NotificationManager messages.

WorkbenchValidation.luau (new) — pure, shared​

Stateless, no Roblox service calls — the single rules source both sides share (mirrors TechTreeState / SprintValidation). Exported helpers:

  • getRecipe(recipeId) -> Recipe?
  • costOf(recipe) -> { [string]: number } (normalizes the Cost map, omitting nil/zero)
  • canAfford(recipe, heldCounts) -> boolean
  • isUnlocked(recipe, isNodeUnlocked) -> boolean where isNodeUnlocked: (nodeId: string) -> boolean
  • validateCraft(recipe, heldCounts, isNodeUnlocked) -> (boolean, code) — recipe membership, gate, affordability. It does not check proximity, output feasibility, or that the player physically holds Tools — those are server-only concerns layered on top.

TechTreeService.server.luau (edit) — gate seam​

Add a ReplicatedStorage/TechTreeUnlocked folder, created at boot, parallel to the existing TechTreeBuffs. On boot and inside unlockNode, publish one marker per unlocked node id (a BoolValue named for the node, or a folder attribute — implementer's choice, single source). This is the only TechTreeService change. Both consumers read this one folder:

  • Client WorkbenchGuiController reads it to grey gated recipes and repaints on change.
  • Server WorkbenchService reads it to authorize crafts.

WorkbenchValidation stays pure by receiving an isNodeUnlocked callback that closes over this folder, so no module depends on the other's internals.

WorkbenchService.server.luau (new) — authority​

Handles ReqCraft.OnServerInvoke(player, bench, recipeId). Validates in this exact order; any failure returns (false, code) and consumes nothing, grants nothing:

  1. recipe = getRecipe(recipeId) exists → else UNKNOWN_RECIPE.
  2. bench is an Instance, IsA("Model"), tagged STATION_TAG, and parented under workspace.PlacedObjects → else INVALID_TARGET.
  3. Player's character is within INTERACT_DISTANCE + INTERACT_DISTANCE_TOLERANCE of the bench → else TOO_FAR.
  4. Per-player cooldown elapsed → else COOLDOWN.
  5. Gate: RequiresNode is nil or unlocked (read TechTreeUnlocked) → else LOCKED.
  6. Output feasibility (checked before consuming): Weapon → template exists in WEAPON_TEMPLATES_FOLDER and IsA("Tool"); Placeable → PlaceableTools/<PlaceableName> exists and IsA("Tool"); Armor → tier exists in ArmorConfig.Tiers → else OUTPUT_FAILED.
  7. Server countMaterial(player, matType) >= need for every cost material → else INSUFFICIENT_MATERIALS.

Then, in order: consumeMaterial(player, matType, need) for each cost (reuse the count/consume helper pattern from TechTreeService), CraftOutputDispatcher.grant(player, recipe.Output), record cooldown timestamp, return (true, NONE).

countMaterial / consumeMaterial count Tools in Backpack and the equipped Tool, matching by IsCraftMaterial + ItemType attributes — identical to the Tech Tree.

CraftOutputDispatcher.luau (new, ServerStorage/SharedModules)​

Mirrors TechEffectsDispatcher: dispatches on Output.Kind with one isolated handler each, so a new output kind is a new handler, not an edit to the service. grant(player, output) -> boolean:

  • Weapon → clone the Tool from WEAPON_TEMPLATES_FOLDER, parent to player.Backpack.
  • Armor → ArmorManager.SetTier(player, output.Tier).
  • Placeable → clone ReplicatedStorage/PlaceableTools/<PlaceableName>, parent to player.Backpack (same Tool the stash/move system grants).
  • Unknown kind → warn + return false (lets recipes be authored ahead of a new handler).

Feasibility was already checked in WorkbenchService step 6 before consuming, so a false here is a defensive last resort; the service logs it. (Materials are only consumed after step 6 passes, so a late failure is not expected in normal operation.)

WorkbenchGuiController.client.luau (new)​

Drives the existing StarterGui/WorkbenchGui (does not rebuild it). Reference paths under MainContainer.SecondaryContainer.Bottom:

  • Recipe grid: RecipeContainer.RecipeScrollingContainer (an ExampleItem ImageButton template).
  • Placement buttons: RecipeContainer.PlacementButtonContainer.StashButton / MoveButton.
  • Detail pane: ActionContainer.ActionContainer → HeaderContainer.RecipeIcon, HeaderContainer.TitleContainer.Header / SubHeader, TierContainer.TierLevelContainer.Tier1..5, MaterialContainer.ReqWoodMaterial / ReqMetalMaterial (MaterialCount / MaterialName / MaterialIcon), and AcceptButton.

Behavior:

  • Open/close: opens via the placed station's ProximityPrompt (CollectionService STATION_TAG, same wiring as TechTreeGuiController). Closes on header/escape and auto-closes if the bound station is removed (stashed/moved/destroyed). One Janitor per open session.
  • Grid build: keep one ExampleItem as a hidden template, clear the rest, instantiate one button per recipe filtered by currentCategory (default "all" → flat list). Set each Icon. A currentCategory field is the only hook category tabs will need later.
  • Selection → detail: populate RecipeIcon, Header/SubHeader from DisplayName/Description, highlight Tier{N}, fill ReqWoodMaterial/ReqMetalMaterial as held/cost (hide a row whose cost is nil/zero), and enable AcceptButton only when canAfford and unlocked.
  • Accept: ReqCraft:Fire(bench, recipeId). On (true, NONE) play Sounds.CraftSuccess, fire Signals.OnItemCrafted, refresh held counts/detail. On failure, surface a NotificationManager message mapped from the result code and play Sounds.CraftFail.
  • Stash/Move: PlaceableActions.bind(stationModel, gui) on open; binding:Unbind() on close. No new logic — the existing buttons named StashButton/MoveButton are wired automatically.
  • Live repaint: recompute affordability on Backpack child add/remove and repaint gate state on TechTreeUnlocked changes / Signals.OnNodeUnlocked so a freshly-unlocked recipe ungreys live.

Data flow​

PLACE
  Player equips Workbench Tool → places via PlacementSystem → station tagged STATION_TAG,
  attribute PlaceableName="Workbench" (set by PlacementServer).

OPEN
  Player near station → ProximityPrompt.Triggered → controller enables WorkbenchGui,
  binds PlaceableActions(stationModel, gui), builds grid from WorkbenchConfig.Recipes.

SELECT
  Click recipe → detail pane filled; AcceptButton enabled iff canAfford && isUnlocked.

CRAFT
  Accept → ReqCraft:Fire(station, recipeId)
        →  server: validate (recipe, target, proximity, cooldown, gate,
                   output feasibility, materials)
        →  consumeMaterial × cost
        →  CraftOutputDispatcher.grant(player, Output)
              Weapon    → clone WeaponTemplates/<ToolName> → Backpack
              Armor     → ArmorManager.SetTier(player, Tier)
              Placeable → clone PlaceableTools/<Name> → Backpack
        ◄  (true, NONE)
  client: SFX + OnItemCrafted + refresh.  (failure → NotificationManager(code))

STASH / MOVE
  StashButton/MoveButton → existing PlaceableActions packets → station removed →
  controller auto-closes GUI.

Edge cases & anti-exploit​

  • Server re-checks proximity on every ReqCraft using INTERACT_DISTANCE + TOLERANCE; a modified client crafting from afar gets TOO_FAR. Client GUI proximity is never trusted.
  • Feasibility-before-consume (step 6 before step 7) guarantees a misconfigured recipe (missing weapon template / placeable Tool / invalid armor tier) returns OUTPUT_FAILED and never eats materials.
  • Validate-then-consume ordering: all checks pass before any Tool is destroyed, so a rejected craft never costs the player materials.
  • Cooldown + serial invokes: RemoteFunction.OnServerInvoke runs serially; the per-player cooldown drops scripted spam. The client also gates the Accept button while a request is in flight.
  • Gate reads server-written state: TechTreeUnlocked is written only by TechTreeService, so the gate is unforgeable by clients.
  • Armor has no ladder: SetTier simply sets the recipe's tier; re-crafting an equal/lower tier is allowed (wastes materials) — accepted design choice, documented. ArmorManager.SetTier already rejects tiers absent from ArmorConfig.
  • Station removed mid-session: controller watches the bound station and the STATION_TAG removal; auto-closes the GUI and unbinds PlaceableActions. An in-flight ReqCraft against a now-removed station fails INVALID_TARGET server-side.
  • Two-material GUI limit: the GUI has exactly ReqWoodMaterial/ReqMetalMaterial. Recipe Cost is restricted to Wood/Metal. Adding a third material requires widening the GUI's material rows.
  • Backpack with no cap: granted Tools land in the default Backpack (no cap in engine); out of scope to limit.

Out of scope (this spec)​

  • Category tab UI (schema carries Category; tabs are a later pure-UI add).
  • The real recipe catalog and balancing (framework only — placeholders ship).
  • DataStore persistence of crafted weapons/placeables (Tool grants are runtime; armor tier persists via the existing ArmorManager/ProfileStore path already specced).
  • Armor avatar visuals, weapon durability/decay/repair, repair recipes.
  • Authoring the WeaponTemplates folder contents and per-placeable Tool templates (Studio setup).
  • Any new crafting materials beyond Wood/Metal.

Studio setup (authored by the user)​

  1. ReplicatedStorage/PlaceableItems/Workbench (the placed Model) gets a child BasePart WorkbenchPromptPart holding a ProximityPrompt, and is tagged WorkbenchStation (the placed instance carries this so the controller can find it). The PlaceableTools/Workbench Tool already exists.
  2. ServerStorage/WeaponTemplates folder holding craftable weapon Tools (e.g. clones of Pistol/SMG/ClassicSword), separate from StarterPack so they are not auto-given.
  3. Each craftable placeable has its ReplicatedStorage/PlaceableTools/<Name> Tool (existing stash/move contract).
  4. Wood/Metal reuse the existing ReplicatedStorage/CraftingMaterials templates.

Testing​

No automated suite (project convention). Verify in Studio: place a Workbench, open it via the prompt, confirm the grid renders all config recipes, gated recipes appear locked until their Tech node unlocks, the detail pane shows correct cost/held/tier, and Accept with sufficient Wood/Metal consumes exactly the cost and grants the right output (weapon Tool in Backpack / ArmorState tier updates / placeable Tool in Backpack). Confirm crafting from too far, while gated, or with insufficient materials each fails with the right notification and consumes nothing. Confirm Stash/Move still work from the GUI and auto-close it.
