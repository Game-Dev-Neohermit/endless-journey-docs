Tech Tree System — Design Spec

Date: 2026-06-10 Status: Approved for planning Game: Endless Journey (Roblox / Rojo / Luau)

Summary​

A cooperative, server-wide tech tree unlocked with craftable materials (Wood, Metal). Players gather at a single fixed tech-tree bench, open a GUI, and pool resources into nodes. Any eligible node is always open for submission; multiple nodes can accumulate concurrently. When a node's full cost is met it auto-unlocks and fires its effect. Cancelling a node's funding (allowed for anyone at the bench) ejects the pooled materials onto the floor as a pickup pile — exactly like the Shredder's material arc — that anyone nearby can collect.

Progress is server-wide and session-only (no DataStore). Because refunds go to a shared ground pile, no per-player contribution tracking is needed — each node has one shared pool.

Architecture​

Follows the project's client-predicts / server-authoritative pattern (as in Placement and Shredder): a pure shared validator both sides agree on, a server authority that owns state, and a client controller that drives an authored GUI and never trusts itself.

ReplicatedStorage/SharedModules/
  Configs/TechTreeConfig.luau       -- branches, nodes, costs, prereqs, effect keys,
                                       bench tag/names, refund-arc tuning, GUI labels
  TechTreeResultCodes.luau          -- numeric reason codes (mirror of ShredderResultCodes)
  TechTreeState.luau                -- PURE shared logic: isUnlocked / isEligible /
                                       remaining / validateSubmit (no side effects)

ServerScriptService/
  TechTreeService.server.luau       -- authoritative state, packet handlers, consumes
                                       Tools, fires OnNodeUnlocked, broadcasts deltas
  TechEffectsDispatcher.server.luau -- listens OnNodeUnlocked, applies effect by key;
                                       ships ONE example effect (StatBuff)

ServerStorage/SharedModules/
  MaterialEjector.luau              -- shared "arc materials onto the floor as a pickup
                                       pile" mechanism; used by TechTree refund

StarterPlayer/StarterPlayerScripts/
  TechTreeGuiController.client.luau -- drives authored StarterGui.TechTreeGui, opens on
                                       bench proximity, sends submit/cancel, repaints on sync

Packets/init.luau   -- new channels (below)
Signals/init.luau   -- OnTechTreeStateChanged (client repaint), OnNodeUnlocked (server effects)

Authoritative state (server only)​

unlocked: { [nodeId]: true }
pools:    { [nodeId]: { [materialType]: number } }   -- submitted-so-far totals per node

No DataStore. No per-player contribution table (refund is a shared pile).

Config & node model​

TechTreeConfig declares branches and nodes. Linear tiers ⇒ a node's Prereq is a single nodeId (or nil for tier 1). Cost keys are material ItemType names matching the existing CraftingMaterials Tool templates.

TechTreeConfig.Nodes = {
    Durability_T1 = {
        Branch = "Durability", Tier = 1,
        DisplayName = "Scrap Plating",
        Description = "Adds +50 Max HP to the ship core.",
        Cost = { Metal = 25 },
        Prereq = nil,
        Effect = { Type = "StatBuff", Stat = "MaxHP", Amount = 50 },
    },
    Durability_T2 = {
        Branch = "Durability", Tier = 2,
        DisplayName = "Iron Barricades",
        Description = "Adds +150 Max HP. Spikes damage attackers.",
        Cost = { Metal = 100 },
        Prereq = "Durability_T1",
        Effect = { Type = "StatBuff", Stat = "MaxHP", Amount = 150 },
    },
    -- Fuel_T1, Fuel_T2, ...  (declared now, effects wired later)
}

Bench / refund tuning (own keys, same shape as ShredderConfig so they read familiarly):

TechTreeConfig.BENCH_TAG = "TechTreeBench"
TechTreeConfig.INTERACT_DISTANCE = 12
TechTreeConfig.INTERACT_DISTANCE_TOLERANCE = 5
TechTreeConfig.TRAJECTORY_MODEL_NAME = "TrajectoryPoints"   -- SpawnPoint/LandingPoint for refund arc
TechTreeConfig.SPAWN_POINT_NAME = "SpawnPoint"
TechTreeConfig.LANDING_POINT_NAME = "LandingPoint"
TechTreeConfig.MATERIALS_FOLDER = "CraftingMaterials"       -- reuse existing Tool templates
-- refund-arc tuning: ARC_DURATION, ARC_HEIGHT_BOOST, LANDING_SCATTER_RADIUS,
-- ITEM_EJECT_DELAY, MAX_ANIMATED_EJECT_ITEMS, AUTO_COLLECT_DELAY

Studio setup (documented in the config header, per project convention)​

One Model tagged TechTreeBench, with its PrimaryPart set and a TrajectoryPoints child Model containing SpawnPoint and LandingPoint BaseParts — identical authoring to the Shredder workbench's trajectory points, used here for the refund arc.

Components & responsibilities​

  • TechTreeState (pure, shared). isUnlocked(state, id), isEligible(state, id) (prereq unlocked AND not already unlocked), remaining(state, id) (cost minus pool per material), validateSubmit(state, id, matType, amount) → (ok, reasonCode). Client uses it to enable/grey buttons; server uses the same function to authorize. Single rule source.
  • TechTreeService (server authority). Owns unlocked/pools. Handles ReqTechSubmit and ReqTechCancel: validates proximity + TechTreeState, consumes exactly N material Tools from the backpack, updates the pool, and on full funding clears the pool, sets unlocked[id]=true, fires Signals.OnNodeUnlocked(id), and broadcasts. On cancel, hands the pooled counts to MaterialEjector and zeroes the pool. Broadcasts TechNodeUpdate deltas; answers ReqTechSnapshot with the full state on join.
  • TechEffectsDispatcher (server). Connects OnNodeUnlocked; switches on Effect.Type. v1 implements one type end-to-end (StatBuff example). Unknown types warn + no-op so future nodes are declarable now and wired later.
  • MaterialEjector (shared server). Eject(benchModel, { [matType]: count }) runs the Shredder-style arc (MotionMaster.SplineMove) from the bench's TrajectoryPoints, registers each piece with ProximityPickupServer, tags CraftMaterial, and provides the auto-collect fallback. Pure mechanism — no tech-tree knowledge.
  • TechTreeGuiController (client). Opens the authored TechTreeGui when the local player is within INTERACT_DISTANCE of the bench (proximity trigger, matching Shredder style). Renders branches/tiers with per-node state (locked / eligible / funding / unlocked) and pool-vs-cost. Selecting a node shows steppers (max = min(held, remaining)); Submit fires ReqTechSubmit per material type; Cancel fires ReqTechCancel. Repaints on OnTechTreeStateChanged. No persistent client state — server is truth.

Network protocol (new Packets)​

-- Client → Server: submit `amount` of one material type toward a node.
ReqTechSubmit = Packet("ReqTechSubmit",
    Packet.String,    -- nodeId
    Packet.String,    -- materialType ("Wood" | "Metal")
    Packet.NumberU16   -- amount
):Response(
    Packet.Boolean8,  -- success
    Packet.NumberU8    -- reason code (TechTreeResultCodes)
)

-- Client → Server: cancel a node's funding (anyone at bench); refunds pool as ground pile.
ReqTechCancel = Packet("ReqTechCancel",
    Packet.String     -- nodeId
):Response(
    Packet.Boolean8,  -- success
    Packet.NumberU8    -- reason code
)

-- Server → Client: per-node delta (sent on every change).
TechNodeUpdate = Packet("TechNodeUpdate",
    Packet.String,    -- nodeId
    Packet.NumberU16,  -- metalSubmitted
    Packet.NumberU16,  -- woodSubmitted
    Packet.Boolean8    -- isUnlocked
)

-- Server → owning Client: full snapshot on join.
ReqTechSnapshot = Packet("ReqTechSnapshot"):Response( Packet.Any )  -- serialized state table

Tradeoff noted: TechNodeUpdate is typed to the two current materials (Metal/Wood) to stay on the typed-packet rails. If a third craft material is added later, this delta widens to an Any material→count map. Two new Signals: OnTechTreeStateChanged (client repaint) and OnNodeUnlocked (server effect dispatch).

Data flow​

Submit: GUI stepper → ReqTechSubmit(id, mat, amt) → server validates proximity + TechTreeState.validateSubmit (eligible, amount > 0, pool+amt ≤ cost) + player actually holds amt of that material → consume exactly amt Tools → pools[id][mat] += amt → if every material now meets cost: clear pool, unlocked[id]=true, fire OnNodeUnlocked(id), broadcast TechNodeUpdate(..., isUnlocked=true); else broadcast updated counts → respond success.

Auto-unlock effect: TechEffectsDispatcher hears OnNodeUnlocked(id) → reads Effect from config → applies it (StatBuff example) → next-tier children automatically light up because TechTreeState.isEligible now passes.

Cancel: ReqTechCancel(id) → server validates proximity + pool > 0 → snapshot pools[id], zero it, broadcast TechNodeUpdate(..., 0, 0, false) → MaterialEjector.Eject(bench, snapshot) arcs the materials onto the floor as a ProximityPickup pile (auto-collect fallback after delay). Node stays open (always-open model).

Join: client fires ReqTechSnapshot → server returns full unlocked + pools so a late joiner sees current progress.

Edge cases & anti-exploit​

  • Proximity re-checked server-side on every submit/cancel (INTERACT_DISTANCE + TOLERANCE), like Shredder — client GUI proximity is never trusted.
  • Over-submission clamped: server rejects an amount that would exceed remaining cost, so the pool can't overshoot and the stepper max is enforced authoritatively.
  • Insufficient materials: if the player doesn't actually hold amount Tools of that type, reject and consume nothing (validate-then-consume; count Tools first).
  • Concurrent submit race (two players fund the last unit at once): server events are single-threaded; the second submit sees the node already unlocked → reason ALREADY_UNLOCKED, consumes nothing.
  • Prereq not met / already unlocked / unknown node: distinct reason codes, no-op.
  • Cancel with empty pool: reject NOTHING_TO_REFUND, no arc.
  • Player leaves mid-session: pools are shared, not per-player — nothing to refund or reset; already-submitted materials remain in the pool.
  • Bench removed / missing TrajectoryPoints: MaterialEjector warns and degrades gracefully (drop at bench origin / skip arc) — never errors the cancel.
  • Effect idempotency: a node unlocks exactly once (unlocked guard before firing OnNodeUnlocked), so StatBuff cannot double-apply.

Out of scope (this spec)​

  • Concrete effects beyond the single StatBuff example (hull/fuel/nets/cosmetics declared in config, wired in later specs).
  • DataStore persistence of tech progress.
  • Migrating the Shredder onto MaterialEjector.
  • Per-party trees and per-player contribution tracking/refunds.
  • Placeable / multiple tech benches.
