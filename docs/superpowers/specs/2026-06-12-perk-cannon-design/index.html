Perk System — Cannon + Cannon Damage Perk (Spec 5 of 5)

Date: 2026-06-12 Status: Approved for planning — cannon gameplay flagged for a dedicated brainstorm (see "Scope note") Game: Endless Journey (Roblox / Rojo / Luau) Series: Spec 5 of 5 — depends on Spec 1 (Perk Framework); reuses the Weapon stack (FastCast2, ServerProjectile, CombatService). Prerequisite: Spec 1 implemented (the CannonDamage perk is declared and publishes PartyPerkBuffs.CannonDamageBonus, but no cannon exists to consume it).

Scope note (read first)​

The Cannon Damage perk is a one-line multiplier on a cannon's damage. The cannon itself is a substantial new combat feature whose gameplay forks (manned turret vs automatic, ammo model, targeting) are not perk concerns. This spec defines a minimal manned turret sufficient to host the perk and to be a real, usable weapon, with its core model stated as an assumption. Before this spec's implementation plan, the cannon gameplay should get its own brainstorming pass (it's effectively its own sub-project). The perk hook is stable regardless of how that brainstorm resolves: finalDamage = base * (1 + CannonDamageBonus).

Summary​

A mounted cannon on the train that a player mans to fire explosive shells at enemies/junk, dealing area damage. It reuses the existing weapon infrastructure (FastCast2 projectile simulation, ServerProjectile, CombatService.ApplyAOE) rather than inventing new systems. The Cannon Damage party perk multiplies its shell damage by the resolved CannonDamageBonus.

Architecture​

Reuses the weapon stack; the cannon is server-authoritative like WeaponServer.

ReplicatedStorage/SharedModules/Configs/CannonConfig.luau   -- NEW: damage, AOERadius,
  -- fireCooldown, shellSpeed, gravity, mount tag, prompt names, FX/sound keys

ServerScriptService/CannonServer.server.luau                -- NEW: mount/dismount auth,
  -- validates fire requests (proximity to mount, cooldown), simulates shell via ServerProjectile,
  -- applies AOE damage scaled by CannonDamageBonus

StarterPlayer/StarterPlayerScripts/CannonController.client.luau -- NEW: mount UX, camera aim,
  -- trajectory preview (reuse WeaponHandlers/TrajectoryPreview), fire input, impact FX

Packets/init.luau   -- + ReqMountCannon, ReqFireCannon, CannonFired (broadcast FX)
Signals/init.luau   -- (optional) OnCannonMounted (HUD/camera bridge)

Damage application reuses CombatService.ApplyAOE(center, radius, damage, "AOE", source, ignore) — the same path grenades/rockets/C4 already use, so faction rules and player/NPC routing are inherited for free.

CannonConfig.FireCooldown = 2.0            -- seconds between shots (rate cap)

Components & responsibilities​

  • CannonServer (server authority).
    • Mount: ReqMountCannon(mountModel) → validate proximity to the tagged mount + not already occupied → record occupant. ReqMountCannon(nil)/dismount/disconnect clears it.
    • Fire: ReqFireCannon(origin, direction) → validate the requester is the mount's occupant, cooldown elapsed, origin near the muzzle (anti-teleport, like WeaponServer) → spawn an authoritative shell via ServerProjectile/FastCast2 → on impact, damage = CannonConfig.Damage * (1 + partyBonus) where partyBonus = ReplicatedStorage.PartyPerkBuffs:GetAttribute("CannonDamageBonus") or 0 → CombatService.ApplyAOE(impact, AOERadius, damage, "AOE", occupant, {}) → broadcast CannonFired + ExplosionAt (reuse the existing explosion FX packet).
    • Per-mount cooldown stored server-side; client aim is never trusted for damage (server re-simulates the shell from its own muzzle CFrame + the supplied direction).
  • CannonController (client). ProximityPrompt to mount; on mount, switch to an aim camera and show a trajectory preview (reuse WeaponHandlers/TrajectoryPreview); fire input sends ReqFireCannon(muzzle, aimDir); renders muzzle flash/impact via WeaponEffectsController patterns and SoundManager. Dismount restores normal camera. No authoritative state.
  • Cannon Damage perk. Consumed entirely at the server damage line above — the Spec 1 dispatcher already publishes PartyPerkBuffs.CannonDamageBonus (party max). Reads the attribute per shot (live; respec/leave changes apply to the next shell).

Network protocol (new Packets)​

-- Client → Server: mount (model) or dismount (nil) a cannon.
ReqMountCannon = Packet("ReqMountCannon", Packet.Any :: Instance?):Response(Packet.Boolean8)

-- Client → Server: fire from the manned cannon. Server validates occupancy/cooldown/origin
-- and runs its own authoritative shell; client aim direction is advisory.
ReqFireCannon = Packet("ReqFireCannon",
    Packet.Vector3F32,  -- muzzle origin (validated near the real muzzle)
    Packet.Vector3F32   -- aim direction (unit)
):Response(
    Packet.Boolean8,    -- accepted
    Packet.NumberF32     -- cooldown remaining (0 if accepted)
)

-- Server → all Clients: a shell was fired; render tracer/shell + muzzle FX for non-gunners.
CannonFired = Packet("CannonFired",
    Packet.Instance :: Player,  -- gunner
    Packet.Vector3F32,          -- muzzle origin
    Packet.Vector3F32           -- initial velocity (for client shell visual)
)
-- Impact reuses the existing ExplosionAt packet.

Data flow​

Mount prompt → ReqMountCannon → server marks occupant → client enters aim mode + trajectory preview → fire → ReqFireCannon(muzzle, dir) → server validates (occupant, cooldown, origin) → spawns authoritative shell → on impact computes Damage × (1 + CannonDamageBonus) → CombatService.ApplyAOE → broadcast CannonFired + ExplosionAt → all clients render. Mid-run perk allocate/respec changes CannonDamageBonus; the next shell reads the new value.

Edge cases & anti-exploit​

  • Server-authoritative fire: occupancy, cooldown, and muzzle-origin proximity are re-validated server-side; the client cannot fire a cannon it doesn't occupy, faster than the cooldown, or from a forged position (same posture as WeaponServer).
  • Single occupant per mount: a second mount request while occupied is rejected; occupant is cleared on dismount, death, or disconnect (Janitor-owned connections, never hand-rolled).
  • Damage read is server-side of the server-written CannonDamageBonus — unforgeable.
  • Party bonus on leave: Spec 1 dispatcher lowers the resolved bonus when the top holder leaves; the next shell reflects it (no cached multiplier).
  • Faction rules inherited: AOE routes through CombatService, so friendly-fire/faction gates and player-vs-NPC routing behave exactly like existing explosives.
  • No mount in world / missing muzzle part: server rejects the fire gracefully; client degrades (no preview) rather than erroring.

Out of scope (this spec)​

  • The dedicated cannon-gameplay brainstorm's eventual choices if they diverge from the assumptions (auto-turret targeting AI, ammo/resource economy, multiple cannon types) — those extend CannonConfig/CannonServer without touching the perk hook.
  • Enemy waves to shoot at (a separate combat/enemy spec).
  • Any new perk plumbing, GUI, or persistence (Spec 1).
