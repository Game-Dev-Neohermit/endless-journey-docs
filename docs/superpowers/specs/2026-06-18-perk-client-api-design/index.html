Perk Client API — Design

Date: 2026-06-18 Status: Approved (pending spec review)

Goal​

Invert the perk UI dependency. Today PerkController.client.luau builds the entire perk panel in code (ScreenGui, panel, points label, respec button, scrolling list + per-perk rows, Personal/Party tabs, and a separate HUD toggle button) and wires behavior + server sync onto those instances.

Instead, the perk system should own no GUI instances. It exposes a client read model + commands + change signal (PerkClient). Any GUI — the planned authored panel opened from a Satchel topbar icon — consumes the API. The GUI depends on the perk system, not the reverse.

Non-Goals​

  • Building the actual perk GUIs (authored later, separate spec/plan).
  • Satchel topbar integration (lives in the future GUI layer, not in PerkClient).
  • Any server-side change. Packets and authority logic are unchanged.

Planned GUI consumers (informs the API surface, built separately)​

The UI is intentionally split so neither screen is over-dense:

  • ActivePerksGui (a.k.a. "Info"/"Loadout") — read-only. Two sections:
    • Personal active — perks the player allocated (Level > 0), each with icon, EffectText, Description, Level.
    • Party active — perks currently buffing the server (ActivePartyLevel > 0), shown at the server-wide active strength (ActiveEffectText / ActivePartyLevel), regardless of who allocated them.
  • PerkUpgradeGui — interactive. Lists upgradeable perks per category with the player's own Level, the + control gated by CanAllocate, available points from GetAvailablePoints, and respec via Respec / CanRespec.

Both subscribe to PerkClient.Changed independently and repaint themselves.

Architecture​

Three pieces:

  1. PerkClient — new client-facing singleton module at src/ReplicatedStorage/SharedModules/PerkClient.luau. Lives alongside PerkState / PerkConfig, consistent with SoundManager being a client-facing singleton in SharedModules. Holds the cached server snapshot, watches the PartyPerkBuffs folder, fires request packets, performs optimistic prediction, and exposes queries + commands + a Changed signal.

  2. PerkController.client.luau — reduced from ~243 lines to a thin bootstrap that requires PerkClient and calls PerkClient.Init() once, so the read model is warm before any GUI opens. All Instance.new GUI building is deleted.

  3. PerkConfig — gains an optional Icon: string? field on the Perk type (nil-safe; entries filled with asset ids later).

The future GUI (a separate *.client.luau script + authored panel) requires PerkClient, subscribes to Changed, renders from the queries, and calls the commands. It owns the Satchel topbar icon and all visibility/toggle logic.

PerkClient API surface​

Lifecycle​

  • PerkClient.Init() — idempotent. Connects PerkStateSync.OnClientEvent, binds the PartyPerkBuffs folder attribute changes, primes state. Safe to call once from the bootstrap; later GUI requires reuse the same singleton.
  • PerkClient.IsReady(): boolean — whether the first PerkStateSync has arrived.

PerkView descriptor​

The per-perk record the GUI renders:

export type PerkView = {
    Id: string,
    DisplayName: string,
    Category: PerkConfig.PerkCategory, -- "Personal" | "Party" (the perk "type")
    Level: number,                     -- levels this player has allocated
    MaxLevel: number,
    PerLevel: number,                  -- bonus fraction per level
    Description: string,               -- raw template, e.g. "+%d%% Max HP"
    EffectText: string,                -- YOUR contribution's strength, e.g. "+12% Max HP"
    EffectValue: number,               -- raw bonus fraction (PerLevel * Level)
    Icon: string?,                     -- asset id from PerkConfig (nil until set)
    CanAllocate: boolean,              -- cap + affordability gate for the "+" control
    -- Party only (nil for Personal):
    ActivePartyLevel: number?,         -- highest level active server-wide
    ActiveEffectText: string?,         -- strength at the active level, e.g. "+25% cannon damage"
    ActiveEffectValue: number?,        -- raw bonus fraction (PerLevel * ActivePartyLevel)
}

Effect strings are formatted as the existing controller does it: math.floor(PerLevel * <level> * 100 + 0.5) substituted into Description. EffectText/EffectValue use the player's own Level; the party-only ActiveEffectText/ActiveEffectValue use ActivePartyLevel. ActivePartyLevel is derived from the replicated PartyPerkBuffs folder attribute (BuffKey value / PerLevel, rounded), as the current repaint does.

Queries​

  • PerkClient.GetAvailablePoints(): { Personal: number, Party: number }
  • PerkClient.GetPerks(category: PerkConfig.PerkCategory?): { PerkView } — all perks, or one category; sorted by Order (mirrors current sortedPerks).
  • PerkClient.GetActivePerks(category: PerkConfig.PerkCategory?): { PerkView } — perks currently providing a benefit, sorted by Order. "Active" is category-aware: a Personal perk is active when the player's Level > 0; a Party perk is active when ActivePartyLevel > 0 (buffing the server, regardless of who allocated it). Pass a category for one section, omit for both.
  • PerkClient.GetPerk(perkId: string): PerkView?

Commands​

  • PerkClient.Allocate(perkId: string): boolean — gate on CanAllocate; if ok, optimistically bump Level, decrement the matching available pool, fire Changed, then Packets.ReqAllocatePerk:Fire(perkId). Authoritative reconciliation arrives via PerkStateSync. Returns whether the predict ran.
  • PerkClient.Respec(category: PerkConfig.PerkCategory) — maps category to the pool selector (Personal=1, Party=2) and fires Packets.ReqRespecPerks.
  • PerkClient.CanRespec(category): boolean — true when any points are spent in that pool (lets the GUI disable the button).

Reactivity​

  • PerkClient.Changed: Signal — a Signal.luau instance fired on every read-model change: a PerkStateSync snapshot, an optimistic Allocate, or a PartyPerkBuffs attribute change. GUI subscribes once and repaints; no polling.

Data flow​

Server ──PerkStateSync──▶ PerkClient (cache levels + available points)
PartyPerkBuffs folder ──AttributeChanged──▶ PerkClient (active party levels)
                                   │
                                   ├── Changed signal ──▶ GUI repaints
                                   └── queries ──────────▶ GUI renders PerkViews

GUI ── Allocate / Respec ──▶ PerkClient ── ReqAllocatePerk / ReqRespecPerks ──▶ Server
                                   └── optimistic predict ──▶ Changed ──▶ GUI

All connections owned by a Janitor inside PerkClient (project cleanup convention). The singleton lives for the session, so it holds one Janitor.

Decisions​

  • Icon field added to PerkConfig now (nil-safe). GUI shows no icon until asset ids are filled in.
  • No Rejected signal. Server rejections of optimistic predicts are edge cases (rapid double-spend races, exploiters); the next PerkStateSync reconciles the UI automatically, so no error-popup surface is exposed. Can be added later.
  • API owns zero instances. Satchel topbar icon and panel visibility belong to the future GUI layer.
  • Module placement in SharedModules (client-facing singleton), matching SoundManager. Only client code requires it.

Affected files​

  • src/ReplicatedStorage/SharedModules/PerkClient.luau — new.
  • src/StarterPlayer/StarterPlayerScripts/PerkController.client.luau — gutted to a bootstrap calling PerkClient.Init(); all GUI building removed.
  • src/ReplicatedStorage/SharedModules/Configs/PerkConfig.luau — add Icon: string? to the Perk type (and to entries as nil/optional).
  • Docs: update docs/systems/perks.md (UI is now consumer- driven via PerkClient); networking/signals maps unchanged (no new packets; Changed is an in-module signal, not the global Signals bus).

Testing / verification​

No automated suite (project convention — verified in Studio):

  • PerkClient.Init() runs without error on join; IsReady() becomes true after the first sync.
  • Queries return correct PerkViews; EffectText matches the old row text.
  • A temporary debug script (or the later GUI) can call Allocate/Respec and confirm optimistic predict + Changed fire, and that values reconcile on sync.
  • GetActivePerks() returns only allocated perks.
