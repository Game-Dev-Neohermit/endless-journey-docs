Consistent Floating-Junk Speed on Train State Change

Date: 2026-05-29 Status: Approved design, pending implementation plan

Problem​

Floating junk speed is baked into each junk instance at spawn time and never revisited. When the train brakes or resumes, the server flips CurrentState.Speed between DEFAULT_JUNK_SPEED (10) and STOPPED_JUNK_SPEED (5), but that value is only read by future spawns:

  • Server bakes the speed into the spawn packet: SpawnJunkEvent:Fire(id, model, pos, speed) (JunkService.server.luau:337).
  • Client stores it per-junk at spawn and the simulation loop moves each junk by data.Speed * dt forever (JunkController.client.luau:111-118, 259-275).

Result: already-floating junk keep their old speed while newly-spawned junk move at the new speed. Since the junk's apparent motion is the train's perceived motion, mixed speeds break the illusion that the train slowed down or sped up.

Goals​

  • All visible junk — existing and new — share a single linear speed at any moment.
  • On train stop/start, junk smoothly ramp to the new speed (≈1.5 s), reading as the train physically decelerating/accelerating.
  • Server-side junk lifetime stays aligned with client-side despawn so junk never disappears server-side while still visibly floating (no un-collectible ghost junk).

Non-Goals​

  • Per-junk linear speed variance. Every junk already gets the identical CurrentState.Speed at a given moment; linear speed is genuinely one global value. (Per-junk rotation speed stays varied and untouched.)
  • Reworking how the server tracks junk positions (it still doesn't track them).

Key Insight​

Because linear junk speed is a single global value, every junk moves the same distance each frame. Distance-traveled is therefore the integral of the global speed over time. Both server and client can integrate the same ramped speed timeline into a shared "odometer" and despawn each junk based on distance since its spawn — keeping both sides aligned without the server tracking positions.

Design​

1. Packets (Packets/init.luau)​

  • Add SetJunkSpeed (Server → all Clients):
    • Packet.NumberF32 — the new target junk speed.
  • Change SpawnJunk: remove the now-redundant Packet.NumberS16 speed field. New signature: (NumberU16 id, String modelName, Vector3F32 startPos).
  • Export SetJunkSpeed in the returned table.

2. Config (JunkConfig.luau)​

  • Add JunkConfig.SPEED_RAMP_DURATION = 1.5 (seconds).
  • Remove JunkConfig.MAX_LIFETIME_CAP (despawn becomes purely distance-based; see §5). Max real-world life is ~140 s at the slowest speed (700 / 5), so no time backstop is needed.

3. Shared ramp math​

Both sides advance a currentSpeed toward rampTo using smoothstep over SPEED_RAMP_DURATION:

alpha     = clamp((now - rampStart) / SPEED_RAMP_DURATION, 0, 1)
smooth    = alpha * alpha * (3 - 2 * alpha)
currentSpeed = rampFrom + (rampTo - rampFrom) * smooth

Ramp state per side: currentSpeed, rampFrom, rampTo, rampStart.

4. Server (JunkService.server.luau)​

  • Add ramp state (currentSpeed, rampFrom, rampTo, rampStart) initialized to DEFAULT_JUNK_SPEED, plus a global junkOdometer = 0.
  • SetTrainState(isMoving): instead of hard-setting CurrentState.Speed, start a ramp — rampFrom = currentSpeed, rampTo = DEFAULT_JUNK_SPEED or STOPPED_JUNK_SPEED, rampStart = os.clock() — then broadcast Packets.SetJunkSpeed:Fire(rampTo).
  • Players.PlayerAdded: Packets.SetJunkSpeed:FireClient(player, currentSpeed) so late joiners initialize to the live speed (snapped, not ramped — see §6).
  • Spawn loop: drop the speed arg from SpawnJunkEvent:Fire(...). Store spawnOdometer = junkOdometer on each activeJunks entry. Remove the per-junk task.delay lifetime cleanup.
  • Heartbeat loop (existing connection): advance currentSpeed via the ramp math, then junkOdometer += currentSpeed * dt. Scan activeJunks and remove any entry where junkOdometer - spawnOdometer > DESPAWN_DISTANCE, decrementing currentCount.

5. Client (JunkController.client.luau)​

  • Add module-level ramp state initialized to DEFAULT_JUNK_SPEED; track whether a first speed value has been received.
  • Packets.SetJunkSpeed.OnClientEvent: first receipt snaps currentSpeed (and ramp targets) to the value; subsequent receipts start a ramp (rampFrom = currentSpeed, rampTo = value, rampStart = os.clock()).
  • Remove the per-junk Speed field from ActiveJunk and from the SpawnJunk handler (which no longer receives a speed arg). Keep per-junk RotSpeed and DistanceTraveled.
  • PreSimulation loop: advance currentSpeed via the ramp math once per frame, then move every junk by currentSpeed * dt and accumulate DistanceTraveled += currentSpeed * dt. Despawn on DistanceTraveled > DESPAWN_DISTANCE (unchanged condition; now fed by the shared speed).

6. Alignment & late joiners​

DistanceTraveled += currentSpeed * dt (client) is mathematically identical to junkOdometer - spawnOdometer (server) as long as both integrate the same speed timeline from the junk's spawn. Both sides ramp with identical math, so despawn occurs at the same distance. Residual drift is bounded only by network latency on when each client receives SetJunkSpeed (tens of ms), not by the full speed delta — satisfying the "more or less aligned" requirement.

Late joiners receive a snapped SetJunkSpeed on join; any junk that spawns for them after join carries a fresh DistanceTraveled = 0, matching the server's spawnOdometer for that junk.
