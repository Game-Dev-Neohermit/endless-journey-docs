Throwable Trajectory Preview — Design

Date: 2026-06-09 Status: Approved design, pending implementation plan Scope: Client-side visible trajectory arc for throwable weapons (Grenade, C4)

Goal​

Show the local player a live, predictive arc of where a thrown weapon will land while the throwable is equipped. The arc updates every frame as the player aims, bends to stop at real geometry, and ends in a landing marker at the predicted impact point. Purely cosmetic and client-local — no networking, no server change.

Decisions (from brainstorming)​

QuestionDecision
When is the arc visible?While equipped — appears on equip, tracks the camera live, hides on unequip. Stays visible through the throw cooldown.
Arc visual styleSolid glowing line — a continuous smooth arc of thin neon parts with a soft glow.
Geometry accuracyRaycast per segment — the arc bends to stop at walls/floors/rooftops; the landing marker snaps to the real surface.
Show AOE blast radius?No — just a landing marker at the impact point, no radius ring.
Per-weapon colorsSame color for grenade and C4 (single green).

Architecture​

One new client module: src/StarterPlayer/StarterPlayerScripts/WeaponHandlers/TrajectoryPreview.luau

It exports two functions:

  • TrajectoryPreview.show(config: WeaponTypes.ThrowableWeaponConfig) — allocates the part pool and starts a RenderStepped loop.
  • TrajectoryPreview.hide() — stops the loop and destroys the pool.

A single Janitor owns every connection and instance the module creates, so a single hide() (or character teardown) cleans up fully with no leaks.

Integration surface​

ThrowableHandler gets two one-line additions — nothing else changes:

  • ThrowableHandler.OnEquip(context) → TrajectoryPreview.show(context.config)
  • ThrowableHandler.OnUnequip(context) → TrajectoryPreview.hide()

ThrowableHandler keeps owning input gating, sound, and networking. TrajectoryPreview owns only the visuals. This mirrors the existing separation between input handlers and WeaponEffectsController.

Arc Simulation Math​

Recomputed from scratch every RenderStepped frame so it tracks the live camera.

  1. Origin & direction — identical to getThrowOriginDir in ThrowableHandler: camera center-screen ray direction plus a Vector3.new(0, 0.25, 0) upward bias, normalized. Origin is the tool Handle position (fallback: character pivot). Then SPAWN_OFFSET = 2.5 studs are added along the direction — matching the exact point where ServerProjectile.spawnThrowable spawns the real clone — so the preview starts where the projectile actually starts.

  2. Ballistic sampling — the exact constant-gravity projectile equation:

    pos(t) = startPos + velocity * t + 0.5 * Vector3.new(0, -workspace.Gravity, 0) * t^2

    where velocity = direction * config.ThrowSpeed and startPos is the offset origin. This is correct because the server throwable is a plain physics body that receives a launch velocity and then falls under standard Roblox gravity — there is no air drag and no custom gravity override for throwables (only the rocket overrides gravity, via a different FastCast system). So the real free-flight path is exactly this parabola.

  3. Fixed time horizon — sample 20 points over a fixed horizon (e.g. 4 seconds) with a fixed dt = HORIZON / 19. We deliberately do not compute an analytic flight time: the naive 2*vy/g estimate breaks when aiming downward (vy negative collapses the horizon to near-zero), which is a common case (lobbing at the floor nearby). A fixed horizon plus raycast truncation handles every aim direction correctly — the horizon only needs to be "long enough," not exact.

  4. Raycast truncation — for each consecutive pair of sample points, fire workspace:Raycast(pointA, pointB - pointA, params). RaycastParams excludes the local character and uses the same filtering the real projectile relies on (the WeaponProjectile collision group passes through characters). On the first hit: stop the arc there, place the landing marker at result.Position oriented to result.Normal, and hide all remaining segments. If no segment hits within the horizon, the arc simply renders its full length with the marker at the last sample.

Rendering & Part Pool​

On show, pre-allocate a fixed pool, parented to a dedicated folder under the Camera (or workspace) so the parts are local-only and never replicate:

  • 19 segment parts (one per gap between the 20 samples).
  • 1 landing marker part.

All pool parts are created once and reused every frame — never created or destroyed inside the loop.

Segment parts:

  • Thin neon parts, green (≈ Color3.fromRGB(80, 255, 140)), Material = Enum.Material.Neon.
  • Anchored = true, CanCollide = false, CanQuery = false, CanTouch = false.
  • Each frame: positioned with CFrame.lookAt(pointA, pointB) * CFrame.new(0, 0, -length/2) and Size = Vector3.new(thin, thin, length) — the same tracer technique already used in WeaponEffectsController.spawnTracer.
  • Segments beyond the truncation point are hidden via Transparency = 1, not destroyed.

Landing marker:

  • A flat neon disc/ring (or small crosshair part) at the impact point, oriented to the hit surface normal so it lies flat on floors, walls, and rooftops.

Glow: comes for free from Material = Neon; no extra parts.

hide() destroys the whole folder in one Janitor cleanup.

Edge Cases & Cleanup​

  • No camera yet (early join): if workspace.CurrentCamera is nil, the frame is skipped (all parts hidden) until it exists — mirrors the nil-camera guard in getThrowOriginDir.
  • Character reset / death while equipped: the Janitor owns the folder and the RenderStepped connection. OnUnequip → hide() tears it down. As a backstop, the loop hides all parts on any frame where the character or its handle is missing.
  • Rapid equip/unequip: show is idempotent — tears down any prior pool before building a new one; hide is safe to call when nothing is showing.
  • Throw cooldown: the arc stays continuously visible while equipped, including during the post-throw cooldown — it does not blink off.
  • Movement: the arc recomputes every frame from the live handle position and camera ray, so it tracks naturally as the player walks and turns. RenderStepped is frame-locked to rendering, so no smoothing is needed.

Non-Goals​

  • No server-side change, no new packets — the arc is purely local cosmetic.
  • No AOE radius ring.
  • No per-weapon arc colors.
  • No arc for the rocket launcher or other weapons (throwables only).

Verification​

No automated suite (per project convention). Verified in Studio:

  1. Equip the Grenade, sweep the camera across walls, floors, rooftops, and straight down — confirm the arc bends to stop at geometry and the marker lies flat on the hit surface.
  2. Repeat with C4 (different ThrowSpeed) and confirm the arc shape changes accordingly.
  3. Throw and confirm the projectile lands at (or very near) the predicted marker.
  4. Equip/unequip rapidly and on death — confirm no leftover parts and no errors.
