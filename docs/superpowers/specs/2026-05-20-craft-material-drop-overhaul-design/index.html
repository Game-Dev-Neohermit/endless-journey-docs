Craft Material Drop Overhaul

Date: 2026-05-20
Branch: overhaul-proximity-item
Status: Approved

Root Cause​

Shredder output placed full Tool objects into workspace.DroppedMaterials. Roblox treats any Tool in workspace as equippable: when a player character overlaps it, the engine auto-equips the tool. Because the tool's Handle was Anchored = true at the moment of auto-equip, equipping an anchored part causes a character physics glitch (sinking underground).

This is not a CanCollide or anchor-ordering issue — those were red herrings. The fix is structural: Tools must never exist in workspace. Tools live only in Character models and Backpack.

Fix Overview​

Dropped craft materials in the world are represented as a plain Model wrapper containing the Handle BasePart. No Tool instance ever touches workspace. On proximity pickup the callback clones a fresh Tool from the ReplicatedStorage.CraftingMaterials template and gives it to the player.

This eliminates the auto-equip path entirely.

Desired Lifecycle​

Shredder ejects material
  Handle (BasePart) cloned from template, wrapped in Model
  CanCollide = false, Anchored = true, CollisionGroup = DroppedMaterial
        ↓
  Arc animation (MotionMaster.SplineMove)
        ↓
  Lands at randomised position
  CanCollide = false, Anchored = true  ← stays this way
        ↓
  ProximityPickupServer.RegisterItem(mat, meta, pickupCallback, false)
  → PickupItemReady fires → HoverEffect + spin starts
  → Pickup zone goes live
  → Auto-collect timer running in parallel
        ↓
  Player walks into zone (or auto-collect fires)
  → executeClaimAsync runs
  → After FLOAT_DURATION: pickupCallback clones Tool from template → Backpack
  → World Model (wrapper + Handle) destroyed by ProximityPickupServer
        ↓
  Player G-drops from hotbar
  → CraftMaterialDropService clones Handle from template
  → Destroys Tool from character
  → Applies forward impulse
  → Landing detection loop (GetTouchingParts + velocity)
  → ProximityPickupServer.RegisterItem(mat, meta, pickupCallback, false)
  → Same pickup flow as above

Collision Groups​

GroupCollides withUsed by
DefaultDefaultCharacters, walls, most geometry
DroppedMaterialDroppableSurface onlyIn-flight and landed Handle parts
DroppableSurfaceDroppedMaterialTrain platform, workbench surfaces (CollectionService-tagged)

DroppedMaterial ignores Default (characters pass through) and ignores itself (handles don't collide with each other). Handles have CanCollide = false during the arc and while landed/unclaimed; CanCollide = true only during G-drop free-fall so they land physically on surfaces.

The collision group registration and surface-group assignment code already lives in DroppedToolService. All new code that creates dropped Handles sets handle.CollisionGroup = "DroppedMaterial".

What Changes​

1. src/ServerScriptService/ShredderServer.server.luau — ejectMaterials​

Remove:

  • template:Clone() (clones entire Tool)
  • All staged changes from the prior failed fix
  • The AncestryChanged re-register listener (G-drop replaces it)
  • keepModel = true — world model is now temporary

Add:

  • Clone only the Handle: template.Handle:Clone()
  • Wrap in a Model container (Instance.new("Model")), set PrimaryPart = handle
  • Copy MaterialType / ItemType attributes to the Model
  • handle.CollisionGroup = "DroppedMaterial", handle.CanCollide = false, handle.Anchored = true
  • Call ProximityPickupServer.RegisterItem(mat, metadata, pickupCallback, false) — keepModel = false
  • Guard: if not mat.Parent then return end after RegisterItem (merge may have destroyed mat)
  • CollectionService:AddTag(mat, "CraftMaterial") after RegisterItem guard

Pickup callback (clone from template):

local function pickupCallback(claimedPlayer: Player, meta: { [string]: any })
    local qty = (meta.Quantity or 1) :: number
    for _ = 1, qty do
        local tool = template:Clone()
        tool:SetAttribute("MaterialType", capturedMaterialName)
        tool:SetAttribute("ItemType", capturedMaterialName)
        tool:SetAttribute("IsCraftMaterial", true)
        tool.CanBeDropped = false
        tool.Parent = claimedPlayer.Backpack
    end
end

Handles merge quantities (clone qty times from template).

2. src/ServerStorage/SharedModules/ProximityPickupServer.luau​

Discard all staged changes — revert to last committed state. The Anchored = false before Callback ordering issue is now irrelevant since nothing uses keepModel = true for craft materials.

3. src/ReplicatedStorage/SharedModules/Packets/init.luau​

Add one client→server packet:

Packets.RequestDrop = Packet.new("RequestDrop", {})

No payload — server infers which item from the character's equipped tool.

4. New: src/StarterPlayer/StarterPlayerScripts/DropController.client.luau​

-- Binds G to drop the active hotbar slot (equipped tool) when it is a craft material.
ContextActionService:BindAction("DropCraftMaterial", function(_, state, _)
    if state == Enum.UserInputState.Begin then
        Packets.RequestDrop:Fire()
    end
    return Enum.ContextActionResult.Pass
end, false, Enum.KeyCode.G)

5. New: src/ServerScriptService/CraftMaterialDropService.server.luau​

Listens for RequestDrop packets. For each request:

  1. Validate: character exists, has an equipped Tool with IsCraftMaterial attribute and a valid ItemType
  2. Rate-limit: 1-second cooldown per player (server-side table)
  3. Look up template: ReplicatedStorage.CraftingMaterials:FindFirstChild(itemType)
  4. Clone template.Handle, wrap in Model, set attributes, CollisionGroup = "DroppedMaterial", CanCollide = true, Anchored = false
  5. Destroy the equipped Tool from the character (safe — it was a clone from template)
  6. Parent the Model to workspace.DroppedMaterials
  7. Apply impulse: handle:ApplyImpulse(hrp.CFrame.LookVector * DROP_IMPULSE * handle.AssemblyMass)
    • DROP_IMPULSE = 20 (tunable constant at top of file)
  8. Landing detection loop (mirrors DroppedToolService.startLandingLoop):
    • Poll every ProximityPickupConfig.DROP_POLL_INTERVAL
    • Condition: handle:GetTouchingParts() has a DroppableSurface-tagged part AND handle.AssemblyLinearVelocity.Magnitude < SETTLED_VELOCITY_THRESHOLD
    • Timeout: ProximityPickupConfig.DROP_LANDING_TIMEOUT
  9. On landing: handle.Anchored = true, handle.CanCollide = false, reset rotation, call ProximityPickupServer.RegisterItem(mat, {MaterialType=itemType, ItemType=itemType, Quantity=1}, pickupCallback, false), then CollectionService:AddTag(mat, "CraftMaterial")
  10. Pickup callback: identical to shredder callback — clone fresh Tool(s) from template

6. src/ServerScriptService/DroppedToolService.server.luau​

No logic changes. The DescendantAdded handler (requires IsCraftMaterial) becomes dead code since CanBeDropped = false on craft material templates — it can never fire. Collision group setup and surface group assignment remain active and serve both shredder and G-drop handles.

Staged Changes to Discard First​

Before implementing, run:

git restore --staged src/ServerScriptService/ShredderServer.server.luau
git restore --staged src/ServerStorage/SharedModules/ProximityPickupServer.luau
git restore src/ServerStorage/SharedModules/ProximityPickupServer.luau
git restore src/ServerScriptService/ShredderServer.server.luau

DroppedToolService has unstaged changes (API-only updates: SetPartCollisionGroup → .CollisionGroup property). Commit these separately before the main work.

Out of Scope​

  • No changes to ProximityPickupController (client hover/spin).
  • No changes to ProximityPickupServer logic (beyond discarding staged changes).
  • No changes to MaterialPickupService (handles non-shredder world craft materials via CraftMaterial tag).
  • No changes to the auto-collect loop in ShredderServer.
  • No UI for the G-drop action (no on-screen prompt needed for MVP).
  • DroppedToolService is not repurposed — it stays as-is for potential non-craft-material tool drops.
