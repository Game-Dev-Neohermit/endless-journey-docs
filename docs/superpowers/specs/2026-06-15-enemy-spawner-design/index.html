Enemy Spawner — Design Spec

Date: 2026-06-15 Status: Approved (brainstorming), pending implementation plan Author: brainstorming session

1. Purpose​

A generic, server-authoritative combatant spawner for the pirate-encounter and outpost gameplay loops. It places enemy (and, generically, friendly) NPC Models at authored spawn points on a model — including a moving pirate ship — with radial jitter, placement verification (no spawning in walls, under floors, or over the void), and adaptive point selection that favors under-used points.

The encounter flow it serves:

cutscene → pirate ship approach → cannon battle → boarding → ENEMY SPAWN
outpost: player stops at outpost → ENEMY SPAWN

The spawner owns only the act of spawning. It does not own when spawning happens — the cutscene/boarding/outpost orchestrators (out of scope) call its API and react to its lifecycle events. This mirrors how CombatService stays a single-purpose damage router; its doc explicitly notes "Enemy AI/spawning is supplied elsewhere." This spec is that "elsewhere," for spawning only.

Explicitly out of scope​

  • Enemy AI / behavior / pathfinding movement.
  • The cutscene / cannon / boarding state machine.
  • Outpost-stop trigger detection (what decides "player stopped").
  • Enemy model art assets (referenced by name; authored in Studio).

2. Relationship to existing systems​

  • SpawnHelper (ReplicatedStorage/SharedModules) is volume-weighted random point picking from a static workspace.SpawnVolumes folder. It is not point-based, not adaptive, has no verification, and cannot follow a moving ship. This spec introduces a new module; it does not extend SpawnHelper.
  • Factions — spawned Models are tagged EnemyNPC (or FriendlyNPC). This single tag is the entire contract that makes them damageable (CombatService.ApplyToModel resolves via Factions.resolve) and places them in the Character collision group (NpcCollisionService). The spawner does not touch combat or collision logic — only tagging.
  • JunkConfig + JunkAssets — the config/auto-populate pattern is mirrored for EnemySpawnerConfig + ServerStorage.EnemyAssets.
  • Signals, Janitor, Configs/ — standard project conventions used throughout (in-process event bus, cleanup primitive, config-driven tuning). No raw RemoteEvents; the spawner is server-only so no Packets are required (spawned Models replicate to clients natively).

3. Modules​

ModuleLocationResponsibility
EnemySpawnerServerStorage/SharedModules/EnemySpawner.luauServer-only service: public API, group registry, cumulative spawn counts, wave handles, drip-feed scheduling, global enemy cap.
SpawnVerificationReplicatedStorage/SharedModules/SpawnVerification.luauPure placement validator: ground raycast (+ Y snap), wall/headroom overlap, enemy spacing. Stateless, independently testable.
EnemySpawnerConfigReplicatedStorage/SharedModules/Configs/EnemySpawnerConfig.luauArchetype registry + verification/weighting tuning; auto-populates model lists from ServerStorage.EnemyAssets.

SpawnVerification is placed in shared (not server) storage because it is pure geometry with no server-only dependencies; living in SharedModules keeps it reusable (e.g. a future client-side preview) and isolates it for testing. All calls to it in v1 happen server-side.

4. Spawn-point authoring (Studio)​

A spawn group is a Model with CollectionService tag EnemySpawnGroup.

  • Group identity: a GroupName string attribute on the model; if absent, the model's .Name is used.
  • Each spawn point is an Attachment tagged EnemySpawnPoint, parented anywhere beneath the group model.
  • Per-point optional attributes:
    • Radius (number) — radial jitter disc radius in studs. Falls back to the archetype DefaultRadius, then a global default.
    • Weight (number) — base selection weight. Defaults to 1.

Because the attachments are descendants of the ship Model, their .WorldPosition moves with the ship's CFrame automatically; the spawner reads world positions live at spawn time. The outpost uses the identical setup on a static model. Studio-authorable and visually editable — no code changes to add or move a spawn point.

The pirate-ship example (points A–E) is exactly this: five EnemySpawnPoint attachments under the ship model.

5. Configuration schema​

-- EnemySpawnerConfig.luau (mirrors JunkConfig structure)

EnemySpawnerConfig.GLOBAL_MAX_ENEMIES = 40   -- hard cap across all groups (perf)
EnemySpawnerConfig.DEFAULT_POINT_RADIUS = 6  -- fallback jitter radius (studs)
EnemySpawnerConfig.WeightFalloff = 1.0       -- exponent k: effectiveWeight = Weight / (count + 1)^k

EnemySpawnerConfig.Verification = {
    MaxGroundDrop   = 25,                     -- max downward raycast to find floor
    HeadroomSize    = Vector3.new(3, 6, 3),   -- box checked for wall/ceiling overlap
    MinEnemySpacing = 4,                      -- reject if a living enemy is within (studs)
    MaxRetries      = 8,                       -- jitter re-rolls before skipping an enemy
}

export type Archetype = {
    Model: string,        -- child name under ServerStorage.EnemyAssets
    Health: number,
    WalkSpeed: number,
    DefaultRadius: number,
    Faction: ("Enemy" | "Friendly")?,   -- default "Enemy"; sets EnemyNPC/FriendlyNPC tag
}

EnemySpawnerConfig.Archetypes = {
    PirateGrunt = { Model = "PirateGrunt", Health = 100, WalkSpeed = 14, DefaultRadius = 6 },
    PirateBrute = { Model = "PirateBrute", Health = 300, WalkSpeed = 10, DefaultRadius = 4 },
}

At module load, archetype Model names are validated against ServerStorage.EnemyAssets children (warn on missing), the same way JunkConfig validates against JunkAssets. Building before art is ready is supported by registering a placeholder dummy model in EnemyAssets.

All tuning lives here per project convention — no magic numbers in spawner code.

6. Public API (EnemySpawner)​

export type SpawnComposition = string | { [string]: number }  -- archetype name, or weighted set

export type SpawnRequest = {
    count: number,
    composition: SpawnComposition,
    interval: number?,   -- seconds between spawns; nil/0 = all at once (drip-feed)
    seed: number?,       -- optional deterministic RNG seed (testing/repro)
}

EnemySpawner.SpawnWave(groupName: string, request: SpawnRequest): WaveHandle
EnemySpawner.SpawnAt(groupName: string, pointName: string, archetype: string): Model?
EnemySpawner.ResetGroup(groupName: string)   -- clears cumulative counts (new encounter)
  • SpawnWave spawns count enemies across the group's points using the selection algorithm (§7). If interval > 0, spawns are scheduled one-per-tick across time (drip-feed) via the handle's Janitor; the handle is returned immediately. composition is resolved per enemy: a string spawns that archetype; a weighted table rolls per enemy.
  • SpawnAt is the direct escape hatch (place one archetype at one named point, still verified). Returns the Model or nil if verification fails.
  • ResetGroup clears the group's cumulative per-point counts at the start of a new encounter so weighting starts fresh.

Group registration is lazy: the first call referencing a groupName resolves and caches the tagged EnemySpawnGroup model and its EnemySpawnPoint attachments. A CollectionService listener keeps the cache live if points are added/removed at runtime.

7. Per-enemy spawn algorithm​

For each enemy in a wave:

  1. Select a point — weighted random over the group's points, where effectiveWeight = point.Weight / (cumulativeCount + 1) ^ WeightFalloff. Points that have spawned fewer enemies this encounter are proportionally more likely. A point never used (count 0) carries full weight and wins most often. (Per the A–E example: once A–D have spawned and E has not, E dominates the roll.) Cumulative-per-encounter semantics: deaths do not reduce a point's count; only ResetGroup does.
  2. Jitter — candidate position = point world position + a uniform random offset within a disc of the point's Radius on the XZ plane.
  3. Verify (SpawnVerification, §8). On failure, re-roll step 2.
  4. Retry-then-skip — repeat steps 2–3 up to MaxRetries. If no valid position is found, skip this enemy, warn, and continue the wave. Never spawn a broken enemy; never hard-fail the wave.
  5. Place:
    • Respect GLOBAL_MAX_ENEMIES; if at cap, skip (and warn).
    • Clone the archetype Model from ServerStorage.EnemyAssets.
    • Position it on the verified (ground-snapped) CFrame.
    • Apply archetype stats (Humanoid.MaxHealth/Health, WalkSpeed).
    • Tag EnemyNPC (or FriendlyNPC if archetype Faction == "Friendly").
    • Parent to a workspace.ActiveEnemies folder (created on first use).
    • Increment the chosen point's cumulative count.
    • Register the enemy with the WaveHandle (§9).
    • Fire Signals.OnEnemySpawned(position, archetypeName) (§10).

8. SpawnVerification​

Stateless validator. Proposed surface:

export type VerifyResult = { ok: boolean, position: Vector3?, reason: string? }

SpawnVerification.Verify(
    candidate: Vector3,
    bodySize: Vector3,                 -- archetype/headroom box
    ignoreList: { Instance },          -- group model, ActiveEnemies, etc.
    livingEnemies: { Model }           -- for spacing test
): VerifyResult

Checks, in order (cheapest first, short-circuit on failure):

  1. Ground below — workspace:Raycast straight down up to Verification.MaxGroundDrop. No hit ⇒ fail "void". On hit, set position to the hit point + half body height (snaps the enemy onto the floor regardless of jitter Y).
  2. Clear of walls / headroom — workspace:GetPartBoundsInBox of HeadroomSize centered on the snapped position, with an OverlapParams filter excluding ignoreList. Any solid (non-ignored, collidable) part ⇒ fail "blocked" (catches in-wall and under-floor cases).
  3. Spacing — reject if any model in livingEnemies is within MinEnemySpacing of the snapped position ⇒ fail "crowded".

Deferred (documented Future, §12): line-of-sight / reachability.

9. WaveHandle (lifecycle)​

SpawnWave returns a handle backed by a Janitor:

export type WaveHandle = {
    OnCleared: Signal.Signal<()>,    -- fires once when the last living enemy dies
    GetAlive: (self) -> number,
    GetEnemies: (self) -> { Model },
    Despawn: (self) -> (),           -- destroy remaining enemies + clean up
    Destroy: (self) -> (),           -- Janitor teardown (implies Despawn)
}
  • Each spawned enemy's Humanoid.Died (and AncestryChanged/removal, to cover despawns) is tracked via the handle's Janitor. When the alive count reaches 0 and all scheduled drip-feed spawns have completed, OnCleared fires once.
  • Despawn lets an orchestrator abort a wave (e.g. encounter cancelled / train resumes) and cleanly remove remaining enemies.
  • The boarding/outpost orchestrator pattern: local wave = EnemySpawner.SpawnWave(...); wave.OnCleared:Connect(resumeEncounter).

10. Signals​

Add to Signals/init.luau (and register in docs/.../signals-map.md in the same commit, per the docs rule):

-- Enemy Spawner System (Server Side)
-- Fired by EnemySpawner after each successful placement; lets a controller
-- play a spawn telegraph (SoundManager SFX + MotionMaster VFX) at the spot.
OnEnemySpawned = Signal() :: Signal.Signal<Vector3, string>,  -- (position, archetypeName)

No new Packets — enemies are server Models that replicate natively, and the spawn telegraph signal is consumed server-side (a server VFX relay or the existing sound replication path). If a client-only telegraph is later wanted, it goes through Packets then.

11. v1 scope (folded in per approval)​

  • Drip-feed interval scheduling.
  • OnEnemySpawned telegraph signal (signal only; VFX/SFX wiring is a thin follow-up using SoundManager + MotionMaster).
  • seed for deterministic testing.
  • Global enemy cap.
  • Faction-generic (Enemy/Friendly) spawning.

12. Future directions (documented, not built)​

  • Off-screen spawn preference — additional weighting term that demotes points currently inside any player's camera frustum, so enemies appear behind cover. Slots into the §7 step-1 weight.
  • Reachability pre-check — PathfindingService:CreatePath from candidate to nearest player, rejecting sealed-off points. The deferred §8 LOS check, done properly. Build alongside enemy pathfinding AI.
  • Encounter director — a layer above the spawner scaling count/composition by wave number, player count, or Tech-Tree progress. Separate module; the spawner stays dumb.

13. Testing / verification (Studio)​

No automated test suite (project convention). Verify in Studio:

  • Author an EnemySpawnGroup on a movable part + 5 EnemySpawnPoint attachments; SpawnWave(..., {count=5, composition="PirateGrunt"}).
  • Confirm: no enemy under floor / in wall / over void; ground-snapped; spacing respected; weighting visibly favors unused points across repeated waves; drip-feed staggers; OnCleared fires when all die; Despawn removes remainder; moving the ship part then spawning places relative to its new pose; GLOBAL_MAX_ENEMIES cap holds.
