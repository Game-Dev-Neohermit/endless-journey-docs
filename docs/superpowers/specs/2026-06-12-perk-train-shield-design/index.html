Perk System — Train Shield + Train Shield Perk (Spec 4 of 5)

Date: 2026-06-12 Status: Approved for planning Game: Endless Journey (Roblox / Rojo / Luau) Series: Spec 4 of 5 — depends on Spec 1 (Perk Framework); relates to the existing Tech Tree (Durability nodes) and the Train Fuel / Energy economy. Prerequisite: Spec 1 implemented (the TrainShield perk is declared and publishes PartyPerkBuffs.TrainShieldBonus, but no consumer exists because there is no train-defense system).

Summary​

Build the train's defensive pool as a shield — the entity the Tech Tree's Durability nodes have been buffing into the void (TechTreeBuffs.MaxHP is written but never read). It is a global, server-authoritative pool for the train, modeled on TrainFuelManager: one shared value, event-driven (changes only on damage/recharge, no per-frame loop), replicated to all clients for a HUD, and reaching 0 triggers game over (sharing the fuel system's game-over path).

Players recharge the shield by inputting Energy items at a shield console — the same Energy crafting items used to refuel the engine — mirroring the existing ReqRefuelTrain interaction. Energy thus becomes a shared resource the party allocates between fuel (keep moving) and shield (stay protected).

Then wire the Train Shield party perk: shield capacity scales by the resolved party TrainShieldBonus, stacking with the Tech Tree's additive MaxHP buff.

This spec provides the damageable target + damage API + the Energy recharge interaction; the enemy AI / hazards that actually attack the train are a separate future combat concern (the API and a tagged core part are provided so that work has a clean target).

Architecture​

Mirrors the fuel system's structure and the project's server-authoritative pattern. The recharge interaction reuses the proven ReqRefuelTrain shape (proximity-validated, consumes Energy tools from the backpack).

Game-over is not duplicated: TrainShieldManager calls into the existing game-over authority. Refactor the onGameOver logic out of TrainFuelManager into a tiny shared TrainGameOver module (or expose TrainFuelManager.TriggerGameOver()), so both "fuel stalled too long" and "shield depleted" funnel through one idempotent path.

Config additions​

-- TrainConfig (new keys)
TrainConfig.BASE_SHIELD = 1000            -- shield capacity before any Tech Tree / perk buffs
TrainConfig.SHIELD_REGEN_ENABLED = false  -- passive shield regen off by default
TrainConfig.SHIELD_REGEN_PER_SEC = 0      -- (only used if enabled)
TrainConfig.CORE_TAG = "TrainCore"        -- CollectionService tag on the damageable core part(s)
TrainConfig.SHIELD_CONSOLE_TAG = "ShieldConsole" -- tagged Model the player feeds Energy into
TrainConfig.SHIELD_PROMPT_PART_NAME = "ProxPromptPart" -- prompt part on the console (matches engine)

-- Shield restored per Energy tool, keyed by its Tier attribute (1..5).
-- Mirrors TrainConfig.TierRecharge (fuel). Tunable independently of fuel.
TrainConfig.ShieldRecharge = {
    [1] = 50, [2] = 100, [3] = 200, [4] = 300, [5] = 500,
}

BASE_SHIELD is the single capacity knob; Durability Tech nodes add flat capacity (their existing StatBuff MaxHP, now consumed as shield), and the Train Shield perk multiplies the total. (The Tech Tree's MaxHP attribute name is kept as-is to avoid touching the Tech Tree; its node copy can be reworded to "shield" in that system's docs.)

Components & responsibilities​

  • TrainShieldManager (server authority). Global state: currentShield, maxShield. API:
    • ApplyDamage(amount, source?) — clamps currentShield = max(0, currentShield − amount); on 0, triggers game over (once). The single damage sink (future enemy AI/hazards call this).
    • RechargeFromEnergy(player, consoleModel) — proximity-validate against the tagged console (server slack PROXIMITY_TOLERANCE, like refuel); scan the player's Energy tools; consume them smallest-tier-first, only as many as needed to reach maxShield, crediting ShieldRecharge[tier] per tool; returns the amount restored + a reason code. Mirrors ReqRefuelTrain semantics exactly (validate-then-consume; never over-fill).
    • GetShield() -> (currentShield, maxShield).
    • recomputeMax() — maxShield = (BASE_SHIELD + TechTreeBuffs.MaxHP) * (1 + TrainShieldBonus); when max changes, preserve the ratio (currentShield = round(ratio * newMax)) so a buff that raises max doesn't fully recharge and a respec that lowers it doesn't instantly deplete.
    • Initialize() — set initial shield = max, wire PlayerAdded (full sync to joiner), subscribe to TechTreeBuffs:GetAttributeChangedSignal("MaxHP") and PartyPerkBuffs:GetAttributeChangedSignal("TrainShieldBonus") → recomputeMax + sync.
    • Replicates via TrainShieldSync on every change.
  • TrainShieldController (client). Binds a ProximityPrompt on the tagged shield console (matching the engine refuel prompt UX); on trigger, fires ReqRechargeShield(consoleModel). Plays a recharge SFX via SoundManager on success. No authoritative state.
  • TrainShieldGuiController (client). Subscribes to TrainShieldSync, fires Signals.OnTrainShieldChanged(currentShield, maxShield), renders a shield bar (mirrors TrainFuelGuiController). Read-only display.
  • Game-over unification. Extract TrainGameOver.Trigger() (idempotent) used by both the fuel stall timer and TrainShieldManager. Behavior identical to today's fuel game over.

Train Shield perk wiring​

The perk is consumed entirely inside recomputeMax (above) — no separate consumer file. The Spec 1 dispatcher already publishes PartyPerkBuffs.TrainShieldBonus (party max); this spec makes something finally read it, alongside the Tech Tree's MaxHP.

Network protocol (new Packets)​

-- Server → Clients: authoritative shield. Event-driven (on damage/recharge/buff change) and a
-- full send to each joining player. Shield need not be extrapolated (no continuous drain).
TrainShieldSync = Packet("TrainShieldSync",
    Packet.NumberF32,  -- currentShield
    Packet.NumberF32    -- maxShield
)

-- Client → Server: feed the player's suitable Energy tools into the shield console
-- (smallest-first, only as much as needed to reach max). Mirrors ReqRefuelTrain.
ReqRechargeShield = Packet("ReqRechargeShield",
    Packet.Instance    -- shield console Model
):Response(
    Packet.Boolean8,   -- success
    Packet.NumberF32,  -- shieldAdded
    Packet.NumberU8     -- reason code (TrainResultCodes — reuse/extend)
)

One new Signal: OnTrainShieldChanged(currentShield, maxShield) (client HUD bridge), matching the OnTrainStateChanged fuel pattern.

Data flow​

  • Damage: (future enemy/hazard) → TrainShieldManager.ApplyDamage(amount) → clamp → TrainShieldSync broadcast → HUD updates. At 0 → TrainGameOver.Trigger().
  • Recharge: player at console triggers prompt → ReqRechargeShield(console) → server proximity-validates, consumes Energy tools smallest-first up to maxShield, credits ShieldRecharge[tier] → TrainShieldSync broadcast + recharge SFX.
  • Buff change: Tech Durability node unlocks (sets TechTreeBuffs.MaxHP) or party TrainShieldBonus changes → recomputeMax preserves ratio → TrainShieldSync.
  • Join: new player → full TrainShieldSync so the HUD bar is correct immediately.

Edge cases & anti-exploit​

  • Server-authoritative; clients only receive TrainShieldSync and never report shield damage. ApplyDamage is server-internal (no packet entry point).
  • Recharge validates then consumes (mirrors ReqRefuelTrain): proximity re-checked server-side; Energy tools are counted and removed only as needed to reach max, never over-consumed; a player without Energy gets a NOTHING_TO_SPEND-style reason and loses nothing.
  • Energy is a shared sink: the same Energy tools can fuel or recharge shield, never both (consumed on use) — the party trades off movement vs protection. No double-spend (tools are destroyed on consume, single-threaded server events).
  • Ratio-preserving max changes: raising max (buff/Tech) keeps the same fraction filled, not a free recharge; lowering it (respec, holder leaves) clamps current shield down without instant depletion.
  • Idempotent game over: both triggers funnel through one Trigger() guarded by a fired flag — shield depletion during a fuel stall (or vice versa) fires the sequence once.
  • Party TrainShieldBonus on leave: the Spec 1 dispatcher lowers the resolved bonus when the top holder leaves; recomputeMax shrinks max with the ratio preserved.
  • Shield never exceeds max / below 0: all mutations clamp.
  • Pre-game frozen phase: if the round hasn't started (the fuel system has a frozen pre-game phase), ApplyDamage is a no-op until the round is live, so the shield can't be chipped before play begins; recharge is allowed (top off before the run).

Planning refinements (added 2026-06-13, locked)​

Confirmed against the codebase before writing the implementation plan:

  • Shared helpers — extract, don't duplicate. The Energy-tool scanning (getEnergyTier / gatherEnergyTools) and proximity validation (findPromptPart / isPlayerNear) currently live as private functions inside TrainFuelManager. The plan extracts these into shared module(s) (e.g. EnergyToolHelper and ProximityValidation under ReplicatedStorage/SharedModules/ or ServerStorage/SharedModules/ as appropriate), refactors TrainFuelManager to consume them (behavior unchanged), and TrainShieldManager reuses them. One source of truth for the recharge/proximity logic both systems depend on.
  • TrainShieldGui is authored in Studio. Like TrainFuelGui, the shield HUD is an authored StarterGui asset; TrainShieldGuiController only drives it (no in-code GUI construction). The plan documents the exact instance names the controller WaitForChilds so the Studio asset can be authored to match.
  • Pre-game freeze wiring. TrainShieldManager subscribes to Signals.SetTrainStarted (the same signal TrainFuelManager fires on first un-brake) so ApplyDamage no-ops until the round is live, per the edge-cases section.
  • Game-over today is a print stub. TrainFuelManager.onGameOver is currently a placeholder print. The extracted TrainGameOver.Trigger() wraps that same stub behavior (idempotent); a real game-over mechanic remains a separate future concern.
  • Shield HUD is simpler than fuel's. Because shield has no continuous drain (regen off by default), TrainShieldGuiController needs no per-frame extrapolation — it sets the bar from the latest TrainShieldSync snapshot (optionally eased). It mirrors TrainFuelGuiController's wiring but omits the RenderStepped prediction loop.
  • TrainResultCodes extension. Add shield-specific reason codes (e.g. INVALID_CONSOLE, SHIELD_FULL) alongside the existing fuel codes; reuse TOO_FAR and NO_ENERGY where they already fit.

Out of scope (this spec)​

  • Enemy AI / hazards that deal damage to the shield (a future combat spec calls ApplyDamage).
  • A separate underlying "hull HP" beneath the shield — the shield is the defensive pool; depletion ends the run (a two-layer shield-then-hull model is a possible future extension).
  • Per-car / segmented shields; visual shield-impact/break states beyond a basic FX hook.
  • Any new perks, GUI for perks, or persistence (Spec 1). The shield value itself is session state (not persisted), consistent with fuel.
