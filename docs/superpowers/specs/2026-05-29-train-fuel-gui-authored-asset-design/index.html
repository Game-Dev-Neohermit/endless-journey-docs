Train Fuel HUD — Adopt Studio-Authored TrainFuelGui

Date: 2026-05-29 Status: Approved (Approach A)

Goal​

Replace the programmatically-built train fuel HUD with the Studio-authored StarterGui.TrainFuelGui asset, while preserving all current runtime behavior (predicted drain, exponential easing, state-based bar coloring).

Background​

TrainFuelGuiController.client.luau currently builds its UI in code with Instance.new: a ScreenGui → FuelContainer (bottom-center track) → FuelBar (fill, recolored by state) + FuelLabel (text). It predicts fuel each frame from the last OnTrainStateChanged snapshot (fuel, rate, serverTime) and eases the displayed value toward the prediction so refuel jumps look smooth.

A designer has now authored a richer HUD directly in Studio at StarterGui.TrainFuelGui. It clones into PlayerGui on spawn and has ResetOnSpawn = false, so it is a single persistent instance for the session.

Authored asset structure (StarterGui.TrainFuelGui)​

ScreenGui "TrainFuelGui"   (ResetOnSpawn=false, IgnoreGuiInset=true, ZIndexBehavior=Sibling)
└ Frame "MainContainer"            (centered ~0.3 x 0.05, transparent)
  ├ Frame "FuelBarContainer"       (dark track, UICorner r=0.2, UIStroke)
  │ └ Frame "FuelBar"              (fill, authored 0.6 wide, yellow, Anchor (0,0.5), Pos (0,0.5), UICorner)
  └ Frame "FuelBarIconTextContainer" (overlay, transparent bg, UICorner, UIStroke)
    ├ ImageLabel "Icon"            (48x48, rbxassetid://82711797226534, ZIndex 10)
    ├ TextLabel  "FuelText"        (TextScaled, custom FontFace, black text, UIPadding + UITextSizeConstraint)
    ├ UIListLayout                 (Horizontal)
    └ UIPadding

Decisions (from clarification)​

  • Icon — static decorative fuel icon. Never modified at runtime.
  • Bar color — keep state-based coloring (green = running, yellow = braked, red = stalled). Overrides the authored static yellow at runtime.
  • FuelText — percent-only for all states (e.g. "100%"). The stalled state shows "0%" on a red bar rather than the old "OUT OF FUEL" word; state is conveyed by bar color.

Approach (A — retarget in place)​

Keep the prediction/easing/state logic; delete the UI-building code; point the render loop at the authored instances.

Changes to TrainFuelGuiController.client.luau​

  • Remove ALL GUI creation — the entire "Build UI" block: the ScreenGui, FuelContainer, FuelBar, both UICorners, and FuelLabel construction. After this change the controller must contain zero Instance.new calls that build fuel UI; it only references the Studio-authored instances. The GUI is owned entirely by the Studio asset.
  • Add reference resolution from PlayerGui:
    • gui = PlayerGui:WaitForChild("TrainFuelGui")
    • bar = gui.MainContainer.FuelBarContainer.FuelBar (resolved via WaitForChild)
    • label = gui.MainContainer.FuelBarIconTextContainer.FuelText (resolved via WaitForChild)
  • Keep unchanged: the snap table, predictedFuel(), displayedFuel, SMOOTH_K exponential smoothing, the Signals.OnTrainStateChanged connection, and the RenderStepped loop driving everything.
  • Keep the three color constants (RUNNING_COLOR, BRAKED_COLOR, STALLED_COLOR); apply to bar.BackgroundColor3.
  • Render loop output becomes:
    • bar.Size = UDim2.new(math.clamp(pct,0,1), 0, 1, 0)
    • recolor bar by state (stalled → red, braked → yellow, else → green)
    • label.Text = ("%d%%"):format(roundedPct) for all states

Because ResetOnSpawn = false, references are stable for the session; no respawn re-binding is required.

Out of scope / unchanged​

  • No packet, signal, or config changes. The data feed (OnTrainStateChanged) is untouched.
  • Styling, layout, font, icon image, corners, and strokes remain owned by the Studio asset — the controller never sets them and never creates them.
  • The controller no longer creates a ScreenGui or any UI instances at all.
  • No server-side changes.

Risks​

Duplicate TrainFuelGui (the main thing to check)​

Both the old code and the new asset use the same name, TrainFuelGui:

  • The old controller did Instance.new("ScreenGui") and named it TrainFuelGui, parenting it into PlayerGui.
  • The Studio-authored asset lives in StarterGui, and Roblox automatically copies everything in StarterGui into each player's PlayerGui on spawn — also named TrainFuelGui.

So before this change, a running game actually has two ScreenGuis named TrainFuelGui stacked in PlayerGui: the StarterGui copy plus the one the old code builds. That is the bug we're removing. It also makes PlayerGui:WaitForChild("TrainFuelGui") ambiguous — it returns whichever one appeared first, which may be the wrong (code-built) one.

After this change the controller builds nothing, so only the StarterGui copy exists and WaitForChild always resolves the authored GUI. No more duplicate.

What to verify in Studio: press Play and confirm PlayerGui contains exactly one TrainFuelGui (the one with MainContainer inside), not two. If two appear, a stale code path is still creating one.

MainContainer must not be renamed in Studio​

The controller reaches elements by path (TrainFuelGui.MainContainer.FuelBarContainer.FuelBar, etc.). If those instance names change in the Studio asset, WaitForChild will hang. Keep the authored names in sync with the paths listed in the element-mapping table.

Verification​

Verified in Studio (per project workflow, no automated tests):

  • Fuel bar fills/drains smoothly and tracks the percentage.
  • Bar turns green (running), yellow (braked), red (stalled).
  • FuelText shows percent only, reaching 0% when stalled.
  • Icon and authored styling render unchanged.
